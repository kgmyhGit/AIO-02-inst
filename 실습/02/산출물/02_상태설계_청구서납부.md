## 1. 1장 설계로 처리할 때의 문제

원인은 세 가지로 묶인다.

- 기록에 납부 여부가 없어 아직 내지 않은 청구서를 고를 수 없다.
- 같은 청구서를 바뀔 수 있는 값(금액, 기한)으로 찾았다.
- 납부 확인과 납부 실패 메일을 청구서와 구분하지 않았다.

여기에 사건이 오지 않는 경우가 더해진다. 도시가스는 납부 확인 메일을 보내지 않으므로, 본인이 표시하지 않으면 납부 여부가 끝까지 기록되지 않는다.

## 2. 데이터 계약

### 2.1 같은 청구서를 찾는 기준과 메일 종류

- **같은 청구서를 찾는 기준:** 발신 주소 `biller_address`와 청구 기간 `billing_period`가 같은 기록이다. 금액과 기한은 정정 고지서나 납부 실패 안내로 바뀌므로 기준이 될 수 없다. 표시 이름은 꾸며낼 수 있으므로 주소를 쓴다.
- **메일 종류:** 청구서, 재발송된 청구서, 정정 고지서는 기록에 하는 일이 같으므로 `bill` 하나로 묶는다. 납부 확인 `payment_confirmed`과 납부 실패 `payment_failed`는 하는 일이 다르므로 따로 둔다. 메일 종류는 실행 안에서만 쓰고 기록에는 남기지 않는다.

### 2.2 청구서 기록

| 필드 | 데이터 타입 | 형식·허용 값 | 값을 정하는 주체 | 없거나 틀릴 때 |
|---|---|---|---|---|
| `bill_id` | 문자열 | `B-` 뒤 숫자 세 자리 | 규칙(기록을 만들 때 새 번호) | — |
| `biller` | 문자열 | 발신처 표시 이름(예: `한빛카드`) | 규칙(`from`에서 분리) | 알림 문구에만 쓴다 |
| `biller_address` | 문자열 | 메일 주소 | 규칙(`from`에서 분리) | — |
| `billing_period` | 문자열 | `YYYY-MM` | LLM 추출 + 형식 검사 | `null`로 두고 `needs_check`(`invalid_extraction`)로 기록한다 |
| `amount` | 숫자 | 원 단위 정수, 1 이상 | LLM 추출 + 데이터 타입 검사 | `billing_period`와 같다 |
| `due_date` | 문자열(날짜) | `YYYY-MM-DD` | LLM 추출 + 형식 검사 | `billing_period`와 같다 |
| `status` | 문자열 | `unpaid`, `needs_check`, `closed` | 전이표 | 전이표에 없는 변화는 적용하지 않고 오류로 남긴다 |
| `check_reason` | 문자열 또는 `null` | `invalid_extraction`, `amount_mismatch`, `overdue` | 전이표 | `status`가 `needs_check`일 때만 값이 있다 |
| `close_reason` | 문자열 또는 `null` | `paid`, `dismissed`, `unconfirmed` | 전이표 | `status`가 `closed`일 때만 값이 있다 |
| `source_mail_ids` | 배열(문자열) | 이 청구서와 연결된 `mail_id` | 규칙 | 처음 기록을 만든 메일부터 차례로 추가한다 |
| `sent_reminders` | 배열(문자열) | `due_minus_3`, `due_day`, `overdue`, `check_followup` | 규칙 | 기한이 바뀌면 `due_minus_3`과 `due_day`를 지운다 |
| `status_changed_at` | 문자열(시각) | ISO 8601, `+09:00` 포함 | 규칙 | 본인 확인을 기다린 기간을 셀 때 쓴다 |

`source_mail_ids`와 `sent_reminders`는 다시 실행해도 결과가 같게 만드는 필드다. 검사에 실패한 청구서도 `needs_check`로 기록해 두고, 지출 합계를 낼 때 이 상태의 기록을 뺀다.

## 3. 상태와 흐름

### 3.1 상태 값

| 상태 값 | 뜻 | 기다리는 대상 |
|---|---|---|
| `unpaid` | 청구서가 기록되었고 납부가 확인되지 않았다 | 납부 확인 메일, 본인의 '납부함' 표시, 납부 기한 |
| `needs_check` | 자동으로 판단할 수 없어 본인 확인을 기다린다. 이유는 `check_reason`에 적는다 | 본인의 수정이나 표시 |
| `closed` | 더 이상 추적하지 않는다. 이유는 `close_reason`에 적는다 | 없음 |

`overdue`와 `paid`는 상태로 두지 않는다. 기한이 지난 청구서가 기다리는 것은 본인의 확인이므로 `needs_check`와 같고, 납부한 청구서는 더 기다릴 것이 없다. 그래서 둘 다 사유 필드의 값으로 둔다.

### 3.2 상태 전이표

| 번호 | 현재 상태 | 사건 | 조건 | 다음 상태 | 실행되는 일 |
|---|---|---|---|---|---|
| T01 | (없음) | `bill` 메일 | 같은 `biller_address`·`billing_period`의 기록이 없고, 추출값이 검사를 통과한다 | `unpaid` | 기록을 만든다 |
| T02 | (없음) | `bill` 메일 | 같은 기록이 없고, 추출값이 검사를 통과하지 못한다 | `needs_check`(`invalid_extraction`) | 기록을 만들고 본인에게 알린다 |
| T03 | 모든 상태 | 모든 메일 | `mail_id`가 이미 어느 기록의 `source_mail_ids`에 있다 | 변화 없음 | 아무것도 하지 않는다 |
| T04 | (없음) | `payment_confirmed`·`payment_failed` 메일 | 같은 기록이 없다 | 변화 없음 | 기록을 만들지 않고 본인에게 알린다 |
| T05 | `unpaid` | `bill` 메일 | 같은 기록이 있다 | `unpaid` | 금액·기한을 새 값으로 바꾸고 `mail_id`를 추가한다. 값이 바뀌었으면 본인에게 알린다 |
| T06 | `unpaid` | `payment_failed` 메일 | 같은 기록이 있다 | `unpaid` | 새 기한이 있으면 기한을 바꾼다. `mail_id`를 추가하고 본인에게 바로 알린다 |
| T07 | `unpaid`, `needs_check` | `payment_confirmed` 메일 | 같은 기록이 있고 금액이 같다 | `closed`(`paid`) | `mail_id`를 추가한다 |
| T08 | `unpaid` | `payment_confirmed` 메일 | 같은 기록이 있고 금액이 다르다 | `needs_check`(`amount_mismatch`) | `mail_id`를 추가하고 본인에게 알린다 |
| T09 | `needs_check` | `bill`·`payment_failed` 메일 | 같은 기록이 있다 | `needs_check` | 값과 `mail_id`를 갱신하고 본인에게 알린다. 상태는 본인이 정한다 |
| T10 | `unpaid` | 기한 확인 | 오늘이 기한 3일 전이나 기한 당일이고, 그 알림을 보낸 적이 없다 | `unpaid` | 알림을 보내고 `sent_reminders`에 추가한다 |
| T11 | `unpaid` | 기한 확인 | 기한이 지났다 | `needs_check`(`overdue`) | 기한 경과 알림을 보낸다 |
| T12 | `needs_check` | 기한 확인 | `needs_check`가 된 지 3일이 지났고, 다시 알린 적이 없다 | `needs_check` | 한 번 더 알린다(`check_followup`) |
| T13 | `needs_check` | 기한 확인 | `needs_check`가 된 지 7일이 지났다 | `closed`(`unconfirmed`) | 추적을 끝낸다고 알린다 |
| T14 | `unpaid`, `needs_check` | 본인 표시 | '납부함' | `closed`(`paid`) | — |
| T15 | `unpaid`, `needs_check` | 본인 표시 | '정리'(추적할 필요가 없다) | `closed`(`dismissed`) | — |
| T16 | `needs_check` | 본인 수정 | 금액·기한을 고쳤고 기한이 지나지 않았다 | `unpaid` | `check_reason`을 지운다 |
| T17 | `closed` | 같은 기록에 관한 메일 | — | 변화 없음 | `mail_id`를 추가하고 본인에게 알린다 |

T03은 표의 맨 앞에서 먼저 확인한다. T05, T06, T09처럼 기한이 바뀌는 줄에서는 `sent_reminders`의 기한 알림을 지운다.

### 3.5 종료 조건과 반복 한도

| 구분 | 값 또는 동작 | 조건 또는 한도 | 끝나거나 한도에 도달했을 때 |
|---|---|---|---|
| **종료 사유** | `paid` | 금액이 같은 납부 확인 메일이 왔거나 본인이 '납부함'을 표시했다 | 추적을 끝낸다 |
| **종료 사유** | `dismissed` | 본인이 추적할 필요가 없다고 표시했다 | 추적을 끝낸다 |
| **종료 사유** | `unconfirmed` | `needs_check`로 7일 동안 본인 응답이 없었다 | 추적을 끝낸다고 알린다 |
| **반복 한도** | 기한 알림 | 기한 3일 전과 당일에 1회씩 | 기한이 바뀌면 새 기한으로 다시 센다 |
| **반복 한도** | 본인 확인 알림 | `needs_check`가 될 때 1회, 3일 뒤 1회 | 7일 뒤 `closed`(`unconfirmed`) |
| **반복 한도** | 같은 메일 처리 | `mail_id`마다 1회 | 다시 처리하면 T03으로 건너뛴다 |

`unconfirmed`는 추적을 멈춘다는 뜻이지 요금이 없어졌다는 뜻이 아니다. 기록은 사유와 함께 남는다.

## 4. 아직 정해지지 않은 사항

- 본인이 '납부함'이나 '정리'를 표시하는 방법(알림에 답하기, 기록표에서 직접 고치기)
- 잔액 부족처럼 급한 메일을 바로 처리하는 방법. 메일함 정리가 21시에만 실행되어 09:10에 온 M24가 12시간쯤 지나서 알려진다. 트리거의 종류는 3장에서 다룬다

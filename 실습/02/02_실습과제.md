# 2장 실습과제. 데이터·상태·책임을 포함한 워크플로우 설계

# 개요

## 1. 이 실습을 통해 배울 것

이 장에서도 n8n을 실행하지 않는다. 1장에서 나눈 업무 단계를 구현할 수 있는 설계로 바꾼다. 단계 사이에 주고받는 데이터를 계약으로 정하고, 여러 날에 걸친 요청의 상태 변화와 실패·승인 경로를 그리고, 설계가 맞는지 확인할 인수 조건을 만든다.

- 함께 쓰는 기록과 단계 사이의 데이터를 계약으로 정한다.
- 여러 날에 걸친 일을 상태 값과 전이표로 설계한다.
- 실패와 승인 경로, 종료 조건, 반복 한도를 정해 모든 경로가 끝나게 한다.
- 설계가 맞는지 확인할 인수 조건과 측정 초안을 쓴다.

## 2. 실습 목차

| 실습 이름 | 종류 | 실습으로 익힐 것 |
|---|---|---|
| 2-1 식단 기록과 하루 리포트가 함께 쓰는 기록 설계 | 주제 실습(개인) | 데이터 계약, 실행 안의 데이터와 남는 기록의 구분 |
| 2-2 주간 업무 보고서 작성 흐름 설계 | 주제 실습(업무) | 단계별 입출력 계약, 실패 경로, 종료 상태와 반복 한도 |
| 2-3 반품 요청의 데이터 계약과 예외 흐름 설계 | 누적 프로젝트(함께하는 실습) | 데이터 계약, 상태 전이표와 흐름도, 승인 설계, 인수 조건 |
| 2-4 교환 요청에 같은 구조 적용 | 누적 프로젝트(스스로 하는 실습) | 같은 구조를 다른 요청 유형에 적용, 재고처럼 바뀌는 값의 처리 |
| 2-5 메일함 정리의 청구서 납부 상태 설계 | 주제 실습(개인) | 같은 대상을 찾는 기준, 상태와 전이, 기한 확인 |

2-1과 2-5는 1장 주제 실습의 식단 기록(1-2)과 메일함 정리(1-1)를 이어서 설계한다. 필요한 1장 내용은 각 실습에서 다시 설명하므로 1장 결과물이 없어도 시작할 수 있다. 2-5는 이론 2.5절을 읽은 뒤 어느 때나 할 수 있다. 2-3과 2-4는 1장 실습 1-3, 1-4의 하루마켓 고객지원 업무를 이어받는다. 이어받는 것은 1장 풀이를 마친 뒤 받은 예시 답안이다.

3장에서는 풀이를 마친 뒤 받는 2-3·2-4 설계서의 예시 답안을 이어받는다. 문의 기록 계약은 웹 문의와 메일 문의를 정규화할 목표 형식이 되고, 분기 조건은 n8n 분기 노드의 조건이 된다. 자신의 설계서는 예시 답안과 비교해 필드 이름, 상태 값, 전이가 다른 곳을 표시해 둔다.

## 3. 공통사항

**진행 방식**

모든 실습은 같은 순서로 진행한다. 먼저 이 문서와 제공 파일만 보고 주어진 시간 동안 직접 해 본다. 시간이 끝나면 강사가 예시 답안을 보여 주며 왜 그렇게 되는지 설명한다. 자신의 결과물은 고치기 전 상태로 남겨 두고, 풀이와 비교해 다른 부분을 표시한다. 예시 답안과 달라도 이유가 맞으면 성립하는 답이 있으므로, 다른 점마다 자신의 이유를 적어 둔다.

**필요한 것**

- Markdown 파일을 편집할 수 있는 편집기. JSON을 작성할 때 편집기의 JSON 문법 검사 기능을 쓰면 쉼표나 따옴표 실수를 찾기 쉽다.
- 흐름도는 Mermaid로 작성하거나, 종이에 그린 뒤 사진으로 넣어도 된다.
- n8n 설치와 외부 서비스 계정은 필요하지 않으며 비용도 들지 않는다.
- CSV 파일은 UTF-8 인코딩이다. 스프레드시트에서 한글이 깨지면 가져오기 기능에서 인코딩을 UTF-8로 지정한다.

**결과물 저장**

작업 폴더에 `02/` 폴더를 만들고 결과물을 저장한다. 설계서 양식을 복사해 이름을 바꾸어 작성한다. 실습마다 쓰는 양식의 절은 다음과 같다.

| 실습 | 사용할 양식의 절 |
|---|---|
| 2-1 | 1절(표 이름을 '분석 결과', '기록 행'으로 바꾸어 사용)과 2.5절 |
| 2-2 | 1.3절, 2절 전체 |
| 2-3, 2-4 | 양식 전체 |
| 2-5 | 1.2절(표 이름을 '청구서 기록'으로 바꾸어 사용), 2.1절, 2.2절, 2.5절 |

2-1, 2-2, 2-5는 실습에 맞게 열을 조정한 표를 '해야 할 것'에 두었다. 양식과 열이 다른 표는 '해야 할 것'의 표를 따른다.

**설계서 양식 구성**

워크플로우 설계서는 네 절로 되어 있다.

- **1절 데이터 계약:** 기록의 필드마다 여섯 항목(필드명, 데이터 타입, 필수 여부, 형식·허용 값, 만드는 단계(판단 주체), 없거나 틀릴 때)을 적는다. 한 사례를 JSON으로 적어 계약과 맞는지 확인한다.
- **2절 상태와 흐름도:** 상태 값, 상태 전이표, 실패 경로, 승인, 종료 조건과 반복 한도를 표로 적은 뒤 흐름도를 그린다.
- **3절 인수 조건:** 사례별 기대 결과와 확인 방법, 측정 초안, 기록 항목을 적는다.
- **4절:** 정책에 없어 스스로 정한 가정과 아직 정하지 못한 내용을 모은다.

1~3절은 서로를 참조한다. 1절의 필드가 2절의 분기 조건에 쓰이고, 2절의 상태가 3절의 기대 결과가 된다. 한 곳에서 이름을 고치면 같은 이름을 쓰는 다른 곳도 함께 고친다.

**주문 상태 값**

`주문목록.csv`의 주문 상태 `order_status`는 `paid`(결제 완료), `preparing`(상품 준비 중), `shipped`(배송 중), `delivered`(배송 완료) 중 하나다.

**하루마켓 실습**(2-3, 2-4)**의 공통 가정**

| 항목 | 기준 |
|---|---|
| **접수일과 영업일** | 접수일은 2026-09-10(목)이고, 재문의 두 건만 2026-09-14(월)에 접수되었다. 영업일은 토·일요일과 공휴일을 뺀 날이며, 2026-09-10부터 09-22 사이에는 공휴일이 없다 |
| **경과일** | 수령일 다음 날부터 접수일까지 달력 날짜로 센다 |
| **자동 처리 시각** | 접수부터 승인 요청까지의 자동 처리는 접수와 같은 시각에 끝난다고 본다 |
| **기한 계산** | "1영업일 뒤"는 다음 영업일의 같은 시각이다. 예를 들어 09-11(금) 14:30의 1영업일 뒤는 09-14(월) 14:30이다 |
| **반복 한도와 기한** | 실습 2-3에서 정한 값을 반품과 교환에 같이 쓴다 |
| **기한 확인** | 정해진 간격으로 실행되므로, 실제 처리는 계산한 시각 이후 첫 기한 확인에서 일어난다 |
| **요청 식별자** | 반품은 `REQ-0001`, 교환은 `REQ-0101`부터 접수 순서대로 붙인다 |
| **사건 파일** | `inquiry_id`는 요청을 처음 만든 문의를 가리킨다 |

# 2-1 - 식단 기록과 하루 리포트가 함께 쓰는 기록 설계

## 1. 실습 주제 및 상황

음식 사진을 메신저로 보내면 사진 속 음식과 영양 정보를 기록하고, 하루가 끝날 무렵 목표와 비교한 리포트를 받고 싶다.   
1장 실습 1-2에서는 이 작업을 사진 속 음식들을 기록하는 흐름과 목표와 비교하는 리포트를 작성하는 흐름으로 나누었다. 
이 두 흐름을 서로 다른 두 개의 워크플로우로 작성하며, 둘 사이에 오가는 기록을 설계한다.

| 구분 | 기록 워크플로우 | 리포트 워크플로우 |
|---|---|---|
| **시작** | 사진을 보낼 때마다 | 매일 21시 |
| **하루 실행 횟수** | 식사 횟수만큼 | 1회 |
| **한 번 실행의 입력** | 사진 1장과 설명 문구 | 그날 기록표의 행 전체와 하루 목표 |
| **판단 주체** | LLM이 음식과 영양 정보를 추정하고 규칙이 검사한다 | 규칙이 합계를 계산하고 목표와 비교한다 |
| **기록표에 하는 일** | 행을 추가한다 | 행을 읽기만 한다 |

두 워크플로우는 서로를 직접 실행하지 않고 기록표로만 이어진다. 하루 목표는 열량 2,000kcal, 단백질 100g, 나트륨 2,000mg으로 가정한다. 끼니는 1장 실습 1-2에서 정한 대로 아침(`breakfast`), 점심(`lunch`), 저녁(`dinner`), 간식(`snack`)의 네 가지로만 구분한다. LLM이 사진으로 추정한 영양 정보는 측정값이 아니다.

## 2. 이 실습의 목적

서로 다른 실행이 함께 쓰는 기록은 계약으로 약속해야 한다. 또 한 실행 안의 데이터와 실행 사이에 남는 기록을 구분해 설계한다.

관련 이론: [2.1 단계 사이를 오가는 데이터: JSON](../../../02_데이터상태책임을포함한워크플로우설계.md#21-단계-사이를-오가는-데이터-json), [2.2 입출력 계약](../../../02_데이터상태책임을포함한워크플로우설계.md#22-입출력-계약), [2.3 상태: 한 번의 실행과 여러 날에 걸친 업무](../../../02_데이터상태책임을포함한워크플로우설계.md#23-상태-한-번의-실행과-여러-날에-걸친-업무), [2.5 최소 구조와 종료 조건](../../../02_데이터상태책임을포함한워크플로우설계.md#25-최소-구조와-종료-조건)

## 3. 관련 파일

- [`templates/워크플로우설계서_양식.md`](templates/워크플로우설계서_양식.md)의 1절과 2.5절

## 4. 결과물

`02_기록설계_식단기록.md`: 기록표에서 찾은 문제, 분석 결과 계약, 기록 행 계약, 실행 데이터와 기록의 구분, 리포트가 끝나는 경우

다음을 만족해야 한다.

- 기록표 샘플에서 리포트를 틀리게 만드는 문제를 다섯 가지 이상 찾고, 각 문제를 원인과 연결했다.
- 분석 결과 계약에 허용 값, 데이터 타입, 값을 모를 때의 표기, 검사 실패 시 행동이 있다.
- 기록 행 계약에 쓰는 쪽의 규칙과 읽는 쪽의 해석이 함께 있고, 날짜와 시각 필드의 기준이 적혀 있다.
- 한 실행 안의 데이터와 남는 기록을 구분하고 이유를 설명했다.
- 리포트가 끝나는 모든 경우와 리포트가 다루는 기간이 정해져 있다.

## 5. 해야 할 것

1. **기록표에서 리포트를 틀리게 만드는 문제를 찾는다.**  
   - 9월 10일 21시에 리포트 워크플로우가 `date`가 `2026-09-10`인 행을 모아 합계를 낸다고 하자. `식단기록_샘플.csv`의 행을 `음식분석_결과샘플.json`의 결과와 한 줄씩 비교해 본다. 분석 결과의 값이 기록표에서 어떻게 바뀌었는지 비교해 문제가 될 수 있는 것을 찾는다.

    | 행 | 발견한 문제 | 리포트에 미치는 영향 | 원인 |
    |---|---|---|---|
    |  |  |  |  |

2. **LLM이 음식 사진을 분석한 결과의 계약을 정한다.** 
   - LLM의 분석 결과(`output`)가 지켜야 할 계약을 필드마다 적는다.  
   - LLM이 만드는 값이므로 검사에 실패했을 때의 행동을 반드시 적는다.  
   - 코드로 쓰는 값은 영어 snake_case로 적는다.  
   - 계약을 샘플의 다섯 결과에 적용하면 각 결과가 어떻게 처리되는지 확인한다.

    | 필드 | 데이터 타입 | 필수 | 형식·허용 값 | 없거나 틀릴 때 |
    |---|---|---|---|---|
    |  |  |  |  |  |

3. **두 워크플로우가 함께 쓰는 식단 기록 행의 계약을 정한다.** 
   - 식단 기록표의 행은 `기록 워크플로우`가 쓰고 `리포트 워크플로우`가 읽는다. 쓰는 쪽이 지킬 규칙과 읽는 쪽의 해석을 함께 적는다. 
   - 계약대로 샘플 기록을 고친 뒤, 9월 10일 21시 리포트의 열량·단백질·나트륨 합계와 값을 모르는 항목 수를 계산한다.

    | 필드 | 데이터 타입 | 형식·허용 값 | 쓰는 쪽(기록)의 규칙 | 읽는 쪽(리포트)의 해석 |
    |---|---|---|---|---|
    |  |  |  |  |  |

4. **실행 안의 데이터와 남는 기록을 나누고, 리포트가 끝나는 경우를 정한다.** 다음 데이터를 한 번의 실행 안에서만 쓰는 것과 기록으로 남기는 것으로 나눈다. 대상은 사진 파일, 분석 결과 전체, 음식별 기록 행, 하루 목표, 하루 합계, 그날 리포트를 보냈다는 사실이다. 남기는 기준은 다른 실행이 그 값을 읽어야 하는지다. 그다음 리포트가 끝나는 경우를 모두 적는다. 그날 기록이 몇 건이든, 기록이 언제 들어왔든 리포트가 어떻게 끝나는지 정한다.

    | 데이터 | 구분 | 이유 |
    |---|---|---|
    |  |  |  |

    | 경우 | 조건 | 리포트 내용 |
    |---|---|---|
    |  |  |  |

## 6. 이어서 더 해 볼 만한 주제

**운동 기록과 주간 리포트 설계하기.** 운동 앱이 운동할 때마다 거리와 시간을 기록하고, 일요일 밤에 주간 운동 리포트를 보낸다. 기록과 리포트가 함께 쓰는 행의 계약을 정하고, 기기를 차지 않은 날의 심박수를 어떻게 적을지 정해 본다. 값이 없는 것과 0인 것을 리포트가 어떻게 구분해 읽는지도 적는다.

**현장 점검 기록과 일일 보고 설계하기.** 현장 점검원이 설비 사진을 올리면 점검 항목을 기록하고, 퇴근 전에 일일 점검 보고를 만든다. 점검 결과 값의 허용 목록, 사진 판독이 불확실할 때의 표기, 점검 기록이 없는 설비의 보고 방식을 정해 본다. 보고가 끝난 뒤 들어온 기록을 어떻게 처리할지도 정한다.

**같은 사진을 두 번 보냈을 때 설계하기.** 같은 음식 사진을 실수로 두 번 보내거나 메신저가 같은 메시지를 다시 전달하는 경우를 생각한다. 기록 행의 어떤 값으로 중복을 알아낼지 정하고, 계약에 무엇을 더해야 하는지 적는다. 고친 계약으로 합계가 어떻게 달라지는지 샘플에 적용해 계산한다.

# 2-2 - 주간 업무 보고서 작성 흐름 설계

## 1. 실습 주제 및 상황

교육운영팀 팀장은 매주 금요일에 팀원들의 업무 기록을 모아 주간 업무 보고서를 써서 부서장에게 보낸다. 이 일을 자동화하는 흐름을 설계한다. 팀 구성, 기록 작성 규칙, 보고서 형식, 검토 중인 자동화안, 업무 조건은 [`data/주간보고서_시나리오.md`](data/주간보고서_시나리오.md)에 있다. 시작하기 전에 시나리오에서 다음 조건을 확인한다.

- 이번 주 기간은 2026-09-14(월)부터 09-18(금)까지다.
- 흐름은 금요일 14시에 시작한다.
- 부서장에게 가는 메일은 17시까지 팀장이 확인한 뒤에만 보낸다.
- 팀장이 가장 걱정하는 것은 LLM이 기록에 없는 성과를 써 넣는 것이다.

## 2. 이 실습의 목적

실패마다 행동과 끝나는 상태가 있고, 반복 한도가 흐름을 끝낸다는 점을 확인한다.

관련 이론: [2.2 입출력 계약](../../../02_데이터상태책임을포함한워크플로우설계.md#22-입출력-계약), [2.4 조건 분기, 실패 경로, 승인 흐름](../../../02_데이터상태책임을포함한워크플로우설계.md#24-조건-분기-실패-경로-승인-흐름), [2.5 최소 구조와 종료 조건](../../../02_데이터상태책임을포함한워크플로우설계.md#25-최소-구조와-종료-조건)

## 3. 관련 파일

- [`data/주간보고서_시나리오.md`](data/주간보고서_시나리오.md): 교육운영팀의 주간 보고서 업무와 자동화안
- [`data/주간업무기록_샘플.csv`](data/주간업무기록_샘플.csv): 팀원들이 적은 업무 기록 9행
- [`templates/워크플로우설계서_양식.md`](templates/워크플로우설계서_양식.md)의 1.3절과 2절

## 4. 결과물

`02_흐름설계_주간업무보고서.md`: 단계별 입출력, 초안의 계약과 검사 규칙, 샘플 검사 결과, 실패 경로, 종료 사유와 반복 한도, 흐름도

다음을 만족해야 한다.

- 단계마다 읽는 값, 만드는 값, 판단 주체가 있다.
- 팀장의 걱정을 막는 계약과 검사 규칙이 있다.
- 샘플에서 규칙을 어긴 기록과 기록을 내지 않은 팀원이 각각 어떻게 처리되는지 설명할 수 있다.
- 실패마다 행동과 다음 상태가 있고, 모든 경로가 끝나는 상태로 이어진다.
- 팀장이 응답하지 않을 때의 처리와 그 이유가 있다.

## 5. 해야 할 것

1. **단계별 입출력 계약을 정한다.** 시나리오의 자동화안을 수집, 검사, 집계, 초안, 확인, 발송의 여섯 단계로 보고 단계마다 읽는 값, 만드는 값, 판단 주체를 적는다. 업무기록 시트의 행 계약은 시나리오의 작성 규칙 표를 그대로 쓴다. 검사에서 기록을 제외할 때 붙일 사유의 허용 값도 정한다. 그리고 팀장의 걱정을 계약으로 막을 방법을 정한다. 필요하면 JSON 발췌로 적는다.

    | 단계 | 읽는 값 | 만드는 값 | 판단 주체 |
    |---|---|---|---|
    |  |  |  |  |

2. **샘플을 검사하고 실패 경로를 정한다.** `주간업무기록_샘플.csv`를 시나리오의 작성 규칙으로 검사한다. 규칙을 어긴 기록과 기록을 하나도 내지 않은 팀원을 찾는다. 그다음 흐름이 머무르는 상태를 두세 개로 정하고, 실패마다 관찰할 사실, 행동, 다음 상태를 적는다. 팀장이 응답하지 않는 경우도 포함한다.

    | 대상 | 검사 결과 | 이유 |
    |---|---|---|
    |  |  |  |

    | 실패 | 관찰할 사실 | 행동 | 다음 상태 |
    |---|---|---|---|
    |  |  |  |  |

3. **종료 상태와 반복 한도를 정한다.** 흐름이 끝나는 사유와, 다시 알리기·다시 수집하기·다시 쓰기·기다리기의 한도를 정한다. 17시 발송 기한 안에 어떤 경우에도 흐름이 끝나는지 확인한다. 정한 한도대로 진행했을 때 팀원별 소요 시간 합계를 계산한다.

    | 구분 | 값 또는 동작 | 조건 또는 한도 | 끝나거나 한도에 도달했을 때 |
    |---|---|---|---|
    |  |  |  |  |

4. **흐름도를 그린다.** 시작부터 모든 종료 상태까지 이어지는 흐름도를 그린다. 기다리는 지점마다 기다림이 끝나는 시각이 있는지 확인한다.

## 6. 이어서 더 해 볼 만한 주제

**가족 여행 경비 정산 설계하기.** 가족 여행이 끝난 뒤 각자 쓴 경비를 모아 정산을 요청한다. 영수증 금액의 데이터 타입 검사, 경비를 올리지 않은 가족에게 보내는 알림 횟수, 정산 요청을 확정하는 사람을 정해 본다. 정해진 날까지 올리지 않은 사람이 있을 때 흐름이 어떻게 끝나는지 적는다.

**부서별 월말 비용 보고 설계하기.** 매달 말 부서별 비용 사용 내역을 모아 경영지원팀에 보고한다. 제출하지 않은 부서의 처리, 계정 과목이 틀린 행의 제외 기준, 보고서를 확정하는 사람과 기한을 정해 본다. 제외한 행을 보고서에 어떻게 드러낼지도 판단한다.

**LLM 초안의 근거 검사 구체화하기.** 초안의 문장마다 어느 기록을 근거로 했는지 번호를 붙이게 하는 계약을 써 본다. 번호가 실제 기록에 있는지, 숫자가 기록의 값과 같은지 규칙으로 검사하는 방법을 적는다. 규칙으로 잡을 수 없는 왜곡은 무엇인지 찾아, 팀장이 무엇을 봐야 하는지 확인 화면에 담을 내용을 정한다.

# 2-3 - 반품 요청의 데이터 계약과 예외 흐름 설계

## 1. 실습 주제 및 상황

1장 실습 1-3의 배송·반품 문의의 업무 분해도 결과를 이어받는다. 이 실습은 그중 반품 요청만 설계한다. 배송 일정 문의는 한 번의 안내로 끝나지만, 반품은 승인·회수·검수·환불로 여러 날에 걸친 상태가 생기기 때문이다.

적용할 반품 정책은 1장과 같다.
- 단순 변심 반품은 수령 후 7일 이내에 할 수 있고, 착용·사용 흔적이 없고 택이 있어야 한다. 왕복 배송비 6,000원을 환불 금액에서 뺀다.

- 같은 건으로 두 번 이상 다시 문의하면 담당자에게 즉시 넘긴다.

관련 이론: [2장 이론](../../../02_데이터상태책임을포함한워크플로우설계.md)

`02_워크플로우설계서_반품.md`: 양식의 1~4절을 모두 채운 설계서(데이터 계약과 INQ-004의 JSON, 상태와 흐름도, 승인 설계, 종료 조건과 반복 한도, 인수 조건, 측정 초안, 기록 항목, 가정)

다음을 만족해야 한다.

- 문의 기록과 요청 기록의 모든 필드에 여섯 항목이 있고, 필수 여부가 "어느 단계부터"로 적혀 있다.

## 5. 해야 할 것

1. **1장의 조건을 실패 유형으로 묶는다.** 1장 업무 분해도의 '사람에게 넘기는 조건'과 판단 결과를 이론의 네 가지 실패 유형(정보 누락, 조회 실패, 정책 불일치, 승인 거절)으로 묶고, 이 장의 사례와 연결한다.

    | 1장의 조건 또는 결론 | 이 장의 분류 | 해당 사례 |
    |---|---|---|
    |  |  |  |

    - **확인 지점:** 조건마다 이어지는 행동을 실패 유형의 기본 행동으로 설명할 수 있는가?
2. **문의 기록과 요청 기록의 계약을 작성한다.** 설계서 1.1절에 문의 기록 계약을 쓴다. 1장에서 정한 필드에 요청 기록과 연결할 식별자를 더한다. 1.2절에는 요청 기록 계약을 쓴다. 요청 기록에는 식별자, 요청자, 대상(주문), 분류와 처리 방식, 상태, 근거, 승인이 모두 들어가야 한다. 필수 여부는 "어느 단계부터"로, 마지막 칸은 행동과 다음 상태로 적는다. 계약을 다 쓰면 INQ-004의 요청 기록을 승인 대기 시점 기준으로 JSON으로 적는다.
    - **확인 지점:** JSON의 값이 계약의 데이터 타입과 형식을 지키는가? 기한 확인이 여러 번 실행되어도 같은 일이 반복되지 않는가?
3. **INQ-004가 단계마다 어떻게 바뀌는지 추적한다.** 설계서 1.3절의 단계별 입출력 표를 채운다. 그 아래에 INQ-004를 따라가며 필드가 채워지는 순서를 다음 표로 더한다.

    | 단계 | 읽는 값 | 쓰거나 바꾸는 값 | 판단 주체 |
    |---|---|---|---|
    |  |  |  |  |

    - **확인 지점:** 요청 기록을 어느 단계에서 만드는지, 그 이유를 설명할 수 있는가?
4. **상태 전이표를 완성하고 INQ-004를 날짜별로 따라간다.** 요청이 머무를 수 있고 기다리는 대상이 다른 지점만 상태 값으로 정한다. 그다음 정상 경로에 실패 경로, 기한 확인, 재문의를 더해 전이표를 완성하고 줄마다 번호(T01, T02…)를 붙인다. `반품진행_사건.csv`로 INQ-004를 날짜별로 따라가며 사건마다 어느 줄이 적용되는지 적는다.

    | 번호 | 현재 상태 | 사건 | 조건 | 다음 상태 | 실행되는 일 |
    |---|---|---|---|---|---|
    |  |  |  |  |  |  |

    - **확인 지점:** 상태 값마다 기다리는 대상이 서로 다른가? 재문의가 어떻게 처리되는지 정책으로 설명할 수 있는가?
5. **승인을 설계하고 흐름도를 그린다.** 설계서 2.4절에 [이론 2.4절의 승인 흐름 설계](../../../02_데이터상태책임을포함한워크플로우설계.md#승인-흐름-설계) 항목을 반품에 맞게 채운다. 2.3절에는 실패 경로를 적는다. 그다음 전이표를 흐름도로 옮기고, 문의 9건을 그림 위에서 한 건씩 따라간다.
    - **확인 지점:** 모든 사례가 상태 상자 중 하나에서 멈추는가? 한 사례가 두 갈래로 동시에 갈 수 있는 조건은 없는가?
6. **종료 조건과 반복 한도를 적고 기한을 계산한다.** 종료 사유와 반복 한도(정보 요청, 승인 대기, 조회 오류, 분류 검사 실패, 재문의)를 정한다. 사건 파일에 사건이 없는 사례를 찾아, 그 사례가 언제 끝나는지 공통 가정으로 계산한다.
    - **확인 지점:** 영업일 계산에서 주말을 뺐는가?
7. **인수 조건, 측정 초안, 기록 항목을 작성한다.** 사례 9건의 인수 조건을 쓴다. 기대 경로는 전이표의 번호로 적고, 확인 방법에는 일어나지 말아야 할 일을 함께 적는다. 이어서 품질·시간·비용 측정 초안과 기록 항목을 쓴다.

    | 사례 | 입력 요약 | 기대 경로 | 기대 상태 | 핵심 필드의 기대 값 | 확인 방법 |
    |---|---|---|---|---|---|
    |  |  |  |  |  |  |

    - **확인 지점:** 기록 항목의 필드가 이론의 기록 항목 기준을 따르는가?

## 6. 이어서 더 해 볼 만한 주제

**부분 반품과 묶음 주문 다루기.** 한 주문의 여러 상품 중 일부만 반품하는 요청을 다룬다. 요청 기록 하나에 상품 여러 개를 담을지 상품마다 요청 기록을 만들지 비교하고, 환불 금액 계산과 왕복 배송비 차감이 어떻게 달라지는지 계약에 반영한다. 사례 두 건을 직접 만들어 전이표로 따라간다.

**승인 이후 취소 요청 다루기.** 승인을 받은 뒤 회수 전에 고객이 "반품을 취소하겠다"고 문의하는 경우를 더한다. 어느 상태까지 취소할 수 있는지 정하고 전이표에 줄을 더한다. 회수가 이미 시작된 경우와 환불이 끝난 경우에 각각 무엇을 해야 하는지, 정책에 없는 부분은 가정으로 적는다.

**다른 신청 업무로 옮겨 보기.** 비품 신청, 휴가 신청, 출장비 정산처럼 승인과 여러 날의 진행이 있는 업무를 하나 고른다. 이 실습의 양식으로 기록 계약, 상태 전이표, 승인 설계, 인수 조건을 작성한다. 반품과 같게 쓸 수 있는 부분과 달라지는 부분을 표로 정리한다.

- 교환 요청 기록의 계약에 원하는 옵션, 재고 확인 결과, 승인한 교환 내용이 들어가야 한다.
- 상태 전이표와 흐름도에는 네 가지 실패 유형과 승인 흐름을 포함한다.
- 사건 파일에 사건이 없는 사례를 찾아, 그 사례가 언제 끝나는지 공통 가정으로 계산한다.
- 재문의의 기준과 반복 한도, 기한은 실습 2-3과 같게 쓴다.

## 6. 이어서 더 해 볼 만한 주제

**처리 도중 반품으로 바꾸는 메일 다루기.** 교환 요청을 처리하는 도중에 같은 고객이 같은 주문으로 "그냥 반품하고 싶다"는 메일을 보낸다. 계약과 상태 전이표에 무엇을 더해야 하는지 설계한다. 진행 중인 교환 요청을 닫고 반품 요청을 새로 만들지 하나의 요청으로 이어 갈지 비교하고, 상태마다 허용할 수 있는지 판단한다.

**마지막 재고에 몰린 두 요청 다루기.** 재고가 1개 남은 옵션에 서로 다른 고객의 교환 요청 두 건이 거의 동시에 승인을 기다린다. 계약과 상태 전이표에 무엇을 더해야 하는지 설계한다. 승인 시점과 발송 직전 중 언제 재고를 확정할지, 늦은 쪽 고객에게 무엇을 안내할지 정한다.

**옵션 대신 다른 상품을 원하는 고객 다루기.** 정책은 다른 상품으로의 교환을 받지 않고 반품 후 새로 주문하도록 안내한다. 이 안내를 받은 고객이 다시 문의하는 경우를 재문의로 볼지 새 요청으로 볼지 정한다. 두 요청을 연결해 추적하려면 어떤 필드가 더 필요한지 계약으로 적어 본다.

# 2-5 - 메일함 정리의 청구서 납부 상태 설계

## 1. 실습 주제 및 상황

1장 실습 1-1에서는 매일 저녁 9시에 그날 받은 메일을 정리하는 작업을 분해했다. 그중 청구서 처리는 다음과 같다.
- 청구서는 금액과 납부 기한을 지출 기록표에 적는다.
- 적기 전에 같은 발신처·금액·기한의 행이 이미 있는지 확인한다.
- 금액이나 기한이 검사를 통과하지 못하면 기록하지 않고 본인에게 알린다.

이제 이 기록을 이용해, 아직 내지 않은 청구서만 납부 기한 3일 전과 당일 아침에 알림으로 받고 싶다. 청구서 기록은 두 워크플로우가 함께 쓴다.

| 구분 | 메일함 정리 | 납부 기한 확인 |
|---|---|---|
| **시작** | 매일 21시 | 매일 08시 |
| **처리하는 사건** | 그날 받은 청구서, 납부 확인, 납부 실패 메일 | 기한 3일 전과 당일, 기한 경과, 본인 확인을 기다린 기간 |
| **청구서 기록에 하는 일** | 기록을 만들거나 상태를 바꾼다 | 알림을 보내고 상태를 바꾼다 |

이 실습에서 쓰는 조건은 다음과 같다.
- 9월 11일 07시에, 전날 정리 실행이 알림 발송 단계에서 실패해 본인이 그 실행을 다시 실행했다. 그래서 M02와 M07이 한 번 더 처리된다.
- 날짜는 영업일이 아니라 달력 날짜로 센다.
- 본인이 '납부함'이나 '정리'를 표시하는 방법은 이 실습에서 정하지 않는다.
- 4단계에서는 도시가스 청구서에 대해 본인이 끝까지 '납부함'을 표시하지 않는다고 가정한다.

    |---|---|---|---|---|
    |  |  |  |  |  |

3. **상태 값과 전이표를 정한다.** 기록이 머무르고, 머무는 동안 기다리는 대상이 다른 지점만 상태 값으로 둔다. 그다음 전이표를 쓰고 줄마다 번호를 붙인다. 제공 자료에 없더라도 실제로 생길 수 있는 사건을 생각해 전이표에 넣는다.

    | 상태 값 | 뜻 | 기다리는 대상 |
    |---|---|---|
    |  |  |  |

    | 번호 | 현재 상태 | 사건 | 조건 | 다음 상태 | 실행되는 일 |
    |---|---|---|---|---|---|
    |  |  |  |  |  |  |

4. **사건 순서대로 따라가며 끝나는 시각을 확인한다.** 메일 7통과 매일 08시의 기한 확인을 시간 순서대로 전이표에 넣는다. 사건마다 적용한 전이와 기록의 변화를 적는다. 그다음 종료 사유와 반복 한도를 정하고, 모든 기록이 끝나는 날짜를 계산한다.

    | 시각 | 사건 | 적용한 전이 | 기록의 변화 |
    |---|---|---|---|
    |  |  |  |  |

    | 구분 | 값 또는 동작 | 조건 또는 한도 | 끝나거나 한도에 도달했을 때 |
    |---|---|---|---|
    |  |  |  |  |

## 6. 이어서 더 해 볼 만한 주제

**도서관 대출 기한 관리 설계하기.** 도서관에서 빌린 책의 반납 기한을 관리한다. 대출 안내, 연장 안내, 반납 확인 메일이 기록에 각각 어떤 변화를 일으키는지 정하고, 같은 대출을 찾는 기준과 연체 알림의 한도를 정해 본다. 메일이 오지 않는 경우에 어떤 실행이 기록을 끝내는지도 적는다.

**세금계산서 지급 기한 관리 설계하기.** 거래처에서 받은 세금계산서의 지급 기한을 관리한다. 수정 세금계산서, 지급 완료 통지, 기한 경과가 기록에 어떤 변화를 일으키는지 정하고, 담당자 확인을 기다리는 기간을 정해 본다. 수정본이 왔을 때 원래 기록을 고칠지 새 기록을 만들지 비교한다.

**계약 갱신 알림 설계하기.** 연간 구독이나 임대처럼 갱신 기한이 있는 계약을 기록하고, 기한 60일 전과 30일 전에 알린다. 갱신 완료, 해지 결정, 금액 변경 안내가 기록에 일으키는 변화를 전이표로 쓴다. 자동 갱신되는 계약과 직접 신청해야 하는 계약의 상태가 어떻게 달라지는지 비교한다.

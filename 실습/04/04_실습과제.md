# 4장 실습과제. API와 도구를 연결한 단일 에이전트

# 개요

## 1. 이 실습을 통해 배울 것

이 장에서는 워크플로우를 밖의 시스템과 모델에 연결한다. 공개 API를 호출하고, 모의 주문 API를 조회 도구로 만들고, 모델을 정해진 자리에서 부르는 방법과 도구를 고르며 반복하는 에이전트를 구분해 사용한다. 마지막으로 하루마켓의 배송·교환 문의에 조회 도구와 에이전트를 붙이고, 결과가 계약을 지키는지 계약 테스트로 확인한다.

- API 명세를 읽고 요청을 채우며, 응답의 모양과 오류 응답을 다룬다.
- 인증 정보를 자격 증명으로 분리하고, 조회 기능을 계약이 있는 서브워크플로우 도구로 만든다.
- 모델을 정해진 자리에서 호출할 때와 에이전트로 쓸 때의 차이를 호출 수와 결과로 비교한다.
- 사진을 모델에 넘겨 정해진 형식으로 받고, 계산은 코드가 하고 문장만 모델이 쓰게 나눈다.
- 도구 설명, 모델이 채우는 입력, 반복 한도가 에이전트의 동작을 어떻게 바꾸는지 실행 기록에서 읽는다.
- 결과를 `status`, `answer`, `evidence` 계약으로 내고, 실패해야 옳은 사례가 제대로 실패하는지 시험한다.

## 3. 공통사항

**진행 방식**

실습의 단계별 진행은 수업에서 강사와 함께 한다. 이 문서의 "해야 할 것"에는 실습마다 해야 할 작업과 주의할 점만 적었다. 스스로 하는 실습(4-7)은 이 문서와 제공 파일만 보고 주어진 시간 동안 먼저 직접 해 본다. 시간이 끝나면 강사가 예시 답안을 보여 주며 왜 그렇게 되는지 설명한다. 자신의 결과물은 고치기 전 상태로 남겨 두고, 풀이와 비교해 다른 부분을 표시한다. 예시 답안과 달라도 이유가 맞으면 성립하는 답이 있으므로, 다른 점마다 자신의 이유를 적어 둔다.

**필요한 것**

- 3장에서 만든 실행 환경과 `웹 문의 정규화`, `메일 문의 정규화` 워크플로우. 3-5를 끝내지 못했다면 3장 풀이 뒤 강사에게 받은 메일 문의 정규화 설정으로 먼저 만든다.
- ngrok 터널. `Webhook` 노드와 폼의 주소, 메일의 응답 링크는 3장에서 받은 공개 주소로 만들어지므로, 이 주소를 쓰기 전에 `ngrok http 5678`을 실행한다. 실습을 마치면 `Ctrl+C`로 닫는다. 3장에서 `localhost`로 설정했다면 필요하지 않다.
- n8n 컨테이너에서 OpenAI API, 공개 API(Open-Meteo, Frankfurter), 그리고 실습 4-3의 Telegram, Google Sheets, Gmail API에 접속할 수 있는 외부망. 확인 방법은 [`guides/외부연결_점검표.md`](guides/외부연결_점검표.md)에 있다.
- 실습 4-2부터 쓰는 OpenAI API 키. 키를 받는 방법은 강사의 안내를 따른다.
- 실습 4-3에서 쓰는 음식 사진 2~3장과 음식이 아닌 사진 1장. 직접 찍은 사진을 쓰고, 사람의 얼굴이나 개인 정보가 찍힌 사진은 쓰지 않는다.
- 실습 4-3에서 쓰는 텔레그램 계정과 Google 계정. 봇과 Google Sheets·Gmail 자격 증명을 만드는 방법은 `교재/실습/_인증관련/`의 안내 문서를 따른다.
- 그 밖의 메일, 캘린더 계정과 공개 API의 가입은 필요하지 않다.

**실행 환경 바꾸기**

첫 실습을 시작하기 전에 3장 실행 환경에 모의 주문 API를 더한다. 실습 4-1과 4-4에서 외부망이 막혔을 때 쓰는 대체 경로도 이 모의 API에 있다. 새 `04/` 폴더에 `env/`의 파일과 `mock-api` 폴더를 복사하고, 3장 `.env`를 가져와 `MOCK_API_KEY`를 더한 뒤, 3장 환경을 내리고 `04/` 폴더에서 실행한다. 순서는 `compose.yml` 머리말에 있다.

- [`env/compose.yml`](env/compose.yml): 3장 구성에 모의 주문 API를 더한 실행 구성
- [`env/환경변수_예시.env`](env/환경변수_예시.env): 더할 환경 변수 `MOCK_API_KEY`
- [`env/업무DB_초기화.sql`](env/업무DB_초기화.sql): 3장과 같은 업무 데이터베이스 초기화 스크립트
- [`env/예제DB_초기화.sql`](env/예제DB_초기화.sql): 3장과 같은 예제용 `n8n_exam` 데이터베이스 생성 스크립트
- `env/mock-api/`: 모의 주문 API 서버와 데이터. 내용을 열어 보지 않아도 된다.

**비용**

이 장부터 모델 호출 비용이 생긴다. 에이전트는 질문 하나에 모델을 여러 번 부르고 계약 테스트는 같은 사례를 여러 번 실행하므로 다음을 지킨다.

- 만드는 중에는 앞 노드의 출력에 데이터 고정을 걸어 두고, 모델이 들어간 노드만 다시 실행한다.
- 결과가 이상하면 다시 누르기 전에 실행 기록을 먼저 읽는다.
- 이 문서가 정한 반복 횟수보다 많이 실행하지 않는다.

**결과물 저장**

- 작업 폴더에 `04/` 폴더를 만들어 저장한다. 워크플로우는 JSON 파일로 내보낸다.
- 내보낸 파일에 OpenAI 키나 모의 API 키가 들어 있지 않은지 편집기로 열어 확인한다.

**모든 실습에 적용하는 기준**

| 항목 | 기준 |
|---|---|
| 모델 | `gpt-6-luna`. 채팅 모델 노드의 Options와 Use Responses API는 기본값으로 둔다 |
| OpenAI 자격 증명 | 이름을 `OpenAI 실습`으로 붙여 모든 실습에서 같이 쓴다. 키는 자격 증명에만 넣는다. 노출이 의심되면 곧바로 강사에게 알리고 키를 폐기한다 |
| 기준일 | 모의 주문 API는 2026-09-10을 오늘로 보고 날짜를 계산한다 |
| 외부 데이터 변경 | 이 장의 요청은 모두 조회다. 주문을 바꾸거나 안내문을 보내지 않는다. 예외로 실습 4-3은 본인만 보는 식단 기록을 본인의 Google Sheets에 쓰고, 본인에게 텔레그램 답장과 Gmail 리포트를 보낸다 |
| 업무 데이터베이스 | 읽기만 한다. 문의 기록 저장과 `inquiry_id` 발급은 5장에서 한다 |
| 반복 한도 | 에이전트의 `Max Iterations`는 5로 둔다 |
| 노드 이름 | 이 문서와 노드 설정 파일의 이름을 그대로 붙인다. 에이전트에 연결하는 도구 노드는 영문자, 숫자, 밑줄로 이름을 붙이고(예: `order_lookup`), 하는 일은 Description에 한국어로 적는다 |
| 데이터 | 샘플과 모의 API의 주문, 재고, 문의는 모두 실습용 가상 데이터다 |

# 4-1 - 날씨 조회 출근 알림

## 1. 실습 주제 및 상황

매일 아침 7시에 오늘 비가 올지와 최저·최고 기온을 확인해 출근 알림 문구를 받고 싶다. 공개 날씨 API인 Open-Meteo를 명세부터 읽어 호출한다. 알림 문구는 비 올 확률이 기준 이상인지만 보면 정해지므로 모델은 쓰지 않는다. 이 실습은 문구를 만드는 데까지 하며, 실제 전송은 하지 않는다.

## 2. 이 실습의 목적

- 명세를 읽어 요청을 채우는 방법을 익힌다.
- 서비스가 정한 응답의 모양을 읽어 필요한 값을 꺼낸다.
- 다시 시도해도 결과가 같은 4xx 오류를 직접 확인한다.

관련 이론: [4.1 워크플로우 밖의 시스템에 요청하기](../../../04_API와도구를연결한단일에이전트.md#41-워크플로우-밖의-시스템에-요청하기)

## 3. 관련 파일

- [`guides/API명세_읽기순서.md`](guides/API명세_읽기순서.md): 명세를 읽는 순서와 확인 질문
- [`guides/오류응답_예제.md`](guides/오류응답_예제.md): 상태 코드별 응답 예시와 다음 행동
- [`data/OpenMeteo_응답샘플.json`](data/OpenMeteo_응답샘플.json): 인터넷이 안될 때 사용할 Open Meteo API 응답 json
- [Open-Meteo 예보 API 문서](https://open-meteo.com/en/docs): 읽을 명세

## 4. 결과물

- `04_출근날씨알림.json`: 내보낸 워크플로우
- 강수 확률에 따라 두 알림 노드 중 하나만 실행되고, 그 노드의 `message` 필드에 날짜, 비 올 확률, 기온이 들어간 문구가 있다.
  - 응답메세지 예 `"message": "오늘(2026-11-07) 비 올 확률 0%입니다. 기온 -0.2~7.5°C"`

## 5. 해야 할 것

**해야 할 작업**

- `API명세_읽기순서.md`의 순서로 Open-Meteo 문서를 읽고, 다음 표를 채운다. 값을 지정하지 않았을 때 무엇이 기본값이 되는지도 함께 확인한다.

    | 찾을 것 | 찾은 내용 |
    |---|---|
    | 기본 주소와 인증 |  |
    | Http 요청 메서드 |  |
    | 필수 값 |  |
    | 강수 확률과 기온을 받는 방법 |  |
    | 시간대를 정하는 방법 |  |
    | 며칠 치를 받는가 |  |
    | 오류 응답 |  |

- 매일 7시에 실행되는 워크플로우 `출근 날씨 알림`을 만들고, 표의 내용으로 `HTTP Request` 노드(`예보 조회`)의 요청을 채운다.
- 응답에서 오늘의 `date`, `rain_probability`, `temp_max`, `temp_min`에 채울 값들을 꺼낸다.
- 비 올 확률이 기준(50) 이상인지에 따라 `우산 알림`과 `맑음 알림`으로 나누고, 각각 `message` 필드에 알림 문구를 만든다.
- 두 경로가 모두 맞게 동작하는지 시험한다.
- 필수 값을 뺀 요청으로 오류 응답을 받아 보고, `오류응답_예제.md`에서 다음 행동을 찾아 적는다.
- 워크플로우를 `04_출근날씨알림.json`으로 내보낸다.

**주의할 점**

- 쿼리 파라미터는 URL에 이어 붙이지 말고 Send Query Parameters를 켜서 칸을 나누어 적는다.
- 응답 구조를 눈으로 확인할 수 있도록 처음에는 여러 날의 예보(`forecast_days` 3)를 받아 본다. 응답에서 날짜와 값이 어떻게 짝지어 있는지 확인한 뒤 오늘 값을 꺼낸다.
- 꺼낸 숫자 필드의 데이터 타입이 숫자인지 확인한다.
- 오늘 날씨로는 한쪽 경로만 실행된다. 응답에 데이터 고정을 걸고 다른 날의 값을 꺼내도록 잠시 바꾸어 다른 경로를 시험한 뒤 되돌린다.
- 오류 응답은 다시 실행했을 때 결과가 달라지는지 확인한다. 시험이 끝나면 요청을 원래대로 되돌린다.
- 외부망이 막혀 있으면 `OpenMeteo_응답샘플.json`을 노드 출력에 붙여 넣고 데이터 고정을 건다.

## 6. 이어서 더 해 볼 만한 주제

**도시 이름을 입력받아서 날씨를 알림.** Open meteo의 Geocoding API 를 이용하면 도시명(영문)으로 위도/경도를 조회할 수 있다. n8n의 `n8n From` 노드의 `On new n8n Form event`트리거를 이용해 도시이름을 입력받고 그 도시의 날씨를 조회한다.


**야외 행사 담당자 알림.** 행사 날짜와 좌표를 입력 값으로 두고, 행사 전날 강수 확률이 기준을 넘으면 우천 대비 체크리스트를 문구에 함께 넣는다. `forecast_days`가 행사 날짜까지 닿지 않을 때 어떤 결과가 나오는지 시험하고, 예보를 얻지 못한 경우의 문구를 따로 만든다.

**실제 뉴스 피드로 3-2 바꾸기.** 3장 실습 3-2에서 샘플 목록을 붙여 넣던 부분을 `HTTP Request` 또는 `RSS Read` 노드로 바꾸어 실제 피드를 가져온다. 응답의 모양이 샘플과 어떻게 다른지 비교하고 필드 참조를 고친다. 피드를 쓰기 전에 그 매체의 이용 조건을 확인한다.

# 4-2 - 뉴스 관련성을 모델로 판단하기

## 1. 실습 주제 및 상황

3장 실습 3-2의 키워드 필터는 낱말 포함 여부만 보기 때문에 AI와 관련 없는 기사를 거르지 못했다. 이번에는 "이 기사가 인공지능에 관한 기사인가"를 모델에게 묻는다. 3장의 기사 목록을 그대로 쓰며, 3장 결과물이 없어도 시작할 수 있다.

## 2. 이 실습의 목적

- 채팅 모델을 연결하고 정해진 자리에서 한 번 부르는 방법을 익힌다.
- 모델이 어느 범주로도 정하지 못한 아이템이 어디로 가는지 확인한다.
- 같은 입력의 결과가 달라질 수 있다는 점과 아이템 수만큼 호출과 비용이 는다는 점을 확인한다.

관련 이론: [4.3 정해진 자리에서 모델 호출하기](../../../04_API와도구를연결한단일에이전트.md#43-정해진-자리에서-모델-호출하기)

## 3. 관련 파일

- [`../03/data/뉴스항목_샘플.json`](../../03/템플릿_가이드/data/뉴스항목_샘플.json): 기사 8건

## 4. 결과물

- `04_뉴스관련성판단.json`: 내보낸 워크플로우. OpenAI 키가 들어 있지 않아야 한다.
- 모든 기사가 범주별 출력 중 하나로 가며, 출력의 아이템 수를 더하면 입력 아이템 수와 같다.
- 두 번 실행한 결과를 기사별로 비교한 표와 호출 수·토큰 메모

## 5. 해야 할 것

**해야 할 작업**

- OpenAI 유형의 자격 증명 `OpenAI 실습`을 만든다.
- 새 워크플로우 `뉴스 관련성 판단`에서 실습 3-2처럼 기사 목록을 넣고 기사 한 건씩의 아이템으로 나눈다.
- `Text Classifier` 노드(`AI 관련성`)에 `OpenAI Chat Model` 노드를 연결해, 기사를 `ai_related`와 `not_ai` 두 범주로 나눈다.
- 기사별로 어느 출력으로 갔는지 적고, 출력의 아이템 수를 더해 입력 아이템 수와 비교한다.
- 다음 애매한 기사를 목록 끝에 더해 실행하고, 어느 출력으로 가는지 확인한다.

    ```json
    { "id": "N-009", "title": "오늘의 주요 소식 모음", "summary": "", "category": "", "published_at": "2026-09-16T07:00:00+09:00", "source": "가상종합일보" }
    ```

- 같은 입력으로 한 번 더 실행해 기사마다 같은 범주로 갔는지 비교하고, 실행 기록에서 모델 호출 수와 토큰을 확인한다.
- 워크플로우를 `04_뉴스관련성판단.json`으로 내보낸다.

**주의할 점**

- OpenAI 키는 자격 증명에만 넣는다. 노드의 칸, 지시문, `.env`, 공유 문서에는 적지 않는다. 내보낸 파일에 키가 없는지 확인한다.
- 모델 노드만 다시 실행할 수 있도록 기사를 나눈 출력에 데이터 고정을 걸어 둔다. 기사를 더할 때는 목록의 데이터 고정을 푼다.
- Input Prompt에는 제목과 요약을 함께 넣는다. 범주의 Description에는 사람이 읽어도 경계가 분명한 기준을 직접 적는다.
- When No Clear Match는 처음에는 기본값으로 두고, 애매한 기사를 더한 뒤 Output on Extra 'Other' Branch로 바꾸어 결과를 비교한다. 출력의 아이템 수 합이 입력 수와 같은지 반드시 센다.
- 3장 키워드 필터가 잘못 통과시킨 기사가 이번에는 어떻게 분류되는지 확인한다.
- 모델은 아이템마다 한 번씩 불린다. 기사가 900건이면 호출 수와 비용이 어떻게 되는지 계산해 본다.

## 6. 이어서 더 해 볼 만한 주제

**저장한 요리 메모 나누기.** 메모 20개를 직접 만들어 한식, 양식, 간식으로 나누고, 어디에도 맞지 않는 메모는 'Other' 출력으로 모은다. 범주의 Description을 짧게 쓸 때와 예시까지 쓸 때 결과가 얼마나 달라지는지 비교한다. 분류 결과가 흔들리는 메모가 어떤 메모인지 찾아 본다.

**설문 자유 응답을 칭찬, 불만, 제안으로 나누기.** 칭찬과 불만이 섞인 응답을 일부러 넣은 샘플을 만든다. 분류 결과를 범주별 개수로 모아 한 건의 보고로 만들고, 분류하지 못한 응답의 수를 보고에 함께 적는다. 숫자만 보고 판단했을 때 놓치는 것이 무엇인지 적어 본다.

**규칙을 먼저 쓰고 남은 것만 모델에게 보내기.** 3-2의 키워드 필터로 확실히 무관한 기사를 먼저 거르고 남은 기사만 모델에게 보낸다. 모델 호출 수가 얼마나 주는지, 그 대신 놓치는 기사가 생기는지 비교한다. 이 방법은 9장에서 본격적으로 다룬다.

# 4-3 - 식단 사진 기록과 하루 리포트

## 1. 실습 주제 및 상황

1장 실습 1-2에서 식단 기록을 기록 흐름과 리포트 흐름으로 나누었다. 이번에는 그 두 흐름을 워크플로우 두 개로 만든다. 텔레그램 봇에 음식 사진을 보내면 모델이 사진 속 음식과 분량, 칼로리와 영양 성분을 추정하고, 음식 하나를 한 행으로 Google Sheets에 기록한 뒤 합계를 답장한다. 매일 21시에 도는 리포트 워크플로우는 그날의 기록과 프로필을 읽어 전용 노드(Filter, Edit Fields, Summarize)로 합계를 낸 뒤, 모델에게는 그 숫자와 목표로 쓰는 조언 문장만 받아 Gmail로 보낸다. 두 워크플로우는 스프레드시트 하나로만 이어진다.

## 2. 이 실습의 목적

- 메신저로 받은 사진(바이너리)을 모델에 넘기고, 결과를 JSON Schema로 정한 형식으로 받는다.
- 모델의 결과 하나를 음식별 행 여러 개로 펼쳐 기록하고, 여러 아이템을 다시 메시지 하나로 모은다.
- 여러 행의 합계를 Code 없이 전용 노드로 낸다. 숫자로 바꾸는 단계가 왜 필요한지 확인한다.
- 계산은 규칙(노드)이 하고 문장만 모델이 쓰게 나눈다. 모델에게 숫자를 새로 계산하지 말라고 지시하는 이유를 확인한다.
- 이벤트로 시작하는 워크플로우와 시각으로 시작하는 워크플로우를 나누고, 둘 사이의 약속이 시트의 열 이름이라는 것을 확인한다.

관련 이론: [4.3 정해진 자리에서 모델 호출하기](../../../04_API와도구를연결한단일에이전트.md#43-정해진-자리에서-모델-호출하기)

## 5. 해야 할 것

**해야 할 작업**

- 설정 파일 0절대로 스프레드시트 `식단`과 시트 `식단기록`, `프로필`을 만들고, 텔레그램 봇과 자격 증명 네 개(Telegram, OpenAI, Google Sheets, Gmail)를 준비한다. 봇에게 `/start`를 보낸다.
- 새 워크플로우 `01_칼로리기록_사진분석`을 만들고 `Telegram Trigger`부터 넣는다. 봇에게 사진 한 장을 보내 출력의 Binary 탭에 `data`가 있는지 확인한다.
- 설정 파일 1절대로 나머지 노드를 넣고 연결한다. 시험할 때는 워크플로우를 저장한 뒤 Active를 켜고 텔레그램으로 보낸다.
- 4절의 표에 있는 네 가지를 차례로 보내고, 실행 기록에서 지나간 경로와 시트의 행, 받은 답장을 표에 적는다.
- 실행 기록에서 `음식 분석`의 출력(아이템 1개)과 `행 만들기`의 출력(음식 수만큼의 아이템)을 비교하고, `회신 메시지 작성`이 그것을 다시 하나로 모으는 것을 확인한다.
- 새 워크플로우 `02_일일리포트_건강조언`을 만든다. 노드는 `매일 21시` → `프로필 읽기` → `오늘 기록 읽기` → `빈 행 거르기`(Filter) → `값 정리`(Edit Fields) → `오늘 합계`(Summarize) → `집계 결과`(Edit Fields) → `건강 조언 생성` → `리포트 메일 발송`(Gmail) 순서로 잇는다.
    - `값 정리`: 영양 성분 다섯 개를 숫자로 바꾸고(값이 없으면 0), 시각·끼니·음식 이름·분량·칼로리를 한 줄로 이은 `line` 필드를 만든다.
    - `오늘 합계`: `food_name`은 개수를, 영양 성분 다섯 개는 합계를, `line`은 줄바꿈으로 이어 붙인다.
    - `집계 결과`: `date`, `profile`(프로필 읽기의 첫 행), `totals`(합계 다섯 개), `food_list`(이어 붙인 음식 목록)를 만든다.
    - `리포트 메일 발송`: 받는 사람은 본인 메일 주소, 제목은 `[{{ $('집계 결과').item.json.date }}] 식단 분석리포트`, 본문은 `건강 조언 생성`의 `text`다.
- 21시까지 기다리지 않고 Execute workflow로 실행해 메일이 오는지 확인한다.
- `값 정리`, `오늘 합계`, `집계 결과`의 출력을 차례로 열어 아이템 수가 어떻게 바뀌는지(행 수 → 1개) 적는다.
- `식단기록` 시트에서 오늘 날짜의 `date`를 잠시 다른 날짜로 바꾸고 다시 실행해 어떤 메일이 오는지 확인한 뒤 되돌린다.
- 조언 메일의 숫자를 `집계 결과`의 출력과 맞춰 보고, 집계에 없는 숫자가 들어 있으면 메모한다.
- 두 워크플로우를 `04_칼로리기록_사진분석.json`, `04_일일리포트_건강조언.json`으로 내보낸다.

**주의할 점**

- Telegram Trigger는 공개 주소가 있어야 동작한다. ngrok 터널을 켜고, 시험이 끝나면 워크플로우의 Active를 끄고 터널을 닫는다. 터널 주소가 바뀌면 워크플로우를 껐다가 다시 켜야 텔레그램에 새 주소가 등록된다.
- `Telegram Trigger`의 Download Images/Files를 켜야 사진이 `data`라는 바이너리로 붙는다. `음식 분석`의 Image Data Field Name과 이 이름이 같아야 한다.
- `사진인가?`와 `음식 있음?`의 false 출력에도 안내 노드를 연결한다. 연결하지 않으면 사용자는 아무 답장도 받지 못해 봇이 멈춘 것으로 생각한다.
- `음식 분석`의 지시문은 모르는 값을 0으로 채우지 말고 추정값을 적되, 확신이 낮으면 `confidence`를 `낮음`으로 표시하게 한다. 답장에서 `[추정 불확실]`이 붙은 항목이 어떤 음식인지 확인한다.
- 날짜와 시각은 `$now.setZone('Asia/Seoul')`로 만든다. 서버 시간대가 UTC이면 밤늦게 기록한 식사가 다른 날짜로 저장될 수 있다.
- `오늘 기록 읽기`는 Return only First Matching Row를 켜지 않는다. 켜면 첫 행만 읽혀 합계가 첫 음식의 칼로리가 된다. 한 번 켜서 결과를 비교한 뒤 끈다.
- `오늘 기록 읽기`와 `빈 행 거르기`는 Always Output Data를 켠다. 끄고 기록이 없는 날짜로 실행해 보면 뒤 노드가 실행되지 않아 메일이 오지 않는 것을 볼 수 있다.
- `값 정리`에서 영양 성분을 숫자로 바꾼다. Summarize의 Sum은 숫자 타입인 값만 더하므로, 시트가 숫자를 문자열로 돌려주면 그 값이 합계에서 빠진다.
- 기록이 없는 날에는 합계가 0인 채로 모델이 조언을 쓰고 메일이 간다. 이런 날 메일을 보내지 않거나 다른 안내를 보내려면 `집계 결과` 뒤에 If 노드를 둔다.
- 사진 한 장마다 모델을 한 번 부르고, 사진은 글보다 토큰을 많이 쓴다. `행 만들기`나 `회신 메시지 작성`을 고칠 때는 `음식 분석`의 출력에 데이터 고정을 걸고 다시 실행한다.
- 이 장의 다른 실습은 조회만 하지만, 이 실습은 본인의 스프레드시트에 쓰고 본인에게만 답장과 메일을 보낸다. 본인만 보는 기록이고 틀리면 본인이 고칠 수 있어서 1장에서 승인 단계를 두지 않기로 했다.

## 6. 이어서 더 해 볼 만한 주제

**캡션의 분량 반영하기.** 캡션에 "밥 반 공기만 먹음"처럼 분량을 적어 보내고, 기록된 `amount`와 칼로리가 달라지는지 확인한다. 지시문의 어느 줄이 캡션을 쓰게 하는지 찾고, 분량을 더 잘 반영하도록 규칙을 한 줄 더한다.

**같은 사진이 두 번 기록되는 경우 찾기.** 같은 사진을 두 번 보내고 리포트의 합계가 어떻게 되는지 본다. `chat_id`와 `message_id`가 같은 행이 이미 있으면 기록하지 않는 단계를 `행 만들기` 앞에 넣는다. 실행을 다시 할 때 중복을 막는 방법은 8장에서 다룬다.

**주간 리포트.** 7일 동안의 기록으로 하루 평균과 목표를 넘긴 날의 수를 내는 리포트를 만든다. Google Sheets의 필터는 같은 값만 찾으므로 기록을 모두 읽은 뒤 Code 노드에서 날짜 범위로 거른다.

# 4-4 - 해외 출장 준비 도우미 에이전트

## 1. 실습 주제 및 상황

해외 출장을 앞둔 직원이 채팅으로 날씨와 환율을 묻는다. 질문마다 필요한 정보가 다르다. 실습 4-1에서는 설계자가 정해진 단계로 날씨 API를 불렀다면, 이번에는 같은 API를 에이전트의 도구로 주어 모델이 언제 부를지 정하게 한다. 공개 API는 계정이 필요 없으며, 모델은 질문 하나에 여러 번 불린다.

## 2. 이 실습의 목적

- 질문이 달라지면 에이전트가 부르는 도구와 순서가 달라지는 것을 확인한다.
- 도구 설명이 모델의 선택을 좌우한다는 것을 결과로 확인한다.
- 실행 기록의 로그 화면에서 호출 순서, 입력, 모델 호출 수를 읽는다.

관련 이론: [4.4 에이전트: 도구를 고르며 반복하는 호출](../../../04_API와도구를연결한단일에이전트.md#44-에이전트-도구를-고르며-반복하는-호출)

## 3. 관련 파일

- [`configs/출장도우미_노드설정.md`](configs/출장도우미_노드설정.md): 출장 준비 도우미의 완성 설정과 시험 질문

## 4. 결과물

- `04_출장준비도우미.json`: 내보낸 워크플로우. 도구 설명과 반복 한도를 원래대로 되돌린 상태여야 한다.
- 질문별 도구 호출 기록(아래 표), 도구 설명을 줄였을 때와 반복 한도를 낮췄을 때의 결과 메모
- 답에 나온 숫자가 모두 로그의 도구 결과에 있는 값이다.

## 5. 해야 할 것

**해야 할 작업**

- 새 워크플로우 `출장 준비 도우미`에서 설정 파일의 1~3절대로 `Chat Trigger`, `AI Agent`, `OpenAI Chat Model`을 연결하고 시스템 메시지를 넣는다.
- 설정 파일의 4절대로 도구 세 개(`city_lookup`, `weather_forecast`, `exchange_rate`)를 붙인다.
- 설정 파일 5절의 질문 여섯 개를 하나씩 보내고, 실행 기록의 로그 화면을 보며 다음 표를 채운다.

    | 질문 | 예상 호출 | 실제 호출(도구와 입력) | 모델 호출 수 | 답이 도구 결과와 맞는가 |
    |---|---|---|---|---|
    | Q1 ~ Q6 |  |  |  |  |

- 도구 설명을 줄였을 때와 반복 한도를 낮췄을 때 결과가 어떻게 달라지는지 시험하고 메모한다.
- 앞 질문에 이어서 묻는 질문(예: 오사카에 관한 질문 직후 "거기 다음 주 날씨는?")을 보내 어떻게 답하는지 확인한다.
- 워크플로우를 `04_출장준비도우미.json`으로 내보내고 호출 기록을 함께 저장한다.

**주의할 점**

- 시스템 메시지는 Expression으로 바꾼 뒤 붙여 넣는다. 모델에게 왜 오늘 날짜를 알려 주어야 하는지 생각해 본다.
- 도구의 칸마다 `$fromAI()`로 모델이 채우는 칸과 고정값인 칸이 있다. 왜 그렇게 나누었는지 확인한다.
- 세 도구 모두 Never Error를 켠다. 외부망이 막혀 있으면 설정 파일의 안내대로 주소를 바꾼다.
- 호출 순서가 예상과 달라도 곧바로 틀린 것은 아니다. 최종 답이 도구 결과와 맞는지를 기준으로 판단하고, 날짜가 나오는 답은 달력으로 확인한다.
- 도구 설명은 `exchange_rate`의 Description을 `환율`로만 줄여 시험하고, 반복 한도는 Max Iterations를 `1`로 낮춰 도구를 두 번 거쳐야 하는 질문으로 시험한다. 시험이 끝나면 둘 다 원래대로 되돌린다.
- 이어서 묻는 질문에 왜 그렇게 답하는지 설명해 본다. 대화를 기억하게 하는 방법은 5장에서 다룬다.

## 6. 이어서 더 해 볼 만한 주제

**주말 나들이 도우미.** 목적지를 말하면 날씨와 일몰 시각을 알려 주는 에이전트를 만든다. 예보 도구의 `daily`에 일몰 시각 변수를 더하고, 도구 설명에 결과의 모양을 고쳐 적는다. "저녁까지 놀 수 있어?"처럼 값을 바로 묻지 않는 질문에서 모델이 도구 결과를 어떻게 쓰는지 확인한다.

**거래처 미팅 준비 도우미와 환산 도구.** 현지 날씨와 환율을 함께 알려 주되, 금액 환산이 필요하면 모델이 곱셈을 하지 않도록 환율 조회와 계산을 함께 하는 서브워크플로우 도구를 만든다(실습 4-5의 방법). 모델이 직접 계산한 값과 도구가 계산한 값을 여러 금액으로 비교한다. 입력에 통화 코드가 틀렸을 때 결과가 어떻게 돌아오는지도 시험한다.

**도구 수를 늘렸을 때의 변화 재기.** 시차, 공휴일 같은 도구를 하나씩 더하면서 같은 질문의 모델 호출 수, 토큰, 답의 정확성을 표로 적는다. 도구가 늘어날 때 시스템 메시지와 도구 설명을 어떻게 고쳐야 선택이 흔들리지 않는지 정리한다.

## 5. 해야 할 것

**해야 할 작업**

- 공통사항의 "실행 환경 바꾸기"를 마쳤는지 확인한다. 세 서비스가 실행 중이고 모의 API의 `/health`가 응답해야 한다.
- `모의API_명세.md`의 1~4절을 `API명세_읽기순서.md`의 순서로 읽고, 응답 필드를 2장 요청 기록 계약의 `order` 필드와 대조한다.
- "사내 주문 시스템에서 주문 정보를 가져온다"는 요구에 맞는 연동 방식을 찾는다. 판단은 [이론의 외부 서비스 연동 방식을 선택](../../../04_API와도구를연결한단일에이전트.md#외부-서비스-연동-방식을-선택)를 따른다.
- Header Auth 유형으로 자격 증명 `하루마켓 주문 API`와 시험용 `주문 API 잘못된 키`를 만든다.
- 정상, 미존재, 인증 실패 응답을 직접 받아 보고, 오류 응답을 멈춤이 아니라 데이터로 받는 설정과 비교한다.
- [이론 4.5절](../../../04_API와도구를연결한단일에이전트.md#45-도구를-계약으로-만들기)을 참고해 `04_도구계약_주문조회.md`에 도구 계약(`templates/도구계약_양식.md` 활용)을 쓴다.
- `configs/주문조회도구_노드설정.md`를 따라 서브워크플로우 `주문 조회`와, 그것을 시험하는 `주문 조회 시험`을 만든다.
- 도구만 따로 시험해 다음 표를 채우고, 결과를 도구 계약 문서의 5절에 옮겨 적는다.

    | 사례 | 입력 | `status` | `answer`의 요점 | `evidence.http_status` |
    |---|---|---|---|---|
    |  |  |  |  |  |

- 두 워크플로우를 내보낸다.

**주의할 점**

- 3장에서 `.env`에 넣은 비밀번호와 암호화 키는 바꾸지 않는다. 다시 실행한 뒤 세 서비스가 실행 중이고 3장의 워크플로우와 자격 증명이 남아 있는지 확인한다.
- 모의 API를 터미널에서 부를 때와 n8n에서 부를 때 주소가 다르다(`localhost:8000`과 `mock-api:8000`). 왜 다른지 생각해 본다. PowerShell에서는 `curl` 대신 `curl.exe`를 쓴다.
- 인증 정보는 자격 증명에만 넣는다. 헤더 칸에 키를 직접 적은 워크플로우를 내보내면 파일에 그 값이 그대로 남는다. 이를 확인하는 시험용 워크플로우는 확인 뒤 지운다.
- 명세의 "이 API가 하지 않는 일"과 404 응답의 뜻을 확인한다. 이 API가 하지 않는 일은 도구가 맡아야 한다.
- 도구 계약을 쓸 때 입력 값마다 누가 채워야 하는지 정한다. 모델이 채우면 위험한 값이 있는지 살핀다.
- `주문 API 호출` 노드의 On Error는 Continue (using error output)로 두어 연결 자체가 실패해도 결과를 돌려주게 한다.
- 서브워크플로우는 마지막 노드의 출력을 돌려준다. 결과를 만드는 노드 뒤에 다른 노드를 붙이지 않는다.
- 인증 실패는 자격 증명을 잠시 바꾸어 시험하고, 시험이 끝나면 되돌린다.
- 내보낸 파일에서 모의 API 키를 검색해 들어 있지 않은지 확인한다. 모의 API만 다시 시작할 때는 `docker compose restart mock-api`를 쓴다.

## 6. 이어서 더 해 볼 만한 주제

**응답에서 도구가 돌려줄 값 줄이기 연습.** 지금 도구는 고객 안내에 필요한 값만 돌려준다. 명세의 응답 필드마다 '안내에 필요함', '내부 판단에만 필요함', '내보내면 안 됨'으로 표를 만들고, 그 표로 `answer`에 넣을 필드를 다시 판단한다. 필드 하나를 더 넣으려면 계약의 무엇을 함께 고쳐야 하는지도 적는다.

**내 업무의 조회 도구 계약 쓰기.** 사내 재고, 일정, 고객 시스템처럼 평소 조회하는 시스템을 하나 고른다. API가 없다면 내보낸 CSV를 대신 쓰는 것으로 가정한다. 입력, 누가 입력을 채우는가, 결과의 `status` 목록, 권한이 없을 때의 결과를 양식에 적고, 작은 샘플로 서브워크플로우를 만들어 시험한다.

**입력 형식을 호출 전에 검사하기.** 지금은 형식이 틀린 주문번호도 API를 호출한 뒤 결과로 돌려준다. 호출 전에 형식을 검사해 API를 부르지 않고 돌려주도록 고친다. 새 `status` 값을 만들 것인지 판단하고, 호출 횟수와 결과가 어떻게 달라지는지 비교한다.

# 4-6 - 배송 문의 분류와 배송 안내 에이전트

## 1. 실습 주제 및 상황

3장에서 만든 `웹 문의 정규화`는 웹 문의 양식으로 들어온 요청을 문의 기록으로 정리하고, 문장에 든 낱말로 요청 유형을 나눈 뒤 경로마다 끝을 비워 둔 채 멈춘다. 이 방식에는 두 가지 한계가 있었다. 첫째, 낱말 규칙은 문장의 뜻을 읽지 못한다. 교환과 환불을 함께 말한 W-6은 먼저 걸린 낱말 때문에 한 유형으로 잘못 갔다. 둘째, 경로 끝에서 고객에게 무엇을 답할지 정해 두지 않았다.

이 실습에서는 하루마켓의 배송 문의를 끝까지 처리한다. 3장에서 만든 `웹 문의 정규화`를 복제해 이름을 `웹 문의 처리`로 바꾸고, 3장의 낱말 규칙 Switch와 그 뒤의 빈 경로 끝 노드를 지운다. 그다음 `웹 문의 처리`에 다음 네 가지를 차례로 만든다.

| 단계 | 하는 일 | 판단하는 주체 |
|---|---|---|
| 1. 문의 분류 | 모델이 문장을 읽어 요청 유형과 분쟁·반복 표시를 정해진 스키마대로 뽑는다. 뽑은 값이 허용 값인지는 규칙이 다시 검사하고, 경로는 규칙(Switch)이 나눈다. | 모델(추출), 규칙(검사·경로) |
| 2. 경로 고르기 | 배송 문의의 문장에서 주문번호를 모두 찾아 센다. 하나면 기본 경로로, 둘 이상이면 에이전트 경로로 보낸다. | 규칙 |
| 3. 기본 경로 | `주문 조회`를 한 번 부르고, 배송 상태에 맞는 안내문 틀로 답한다. 지연 조사 대상이나 조회 실패는 사람에게 넘긴다. | 규칙 |
| 4. 에이전트 경로 | 서브워크플로우 `배송 안내 에이전트`가 문장의 주문마다 `주문 조회` 도구를 골라 부르고, 결과를 묶어 한 번에 안내한다. 결과는 검증 규칙을 통과해야 고객 답이 된다. | 에이전트(도구 선택·안내문), 규칙(검증) |

에이전트 경로를 따로 두는 이유는 조회 횟수가 문의마다 다르기 때문이다. "O-2005랑 O-2006 둘 다 언제 출고되나요?"처럼 주문이 둘 이상이면 몇 번 조회할지, 결과를 어떻게 묶을지를 미리 정한 틀로 처리하기 어렵다. 반대로 주문이 하나인 문의는 조회 한 번과 정해진 문구로 충분하므로 모델을 쓰지 않는다. 실습 마지막에는 같은 문의를 두 경로로 처리해 모델 호출 수와 걸린 시간을 비교하고, 이 판단이 맞았는지 숫자로 확인한다.

에이전트에게 맡기는 범위는 좁게 둔다. 고객 이름은 워크플로우가 채우고, 모델은 주문번호만 채운다. 이름까지 모델이 채우면 문장에 적힌 다른 사람의 이름으로 조회해 남의 주문 정보를 알려 줄 수 있기 때문이다. 에이전트의 결과는 `status`, `answer`, `evidence`의 결과 계약을 따라야 하며, 검증 규칙이 조회에 실패한 주문을 안내했는지 같은 위반을 걸러 낸다. 마지막으로 계약 테스트 사례를 세 번 실행해, 안내 문장이 회차마다 달라도 결과의 상태와 판정이 같은지 확인한다.

요청은 [`배송문의_요청샘플.json`](data/배송문의_요청샘플.json)의 D-1~D-7을 보낸다. 주문 하나인 배송 중 문의(D-1), 지연 조사 대상(D-2), 같은 고객의 주문 두 개(D-3), 다른 고객의 주문번호가 섞인 문의(D-4), 없는 주문번호가 섞인 문의(D-5), 형식이 다른 번호가 섞인 문의(D-6) 등이 들어 있고, 각 사례가 어느 경로에서 어떤 `status`로 끝나야 하는지 함께 적혀 있다.

실습 4-5의 `주문 조회`(조회 도구), 실습 4-2의 `OpenAI 실습`(모델 자격 증명), 3장의 `웹 문의 정규화`(문의 기록)를 이어받는다. 이 장에서는 고객에게 줄 답을 만드는 데까지 하며, 안내문을 실제로 보내거나 처리 기록을 저장하지는 않는다. 배송이 아닌 유형의 경로 끝은 그대로 비워 두고, 교환 문의는 실습 4-7에서 채운다.

## 2. 이 실습의 목적

- 분류를 모델에게 맡기되 결과를 규칙으로 검사하고, 경로는 규칙이 정하게 만드는 방법을 익힌다.
- 고객 이름처럼 결과를 볼 수 있는 사람을 바꾸는 값을 모델이 채우지 못하게 한다.
- 결과 계약과 검증 규칙, 계약 테스트로 에이전트의 결과를 확인한다.
- 같은 문의를 두 경로로 처리해 호출 수와 시간을 숫자로 비교한다.

## 5. 해야 할 것

**해야 할 작업**

- `웹 문의 정규화`를 복제해 `웹 문의 처리`를 만들고, 3장의 키워드 분기를 모델 분류와 규칙 검사로 바꾼다. 설정은 `배송안내_노드설정.md`의 1-1~1-4를 따른다.
- 문의에 적힌 주문번호를 세어, 주문이 하나면 기본 경로로, 둘 이상이면 에이전트 경로로 보낸다(설정 1-5, 1-6).
- 조회 한 번과 안내문 틀로 답하는 기본 경로를 만든다(설정 1-7~1-10).
- 서브워크플로우 `배송 안내 에이전트`를 만들고(설정 2절), 에이전트 경로에 연결한다(설정 1-11).
- 주문이 둘인 샘플(D-3)을 보내고 실행 기록을 읽어 다음 표를 채운다.

- 에이전트 결과를 검증하는 규칙과 결과 노드를 만든다(설정 2-6~2-8).
- `계약 테스트 실행`을 만들어(설정 3절) 같은 테스트를 세 번 실행하고, `04_계약테스트_배송안내.md`에 양식대로 결과를 적는다. 인증 실패 사례도 테스트 케이스에 넣는다. 도구 오류 전달도 시험한다.

**주의할 점**

- 모델의 추출 결과가 출력의 어느 필드 아래에 있는지 먼저 확인하고 표현식을 적는다. 3장에서 틀린 경로로 갔던 W-6을 다시 보내 결과를 비교한다.
- 스키마에 허용 값을 적어도 모델이 그 밖의 값을 낼 수 있다. 분류 결과는 규칙으로 한 번 더 검사한다.
- 경로를 나누는 일은 모델이 아니라 규칙이 정한다. 규칙으로 가려내지 못하는 문의가 어떤 것인지 생각해 본다.
- 기본 경로에서 배송 상태를 나누는 규칙의 순서가 결과를 바꾼다.
- 에이전트에게 주는 입력은 최소한으로 한다. 고객 이름처럼 결과를 볼 수 있는 사람을 바꾸는 값은 모델이 아니라 워크플로우가 채운다. 결과 형식을 강제하고, 반복 한도와 실패 처리를 둔다.
- 검증 규칙이 제대로 걸러 내는지 일부러 시험한다. 에이전트 출력에 데이터 고정을 걸고 조회에 실패한 주문을 안내한 것처럼 고쳐 실행해 본다. 끝나면 데이터 고정을 모두 푼다.
- 계약 테스트에서는 안내문 표현이 회차마다 달라도 판정에 영향이 없어야 한다.
- 인증 실패 시험에서는 에이전트가 답을 지어내지 않는지 확인한다. 도구 오류 전달은 `주문 API 호출`의 Never Error를 잠시 꺼서 시험한다.
- 시험으로 바꾼 자격 증명과 Never Error 설정은 끝나면 원래대로 되돌린다.

## 6. 이어서 더 해 볼 만한 주제

"**다른 주문도**"**를 가려내기.** 번호 없이 "다른 주문도 확인해 주세요"라고 적은 문의는 지금 규칙으로 가려지지 않는다. 분류 단계에서 '여러 주문을 언급했는가'를 함께 뽑도록 스키마를 고치고, 그런 문의를 어디로 보낼지 정한다. 샘플을 다섯 건 만들어 규칙 방식과 추출 방식의 결과를 비교한다.

**배송 지연 사과 문구의 틀과 에이전트 비교.** 지연 안내를 안내문 틀로 만든 경우와 모델이 쓰게 한 경우를 같은 사례로 비교한다. 정책에 없는 약속이 들어가는지, 날짜가 도구 결과와 맞는지를 검증 규칙으로 옮겨 본다. 어떤 문구는 모델에게 맡기지 않는 편이 나은지 판단 근거를 적는다.

**내 업무 문의에 기본 경로와 에이전트 경로 나누기.** 팀에 자주 오는 문의를 스무 건 적고, 한 번의 조회와 정해진 문구로 끝나는 것과 여러 정보를 살펴야 하는 것으로 나눈다. 각 경로의 비율을 추정하고, 에이전트 경로에 필요한 도구와 결과 계약을 설계서로 적어 본다.

# 4-7 - 교환 가능 여부 조회와 교환 안내 에이전트

## 1. 실습 주제 및 상황

하루마켓 고객지원 메일함으로 들어온 교환 문의에 실습 4-5와 4-6의 구조를 적용한다. 모의 주문 API의 교환 가능 여부 조회 기능을 도구로 만들고, 메일 문의 처리 워크플로우에 기본 경로와 교환 안내 에이전트 경로를 붙인다. 메일 문의에는 원하는 옵션이 고객의 표현으로 적혀 있어 옵션 이름과 다를 수 있다.

## 2. 이 실습의 목적

- 도구 계약, 서브워크플로우, 분류와 규칙 검사, 결과 검증, 계약 테스트의 전 과정을 스스로 적용한다.
- 모델이 채워도 되는 입력과 워크플로우가 정해야 하는 입력을 구분한다.
- 교환에 맞는 검증 규칙을 스스로 정한다.

## 5. 해야 할 것

도구 만들기는 실습 4-5의 명세 읽기, 연동 방식 탐색, 도구 계약, 서브워크플로우, 도구 시험을, 분류와 경로, 결과 검증, 계약 테스트는 실습 4-6의 작업을 참고한다. 해당 실습의 설정 파일을 복제해 쓰지 말고 필요한 부분을 읽어 직접 만든다.

다음은 4-5, 4-6과 다르거나 반드시 지켜야 할 사항이다.

1. **도구** `교환 가능 여부 조회`**:** 입력은 `order_id`, `customer_name`, `option`이다. 자격 증명은 `하루마켓 주문 API`를 그대로 쓰고, 이름 확인과 오류 변환은 `주문 조회`와 같게 한다.
2. **메일 문의 분류:** 3장 `메일 문의 정규화`를 복제해 `메일 문의 처리`로 만들고 키워드 분기를 `Information Extractor`와 규칙 검사로 바꾼다. 실습 4-6의 분류 항목에 다음 두 가지를 더 뽑는다.
    - `desired_option`: 고객이 적은 표현을 고치지 않고 그대로 옮긴다. 옵션 이름으로 해석하는 일은 옵션 목록을 볼 수 있는 쪽이 맡는다.
    - 주문번호가 둘 이상일 때의 처리 대상 주문: 모델이 고른 번호는 제목과 본문에서 정규식으로 찾은 후보 안에 있을 때만 쓰고, 아니면 사람에게 넘긴다.
3. **기본 경로:** `exchange_option` 문의는 추출한 옵션으로 한 번 조회한다. 교환 가능, 기한 초과, 재고 없음이면 안내문 틀로 답한다. 재고가 없으면 재고가 있는 옵션을 알려 주되 대신 골라 주지 않는다. `exchange_other_product` 문의는 조회하지 않고 반품 후 새로 주문하라고 안내한다.
4. **에이전트 경로:** 원하는 옵션을 추출하지 못했거나 추출한 표현으로 조회한 결과가 "제공하지 않는 옵션"이면 `교환 안내 에이전트`에게 넘긴다. 에이전트는 옵션 목록을 보고 고객 표현을 옵션 이름으로 해석해 다시 조회하고, 하나로 정할 수 없으면 원하는 옵션을 묻는다.
5. **검증 규칙:** 교환에 맞는 규칙을 하나 이상 스스로 더한다.

지켜야 할 조건은 다음과 같다.

- `order_id`와 `customer_name`은 워크플로우가 정한다. 에이전트의 도구에서 모델이 채우는 입력은 `option` 하나뿐이다.
- 에이전트는 문의 한 건씩 실행한다.
- 안내문에 교환을 진행했다고 쓰지 않는다. 실제 교환은 담당자 승인 뒤에 진행하며, 이 절차는 6장에서 만든다.
- 날짜와 기한은 모의 API가 계산한 값만 쓴다.
- 이 장에서 교환 문의의 요청 기록을 만들거나 저장하지 않는다.

## 6. 이어서 더 해 볼 만한 주제

**도구에 입력 검증과 오류 응답 변환 더하기.** 지금은 400 응답이 `lookup_error`가 된다. 호출 전에 `option`이 비었는지 검사해 API를 부르지 않고 알려 주고, 400 응답의 오류 코드를 에이전트가 다음 행동을 정할 수 있는 결과로 바꾼다. 같은 계약 테스트 사례를 전후로 실행해 도구 호출 수, `handoff` 비율, 모델이 옵션을 짐작한 횟수, 토큰을 표로 비교한다. 결과 계약에 새 `status` 값이 생기면 검증 규칙도 함께 고친다.

**옵션 표현 해석을 규칙으로 얼마나 줄일 수 있는지 보기.** "한 치수 큰 걸로", "검정색으로" 같은 표현을 옵션 이름과 짝지은 표를 만들어 에이전트 앞에 둔다. 표로 해결되는 비율과 여전히 에이전트가 필요한 표현을 세어 보고, 호출 수가 얼마나 주는지 비교한다. 표를 관리하는 비용도 함께 판단한다.

**메일 스레드를 입력으로 바꾸어 보기.** 답장이 이어진 메일은 앞선 대화가 인용문으로 함께 들어온다. 인용문이 포함된 샘플을 만들어 추출 결과가 어떻게 달라지는지 시험하고, 인용문을 먼저 지우는 규칙을 더해 비교한다. 이전 메일의 주문번호를 잘못 고르는 경우가 있는지 확인한다.

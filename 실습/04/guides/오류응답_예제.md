# 오류 응답 예제

> 상태 코드별로 흔히 만나는 응답과 다음에 할 일을 정리했다. 4장 실습 4-1, 4-5, 4-7에서 참고한다.
> 본문 예시는 이 교재에서 실제로 호출해 받은 응답이다. 다른 서비스는 본문의 모양이 다르므로 그 서비스의 명세를 확인한다.

## 상태 코드 묶음

| 묶음 | 뜻 | 누가 고치는가 |
|---|---|---|
| **2xx** | 요청이 성공했다 | — |
| **4xx** | 요청하는 쪽에 문제가 있다. 주소, 값, 인증, 권한 중 하나다 | 요청하는 쪽. 같은 요청을 다시 보내도 대개 결과가 같다 |
| **5xx** | 서비스 쪽에 문제가 있다 | 서비스 쪽. 잠시 뒤 다시 시도하면 될 수도 있다(8장) |

## 자주 만나는 상태 코드

| 상태 코드 | 뜻 | 흔한 원인 | 다음에 할 일 | 다루는 장 |
|---|---|---|---|---|
| **400** | 요청이 잘못되었다 | 필수 값 누락, 형식 오류, 파라미터 이름 오타 | 명세의 요청 표와 보낸 값을 대조해 고친다 | 4장 |
| **401** | 인증되지 않았다 | 키 없음, 키 오타, 다른 서비스의 키 | 자격 증명의 키와 헤더 이름을 확인한다. 다시 시도해도 소용없다 | 4장 |
| **403** | 인증은 되었지만 권한이 없다 | 키에 그 작업의 권한이 없음 | 키의 권한 범위를 확인한다 | 4장, 6장 |
| **404** | 찾을 수 없다 | 없는 자원(주문 등), 주소 오타 | 오류 코드로 둘을 구분한다. 없는 자원이면 업무 규칙에 따라 고객 확인이나 담당자에게 넘긴다 | 4장 |
| **422** | 값의 모양은 맞지만 처리할 수 없다 | 지원하지 않는 값(예: 없는 통화 코드) | 허용 값 목록을 확인한다 | 4장 |
| **429** | 요청이 너무 많다 | 호출 한도 초과 | 기다렸다가 다시 시도한다 | 8장 |
| **500, 502, 503** | 서비스 오류 | 서비스 장애 | 제한된 횟수만 다시 시도하고, 계속되면 사람에게 알린다 | 8장 |

## 이 교재에서 받은 오류 응답

### 하루마켓 모의 주문 API

**401: 키가 틀렸을 때**

```json
{
  "error": {
    "code": "INVALID_API_KEY",
    "message": "API 키가 없거나 올바르지 않습니다."
  }
}
```

**404: 없는 주문일 때**

```json
{
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "주문을 찾을 수 없습니다."
  }
}
```

**400: 주문번호 형식이 틀렸을 때**

```json
{
  "error": {
    "code": "INVALID_ORDER_ID",
    "message": "주문번호는 O- 뒤에 숫자 네 자리입니다."
  }
}
```

### Open-Meteo 예보 API

**400: 필수 파라미터가 빠졌을 때**(경도를 빼고 호출한 경우)

```json
{
  "reason": "Parameter 'latitude' and 'longitude' must have the same number of elements",
  "error": true
}
```

### Open-Meteo 지명 검색 API

**200이지만 결과가 없을 때**(없는 지명을 검색한 경우)

```json
{
  "generationtime_ms": 0.10514259
}
```

오류가 아니라 성공 응답이다. 그런데 `results` 필드가 **아예 없다.** 3장에서 본 "필드 자체가 없는 경우"다. 결과가 없을 때 빈 배열이 올 것이라고 짐작하고 `results[0]`을 읽으면 틀린다.

### Frankfurter 환율 API

**422: 없는 통화 코드를 보냈을 때**

```json
{
  "status": 422,
  "message": "invalid currency: ABC"
}
```

서비스마다 오류 본문의 모양이 다르다는 점을 확인한다. 하루마켓은 `error.code`, Open-Meteo는 `reason`, Frankfurter는 `message`에 이유를 적는다.

## n8n에서 오류 응답을 데이터로 받기

`HTTP Request` 노드는 기본 설정에서 4xx, 5xx 응답을 받으면 오류로 멈춘다. 응답 본문과 상태 코드를 다음 노드에서 읽으려면 Options의 Response에서 다음 두 가지를 켠다. 설정 방법은 실습 4-5의 5단계에 있다.

- **Include Response Headers and Status**: 본문과 함께 상태 코드와 헤더를 출력에 담는다.
- **Never Error**: 상태 코드가 2xx가 아니어도 오류로 멈추지 않는다.

서버에 아예 연결하지 못한 경우(주소 오류, 서버 중지)에는 상태 코드가 없으므로 Never Error로 막을 수 없다. 이때는 노드 Settings의 On Error를 쓴다(실습 4-5의 7단계).

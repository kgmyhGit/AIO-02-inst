# API 명세 읽기 순서

> 처음 보는 API 명세를 읽을 때 쓰는 순서와 확인 질문이다. 4장 실습 4-1, 4-5, 4-7에서 쓴다.
> 명세는 그 API를 만든 쪽이 적어 둔 데이터 계약이다. 2장에서 계약을 쓸 때 채운 항목을 이번에는 명세에서 찾아낸다.

## 여섯 단계

| 순서 | 찾을 것 | 설명 | 
|---|---|---|
| 1 | **기본 주소와 인증** | 요청을 어디로 보내는가? 키가 필요한가? 키는 헤더에 넣는가, 주소에 넣는가? | 
| 2 | **필요한 엔드포인트** | 내가 하려는 일(조회, 등록, 변경)에 맞는 요청 경로는 무엇인가? (기본주소 + 요청경로 로 url을 만든다.) 요청 메서드는 무엇인가? |
| 3 | **요청의 값** | 경로에 넣는 값, 쿼리 파라미터, 본문 중 무엇이 필수인가? 형식이 정해진 값은 무엇인가? |
| 4 | **성공 응답의 필드** | 요청결과로 응답시 전달되는 필드들. "내가 쓸 값은 어느 필드에 있는가?", "데이터 타입은 무엇인가?", "값이 없을 때 `null`인가, 필드가 빠지는가?" 등을 확인한다.|
| 5 | **오류 응답** | "오류 코드로 어떤 상태 코드가 오는가?", "오류 본문의 모양은 무엇인가?", "각 오류에 무엇을 해야 하는가?" 등을 확인한다. |
| 6 | **사용 제한과 이용 조건** | "호출 횟수 제한이 있는가?", "상업적 이용이나 출처 표시 조건이 있는가?" 확인한다. | 

## 2장 계약 항목과의 대응

명세를 읽으며 아래 표를 채우면, 이 API를 워크플로우의 한 단계로 쓸 때의 계약이 된다.

| 2장 계약 항목 | API 명세에서 확인할 것 |
|---|---|
| **필드명** | 요청 파라미터 이름, 응답 필드 이름 |
| **데이터 타입** | 각 필드가 문자열, 숫자, 불리언, 배열 중 무엇인지, `null`이 올 수 있는지(필드 표의 타입 칸, 응답 예시) |
| **필수 여부** | 빠뜨리면 안 되는 요청 값이 무엇인지(요청 표의 필수 칸) |
| **형식·허용 값** | 형식 설명, 값 목록(예: `order_status`의 네 값) |
| **값을 만드는 곳** | 누가 만든 값인가. 내가 보내는 값인지 API가 계산해 주는 값인지 |
| **없거나 틀릴 때** | 값이 없거나 틀릴 때 돌아오는 상태 코드와 오류 코드(오류 응답 표) |

## 읽고 나서 할 일

- 읽은 내용을 믿기 전에 **작은 요청 한 번**으로 확인한다. 정상 한 번, 일부러 틀린 요청 한 번이면 충분하다.
- 명세와 실제 응답이 다르면 실제 응답을 기록하고, 무엇이 달랐는지 적어 둔다. 기능 탐색 기록을 쓰고 있다면 "주의할 점"에 적는다.
- 명세에 "이 API가 하지 않는 일"이 적혀 있으면 특히 주의해서 읽는다. 그 일은 호출한 쪽이 해야 한다.

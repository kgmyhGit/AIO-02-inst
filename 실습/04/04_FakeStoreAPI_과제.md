# 4장 과제. Fake Store API로 상품·장바구니 보고 워크플로우 만들기

# 개요

## 1. 이 과제를 통해 배울 것

처음 보는 공개 API의 문서를 스스로 읽고, 어떻게 요청하고 응답이 어떤 모양으로 오는지 분석한 뒤 그 결과로 업무 워크플로우를 만든다. 4장 실습 4-1에서 Open-Meteo 명세를 읽은 순서를 이번에는 안내 없이 적용한다.

- API 문서에서 기본 주소, 요청 경로, 메서드, 인증 필요 여부를 찾고 작은 요청으로 확인한다.
- 응답의 최상위 모양과 중첩된 목록, 식별자와 숫자 필드의 데이터 타입을 읽는다.
- 서로 다른 응답을 식별자로 연결하고, Code 노드 없이 기본 노드로 거르기·나누기·합치기·집계를 한다.
- 조회 결과를 Google Sheets와 Gmail로 보내 사람이 확인할 수 있는 업무 결과물로 만든다.

관련 이론: [4.1 워크플로우 밖의 시스템에 요청하기](../../../04_API와도구를연결한단일에이전트.md#41-워크플로우-밖의-시스템에-요청하기), [4.2 인증과 자격 증명, 연동 방식 고르기](../../../04_API와도구를연결한단일에이전트.md#42-인증과-자격-증명-연동-방식-고르기)

## 2. 과제 목차

| 과제 이름 | 실습으로 익힐 것 | 최종 결과 |
|---|---|---|
| 과제 1 - 상품 현황 저장과 고가 상품 보고 | 명세 읽기, 응답을 시트 행으로 바꾸기, 조건으로 거르기, 여러 아이템을 메일 한 통으로 묶기 | Google Sheets 문서 1개, 관리자 메일 1통 |
| 과제 2 - 고객별 구매예정 금액 보고 | 세 자원(장바구니, 고객, 제품 정보 조회)의 API 요청, 중첩 목록 나누기, 고객별 집계 | 관리자 메일 1통 |

# 과제 1 - 상품 현황 저장과 고가 상품 보고

## 1. 실습 주제 및 상황

온라인 쇼핑몰의 상품 운영 담당자는 매주 전체 상품 목록을 공유 시트에 정리하고, 그중 가격이 높은 상품을 관리자에게 따로 보고한다. 이 일을 자동화 하려고 한다. 수동으로 실행하면 Fake Store API에서 전체 상품을 조회해 Google Sheets에 상품 하나당 한 행으로 저장하고, 가격이 $500 이상인 상품만 골라 관리자 메일로 요약 메일 한 통을 보낸다.

```text
수동 실행 → 실습 설정 → 전체 상품 조회 →  시트 저장 → 고가 상품 조회 → 메일 한 통으로 묶기 → 관리자 메일 발송
```

위 흐름은 단계의 순서만 보인 것이다. 단계마다 어떤 노드를 쓸지는 스스로 정한다.

## 2. 이 실습의 목적

- 공식 문서에서 전체 상품을 조회하는 요청을 찾아 `HTTP Request` 노드에 채운다.
- 응답의 필드를 업무에서 쓰는 열 이름으로 바꾸어 시트에 저장한다.
- 조건에 맞는 아이템만 거르고, 여러 아이템을 메일 한 통의 내용으로 묶는다.

## 3. 관련 파일

- [Fake Store API 문서](https://fakestoreapi.com/docs): 읽을 명세
- [`guides/API명세_읽기순서.md`](guides/API명세_읽기순서.md): 명세를 읽는 순서와 확인 질문
- [`templates/FakeStore_API명세분석_양식.md`](templates/FakeStore_API명세분석_양식.md): 분석 기록 양식

## 4. 결과물

**워크플로우 JSON**

- `04/fakestore/04_상품현황보고.json`: n8n 워크플로우 `과제1 상품 현황 보고`를 내보낸 파일

**Google Sheets 문서**

- Google Drive에 `n8n_과제_이름` 폴더를 만들고, 그 안에 `04_과제1_상품현황_이름` 문서를 만든다. 예를 들어 이름이 홍길동이면 `04_과제1_상품현황_홍길동`이다.
- 시트 탭 이름은 `Products`로 바꾼다.
- `Products` 탭의 1행 A열부터 아래 헤더를 순서대로 적는다. 이 이름은 시트의 열 이름이며 API 응답의 필드 이름과 같지 않을 수 있다. 응답의 어느 필드를 어느 열에 넣을지는 분석 기록을 보고 스스로 정한다.

    | 열 | 헤더 | 저장할 값 |
    |---|---|---|
    | A | `product_id` | 상품의 식별자 |
    | B | `product_name` | 상품명 |
    | C | `price` | 가격(숫자) |
    | D | `category` | 상품 분류 |
    | E | `collected_at` | 조회한 시각(한국 시간, `yyyy-MM-dd HH:mm:ss`) |

- 최종 상태의 시트에는 API가 돌려준 상품이 상품마다 한 행씩 빠짐없이 있고, 같은 `product_id`가 두 번 나오지 않는다.
- 강사 계정에 보기 권한을 준다. 별도 안내가 없으면 링크 공개 범위를 인터넷 전체로 바꾸지 않는다.

**관리자 메일**

- 관리자 mail 주소로 메일 한 통이 간다.
- 본문에 전체 상품 수, 고가 상품 수, 고가 상품마다의 상품 ID·상품명·분류·가격을 포함한다.
- 기준 이상인 상품이 하나도 없으면 메일을 보내지 않는 대신 "해당 없음"이라고 적은 메일을 보낸다.

**분석 기록**

- `04/fakestore/04_FakeStore_API명세분석.md`에 상품 자원의 분석과 과제 1의 결과 검증 기록이 들어 있다.

## 5. 해야 할 것

**해야 할 작업**

- 공식 문서를 읽어 분석 기록의 1)~3)에서 상품에 해당하는 칸을 채운다. 브라우저나 `HTTP Request` 노드로 작은 요청을 한 번 보내 문서의 내용을 확인한다.
- 새 워크플로우 `과제1 상품 현황 보고`를 만들고 `Manual Trigger` 를 트리거 노드로 사용한다.
- `HTTP Request` 노드(`전체 상품 조회`)로 전체 상품을 조회한다. 출력 아이템이 몇 개인지, 아이템 하나가 상품 하나인지 확인한다.
- 응답의 필드를 시트 헤더 다섯 개에 맞춘 아이템으로 바꾼다. 가격은 숫자 타입으로 둔다.
- `Google Sheets` 노드(`상품 시트 저장`)로 `Products` 탭에 저장한다. 같은 워크플로우를 다시 실행해도 행이 늘어나지 않도록 저장 방식(Operation)을 고른다.
- 시트 저장이 끝난 뒤 가격이 기준 이상인 상품만 남기고, 남은 상품을 메일 한 통에 넣을 수 있도록 하나의 아이템으로 묶는다.
- `Gmail` 노드(`관리자 메일 발송`)로 요약 메일을 보낸다. 본문은 표나 줄 단위 목록으로 읽을 수 있게 만든다.
- 분석 기록의 4)에 과제 1의 검증 결과를 채우고, 워크플로우를 `04_상품현황보고.json`으로 내보낸다.

# 과제 2 - 고객별 구매예정 금액 보고

## 1. 실습 주제 및 상황

쇼핑몰 관리자는 고객들이 장바구니에 담아 둔 상품이 모두 결제되면 고객마다 얼마가 될지를 알고 싶다. 수동으로 실행하면 Fake Store API에서 전체 고객, 전체 장바구니, 전체 상품을 조회하고, 장바구니의 상품마다 가격과 수량을 곱해 고객별 구매예정 금액을 계산한다. 결과는 모든 고객을 담은 메일 한 통으로 관리자 Gmail에 보낸다.

```text
수동 실행 →  (전체 고객 조회 / 전체 장바구니 조회 / 전체 상품 조회)
→ 장바구니의 조회 상품들을 한 줄씩 나누기 → 상품정보 조회결과에서 상품 가격 연결 → 줄마다 금액 계산 → 고객별 합계 집계
→ 전체 고객조회 결과 연결해 고객정보 추가 → 메일 한 통으로 묶기 → 관리자 메일 발송
```

위 흐름은 단계의 순서만 보인 것이다. 단계마다 어떤 노드를 쓸지는 스스로 정한다.

## 2. 이 실습의 목적

- 하나의 업무 결과를 만들기 위해 여러 자원을 조회하고, 응답끼리 식별자로 연결한다.
- 응답 안에 중첩된 목록을 아이템으로 나누고, 기준 필드별로 다시 합친다.
- 데이터가 없는 대상(장바구니가 없는 고객)과 연결에 실패한 데이터(가격을 찾지 못한 상품)를 구분해 처리한다.

## 3. 관련 파일

- [Fake Store API 문서](https://fakestoreapi.com/docs): 읽을 명세
- [`guides/API명세_읽기순서.md`](guides/API명세_읽기순서.md): 명세를 읽는 순서와 확인 질문
- [`templates/FakeStore_API명세분석_양식.md`](templates/FakeStore_API명세분석_양식.md): 분석 기록 양식. 과제 1에서 만든 기록에 이어서 쓴다

## 4. 결과물

**워크플로우 JSON**

- `04/fakestore/04_구매예정금액보고.json`: n8n 워크플로우 `과제2 구매예정 금액 보고`를 내보낸 파일


**관리자 메일**

- 관리자 mail 주소로 메일 한 통이 간다.
- 본문에 조회 시각, 전체 고객 수, 조회한 장바구니 수, 전체 고객의 금액 합계, 고객마다의 고객 ID·사용자명·고객명·장바구니 수·장바구니 상품 개수·구매예정 (총)금액가 들어 있다.

**분석 기록**

- `04/fakestore/04_FakeStore_API명세분석.md`에 고객·장바구니 자원의 분석, 자원 사이의 연결 기준, 과제 2의 결과 검증 기록이 들어 있다.

## 5. 해야 할 것

**계산 규칙**

- 고객의 구매예정 금액은 그 고객의 **모든 장바구니**에 담긴 상품마다 "상품 가격 × 수량"을 구해 더한 값이다. 날짜가 오래된 장바구니도 포함하며, 최근 장바구니 하나만 고르지 않는다.
- 장바구니 수는 고객이 가진 장바구니의 개수, 상품 수량 합계는 그 장바구니들에 담긴 수량을 모두 더한 값이다.
- 장바구니에 담긴 상품의 가격을 찾지 못하면 그 상품을 0원으로 계산하지 않고 메일을 보내기 전에 워크플로우를 멈춘다.

**해야 할 작업**

- 공식 문서를 읽어 API 분석 기록에 고객과 장바구니에 해당하는 칸을 채운다.(상품은 첫번째 과제에서 채움) 특히 장바구니 응답의 아이템 하나가 무엇을 나타내는지, 상품 정보가 어떤 모양으로 들어 있는지, 가격이 장바구니 응답 안에 있는지를 확인한다.
- 장바구니와 고객, 장바구니의 상품과 상품 목록을 이어 주는 필드를 찾아 본다. 
- 새 워크플로우 `과제2 구매예정 금액 보고`를 만들고 `Manual Trigger`
- `HTTP Request` 노드 세 개로 전체 고객, 전체 장바구니, 전체 상품을 조회한다. 특정 고객 한 명의 장바구니만 조회하는 요청으로 전체를 대신하지 않는다.
- 장바구니 하나에 상품이 여러 개 들어 있으므로, 상품 한 줄이 아이템 하나가 되도록 나눈다. 나눈 아이템에도 어느 장바구니, 어느 고객의 상품인지가 남아 있어야 한다.
- 나눈 아이템에 상품 가격을 연결하고 줄마다 금액을 계산한다.
- 고객별로 금액, 수량, 장바구니 수를 합친다.
- 전체 고객 목록을 기준으로 합계를 연결해, 장바구니가 없는 고객도 결과에 남게 한다. 고객명은 응답의 이름 필드를 이어 붙여 만든다.
- 모든 고객의 결과를 하나의 아이템으로 묶어 `Gmail` 노드(`관리자 메일 발송`)로 보낸다.
- 분석 기록의 4)에 과제 2의 검증 결과를 채우고, 워크플로우를 `04_구매예정금액보고.json`으로 내보낸다.

# 분류 추출 지시문과 스키마

> 4장 실습 4-6에서 `Information Extractor` 노드 `요청 분류`에 넣는 지시문과 스키마다. 1장 분해도의 분류 단계와 2장 요청 기록 계약의 유형 값을 문의 기록 단계로 옮긴 것이다.
> 실습 4-7의 메일 문의에서는 여기에 추출 항목을 더해 쓴다.

## 1. System Prompt Template

`Information Extractor`의 **Options → System Prompt Template**에 넣는다. n8n이 출력 형식에 관한 지시를 뒤에 자동으로 덧붙인다.

```text
너는 온라인 쇼핑몰 하루마켓의 고객 문의를 분류한다.
문의 문장만 보고 판단한다. 문장에 없는 사실을 짐작하지 않는다.

detected_type은 아래 값 중 하나다.
- shipping_status: 배송 일정, 배송 위치, 출고 시점을 묻는다
- return_change_of_mind: 단순 변심으로 반품이나 환불을 원한다
- return_defect: 불량, 오배송, 구성품 누락, 상품 정보와 다름을 이유로 반품이나 환불을 원한다
- exchange_option: 같은 상품의 다른 옵션(사이즈, 색상)으로 바꾸고 싶다
- exchange_other_product: 다른 상품으로 바꾸고 싶다
- cancel_full: 주문 전체를 취소하고 싶다
- cancel_partial: 주문 수량의 일부만 취소하고 싶다
- mixed: 위의 요청이 두 가지 이상 섞여 있거나, 고객이 둘 중 무엇을 원하는지 정하지 않았다
- other: 위 어디에도 해당하지 않는다

dispute_mentioned는 소비자원, 신고, 소송처럼 분쟁을 언급하면 true다.
repeat_mentioned는 같은 일로 이미 문의했다고 말하면 true다.
```

## 2. 스키마

**Schema Type**을 Define using JSON Schema로 두고 아래를 넣는다.

```json
{
  "type": "object",
  "properties": {
    "detected_type": {
      "type": "string",
      "enum": [
        "shipping_status",
        "return_change_of_mind",
        "return_defect",
        "exchange_option",
        "exchange_other_product",
        "cancel_full",
        "cancel_partial",
        "mixed",
        "other"
      ]
    },
    "dispute_mentioned": { "type": "boolean" },
    "repeat_mentioned": { "type": "boolean" }
  },
  "required": ["detected_type", "dispute_mentioned", "repeat_mentioned"]
}
```

JSON 예시로 스키마를 만들지 않고 JSON Schema를 직접 쓰는 이유는 허용 값 목록(`enum`)을 적기 위해서다. 예시로 만들면 "문자열"이라는 데이터 타입만 정해지고 어떤 문자열이 허용되는지는 정해지지 않는다.

## 3. 값을 고른 이유

| 값 | 어디에서 왔는가 |
|---|---|
| `shipping_status`, `return_change_of_mind`, `return_defect`, `mixed`, `other` | 1장 실습 1-3의 요청 유형 목록 |
| `exchange_option`, `exchange_other_product`, `cancel_full`, `cancel_partial` | 1장 실습 1-4의 요청 유형 목록 |
| `dispute_mentioned`, `repeat_mentioned` | 1장 분류 단계의 표시, 2장 문의 기록 계약의 `flags` |

2장 계약의 `flags`에는 `reason_unclear`(반품 사유 불명확)도 있다. 4장은 반품 경로를 만들지 않으므로 넣지 않았고, 반품 경로를 만드는 6장에서 더한다. 더하는 내용은 5절에 있다.

## 4. 스키마가 막아 주는 것과 막지 못하는 것

- 막아 주는 것: 목록에 없는 유형 이름, 불리언이 아닌 표시 값이 나오는 일을 모델 호출 단계에서 줄인다.
- 막지 못하는 것: 목록 안의 **틀린 값**이다. 반품 문의를 `exchange_option`으로 분류해도 형식은 맞다. 그래서 분류 결과는 계약 테스트로 사례를 대조해 확인한다.
- 스키마를 지정해도 규칙 검사를 빼지 않는다. 뒤의 분기가 이 값에 의존하기 때문이다(2장 원칙).

## 5. 6장에서 더하는 것

6장에서 반품 경로를 만들면서 표시 하나와 항목 하나를 더한다. **4장 실습에서는 더하지 않는다.** 6장 실습 6-3의 1단계에서 아래를 반영한다.

### 5-1. `reason_unclear` 표시

1절의 지시문 끝에 한 줄을 더한다.

```text
reason_unclear는 반품이나 교환을 원한다고는 했지만 그 이유가 문장에 드러나지 않으면 true다.
불량인지 단순 변심인지 알 수 없는 경우가 여기에 해당한다.
```

2절의 스키마에서 `flags`의 속성에 아래를 더하고 `required`에도 이름을 넣는다.

```json
"reason_unclear": { "type": "boolean" }
```

이 표시가 필요한 이유가 있다. **단순 변심과 불량은 배송비를 누가 내는지가 다르다.** 어느 쪽인지 모르는 채로 판단하면 금액이 틀린다. 그래서 `reason_unclear`가 `true`인 반품 요청은 판단하지 않고 담당자에게 넘긴다(`handover_reason`은 `flagged`).

### 5-2. 교환 사유 `exchange_reason`

교환 요청에는 사유를 따로 받는다(2장 표 2-56). 지시문에 아래를 더한다.

```text
exchange_reason은 detected_type이 exchange_option이나 exchange_other_product일 때만 채운다.
- change_of_mind: 사이즈나 색상이 마음에 들지 않는다
- defect: 불량, 오염, 오배송을 이유로 든다
어느 쪽인지 알 수 없으면 비워 둔다.
```

스키마에는 `enum`이 `change_of_mind`와 `defect`인 문자열 속성으로 더한다. `required`에는 넣지 않는다. 반품 문의에는 이 값이 없어야 하기 때문이다.

`defect`인 교환은 사실 확인이 필요하므로 판단 단계에서 담당자에게 넘긴다. 모델이 "불량이라고 했다"는 사실만 옮기고, 정말 불량인지는 사람이 본다.

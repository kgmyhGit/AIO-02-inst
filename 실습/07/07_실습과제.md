# 7장 실습과제. 역할 분담과 상태 전달을 갖춘 멀티 에이전트

# 개요

## 1. 이 실습을 통해 배울 것

이 장에서는 에이전트 하나가 하던 일을 여러 역할로 나누고, 나눈 역할을 다시 잇는다. 모든 실습은 같은 순서를 따른다. 먼저 에이전트 하나로 만들어 기준선을 재고, 나눈 뒤에 같은 입력으로 다시 재서 비교한다. 나눈 구성이 기준선보다 낫지 않다는 결과도 그대로 기록한다.

- 역할 계약을 쓰고, 나누어서 얻는 것과 잃는 정보를 함께 확인한다.
- 순차 연결, 라우팅, 감독-작업자 구성을 만들고 언제 어느 구성이 알맞은지 판단한다.
- 위임 방식을 공식 문서로 비교하고, 대상을 정하는 값을 모델이 채우지 않게 한다.
- 역할 사이에서 결과를 규칙으로 검사하고, 상충, 정보 부족, 위임 실패, 한도 도달을 종료 사유로 구분해 남긴다.
- 전문 에이전트가 제안한 집행의 승인을 워크플로우가 요청하게 하고, 여러 요청의 정보가 섞이지 않게 한다.

실습 번호가 권장 순서다. 7-1, 7-2, 7-4, 7-5, 7-6은 누적 프로젝트 결과물 없이 시작할 수 있다. 7-3은 5장의 두 상담 에이전트가, 7-7은 5장 `정책 검색`과 6장의 승인 흐름이, 7-8은 7-7이 있어야 한다.

## 3. 공통사항

**진행 방식**

모든 실습은 같은 순서로 진행한다. 먼저 이 문서와 제공 파일만 보고 주어진 시간 동안 직접 해 본다. 시간이 끝나면 강사가 예시 답안을 보여 주며 왜 그렇게 되는지 설명한다. 자신의 결과물은 고치기 전 상태로 남겨 두고, 풀이와 비교해 다른 부분을 표시한다. 예시 답안과 달라도 이유가 맞으면 성립하는 답이 있으므로, 다른 점마다 자신의 이유를 적어 둔다.

**필요한 것**

- 6장에서 바꾼 실행 환경. 이 장은 컨테이너 구성을 바꾸지 않는다.
- ngrok 터널. `Webhook` 노드와 폼의 주소, 메일의 응답 링크는 3장에서 받은 공개 주소로 만들어지므로, 이 주소를 쓰기 전에 `ngrok http 5678`을 실행한다. 실습을 마치면 `Ctrl+C`로 닫는다. 3장에서 `localhost`로 설정했다면 필요하지 않다.
- 5장의 `정책 상담 에이전트`, `교환 취소 상담 에이전트`, `정책 상담 채팅`, `정책 검색`
- 4장의 `교환 가능 여부 조회`, 6장의 `승인 응답 수신`, `기한 확인`, `반품 진행 통지`, 교환 승인 흐름
- 자격 증명: `OpenAI 실습`, `하루마켓 업무 DB`, `하루마켓 주문 API`, `내 Gmail 발송`. 새로 만드는 것은 없다.
- 집행 키와 외부 뉴스·메신저 계정은 필요하지 않다.

**비용과 메일**

이 장은 앞 장보다 모델을 많이 부른다. 같은 입력을 여러 구성으로 여러 번 실행하기 때문이다. 장 전체를 합해 400번 안쪽으로 어림하며, 반복 횟수를 줄이면 비용이 비례해 준다. 메일은 7-5와 7-7에서 나가고 받는 사람은 본인 주소 하나뿐이다. `설정` 노드나 `요청` 노드의 `mail_to` 값을 실습 전에 반드시 확인한다.

**결과물 저장**

- 작업 폴더에 `07/` 폴더를 만들어 저장한다. 워크플로우는 JSON 파일로 내보내고 문서는 Markdown으로 쓴다.
- 내보낸 파일에 비밀 값이 들어 있지 않은지 확인한다.

**모든 실습에 적용하는 기준**

| 항목 | 기준 |
|---|---|
| 기준일 | 하루마켓의 날짜 계산은 2026-09-10을 오늘로 본다 |
| 모델 | 모든 역할이 `gpt-6-luna`를 쓴다. 비교할 때 모델이 달라지면 차이의 원인을 알 수 없기 때문이다. Options와 Use Responses API는 기본값으로 둔다 |
| 모델 호출 수 | 에이전트는 `Return Intermediate Steps`에 남은 도구 호출 수에 1을 더해 어림하고, `Basic LLM Chain`은 1로 센다 |
| 처리 시간 | 실행 추적에 남긴 시작과 끝 시각의 차이로 잰다 |
| 반복 실행 | 모델의 결과는 실행마다 달라질 수 있다. 문장이 아니라 조건을 만족하는지 본다 |
| 노드 이름 | 사용자가 붙이는 이름은 한국어로, n8n이 제공하는 노드 이름은 원문 그대로 쓰며, 도구 이름은 영문자와 밑줄로 정한다 |
| 데이터 | 글, 매물, 모델 이름, 시세, 요청은 모두 실습용 가상 데이터다 |

# 7-1 - 주간 기술 동향 보고서

## 1. 실습 주제 및 상황

팀에서 매주 월요일에 지난주 기술 동향을 한 쪽짜리 보고서로 정리한다. 기술 커뮤니티에 올라온 글 목록을 읽고, 중요한 글을 골라 주제별로 묶고, 글마다 핵심 사실을 뽑아 보고서를 쓴다. 이 일을 에이전트 하나로 만들어 기준선을 재고, 자료 조사 역할과 요약 작성 역할로 나눈 뒤 비교한다. 수업 중 사이트 상태에 결과가 좌우되지 않도록 가상의 글 12편을 제공한다.

## 2. 이 실습의 목적

- 단일 에이전트 기준선을 재는 방법을 익힌다.
- 역할 계약을 쓰고 순차 연결로 잇는다.
- 나누었을 때 잃는 정보를 규칙 검사가 찾아내는지 확인한다.
- 호출과 시간의 부담까지 보고 구성을 판단한다.

관련 이론: [7.1 단일 에이전트로 부족해지는 때](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#71-단일-에이전트로-부족해지는-때), [7.2 멀티 에이전트의 기본 개념](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#72-멀티-에이전트의-기본-개념), [7.3 주요 멀티 에이전트 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#73-주요-멀티-에이전트-패턴), [7.4 역할을 나누는 기준과 역할 계약](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#74-역할을-나누는-기준과-역할-계약)

## 3. 관련 파일

- [`data/기술동향_한주글.json`](data/기술동향_한주글.json): 가상 기술 커뮤니티의 한 주 글 12편(제목, 요약, 본문, 주소)
- [`configs/동향보고서_설정.md`](configs/동향보고서_설정.md): Data table, 단일 에이전트, 조사·요약 역할, 검사 규칙, 선택 과제의 완성 설정
- [`templates/역할계약서_양식.md`](templates/역할계약서_양식.md): 역할 계약을 쓰는 양식
- [`templates/구성비교표_양식.md`](templates/구성비교표_양식.md): 기준선과 나눈 구성을 비교하는 양식

## 4. 결과물

- `07_주간동향단일.json`, `07_주간동향보고서.json`: 내보낸 워크플로우
- `07_역할계약_동향보고서.md`: 두 역할의 계약
- `07_구성비교_동향보고서.md`: 세 번씩 실행한 비교 표, 나누어 잃은 정보의 확인 결과, 채택할 구성과 이유
- `조사 결과 검사`가 실패하면 `요약 작성`이 실행되지 않는다.

## 5. 해야 할 것

1. **한 주의 글을 넣는다.** 설정 파일 1절대로 Data table `tech_posts`를 만들고, `동향보고서 관련데이터 넣기` 워크플로우를 실행해서 샘플 데이터를 넣는다. 글 12편의 제목, 요약, 본문을 모두 훑어보고, 보고서에 꼭 넣어야 할 글과 빼야 할 글을 먼저 적어 둔다. 요약만 읽을 때와 본문까지 읽을 때 판단이 달라지는 글이 있는지 찾는다.
2. **에이전트 하나로 기준선을 잰다.** 설정 3절의 `주간 동향 단일`을 만들어 세 번 실행하고 비교표 1절에 적는다. 1단계에서 정한 글이 들어가고 빠졌는지, `출처 검사`의 `passed`, 도구 호출 수와 어림 모델 호출 수, 처리 시간을 기록한다. 결과가 좋으면 그대로 적는다.
3. **역할 계약을 쓴다.** 양식에 자료 조사와 요약 작성 역할의 입력, 출력, 쓸 수 있는 도구, 할 수 없는 일, 끝내는 조건을 쓴다. 자료 조사 역할의 입력은 글 목록(`post_id`, `title`, `summary`), 요약 작성 역할의 입력은 조사 결과뿐이다. 나머지 칸을 채운 뒤 설정 4절과 비교한다. 요약 작성 역할에 도구를 주어야 하는지 판단하고 이유를 적는다.
4. **두 역할로 나누어 잇는다.** 설정 5절의 `주간 동향 보고서`를 만든다. `조사 결과 검사`에는 상태 값, 글 번호, 사실 유무, 조사 역할이 보고서 문장을 쓰지 않았는지를 확인하는 규칙 네 개를 둔다. 세 번 실행해 2단계와 같은 항목을 적는다.
    - `요약 작성`의 입력을 왜 글 목록이 아니라 조사 결과로 제한하는지 설명한다.
5. **나누어 잃는 것을 확인한다.** `자료 조사`의 System Message에서 "요약이 짧거나 모호한 글은 반드시 본문을 읽는다"라는 줄을 지우고 두 번 실행한다. 조사 결과에서 빠진 글이 있는지, 그 내용이 보고서에 있는지, `출처 검사`가 어떻게 나오는지 적는다. 이 결과에서 규칙 검사가 무엇을 찾지 못하는지 설명하고 줄을 되돌린다.
6. **두 구성을 비교한다.** 비교표 2절에 나란히 적고 3절에 판단을 쓴다. 나누어서 좋아진 것이 호출과 시간이 늘어난 만큼 가치가 있는가? 기준선에서 틀린 건은 [이론의 규칙·도구·컨텍스트 개선](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#71-단일-에이전트로-부족해지는-때)으로도 고칠 수 있었는가? 매주 자동으로 돌린다면 어느 구성을 쓰겠는가?

## 6. 이어서 더 해 볼 만한 주제

**생성-평가 반복 붙이기.** `요약 작성` 뒤에 평가를 붙이고, 통과하지 못하면 되돌려 다시 쓰게 한다. 설정 파일 6절을 따른다. 평가는 `출처 검사`를 그대로 쓰는 규칙 평가와, "조사 결과의 사실보다 부풀린 표현이 있는가"만 판정하는 모델 평가 두 가지다. 평가가 적은 고칠 점을 입력에 넣고, 되돌림은 두 번까지로 하며, 한도에 이르면 `limit_reached`로 끝낸다. 되돌림 횟수, 통과 여부, 호출 증가를 기록하고 규칙 평가만 남겼을 때와 비교한다.

**주제별 조사를 병렬로 하기.** 설정 파일 7절을 따라 두 방법을 비교한다. 하나는 주제 셋으로 갈래를 나누어 `Merge`(`Append`)로 합치는 방법이고, 다른 하나는 주제 셋을 아이템으로 만들어 `자료 조사`의 `Batch Processing`에서 `Batch Size`를 3으로 두는 방법이다. 실행 화면에서 갈래가 차례로 실행되는지 보고 처리 시간을 잰다. 한 글이 두 주제에 걸칠 때 합치는 단계에서 어떻게 할지도 정한다.

**경쟁사 보도자료 월간 동향.** 조사 역할이 보도자료를 고르고 사실을 뽑으며, 작성 역할이 그 사실만으로 보고서를 쓴다. 실제 사이트의 새 글로 해 보려면 `RSS Read` 노드를 쓰되, 이용 조건을 확인하고 본문 전체를 저장하거나 다시 배포하지 않는다. 뺀 자료의 목록을 남겨 사람이 훑어볼 수 있게 하고, 그 목록에서 실제로 놓친 자료를 몇 건 찾았는지 적는다.

# 7-2 - 영어 공부 도우미 라우팅

## 1. 실습 주제 및 상황

영어 공부를 도와주는 채팅을 만든다. 사용자는 채팅 하나에 세 가지를 요청한다. 영어 문장을 고쳐 달라는 요청, 단어를 단어장에 넣거나 찾아 달라는 요청, 단어장으로 퀴즈를 내 달라는 요청이다. 먼저 에이전트 하나에 모든 도구와 규칙을 주어 기준선을 재고, 요청을 분류해 담당 셋으로 보내는 라우팅 구성과 비교한다.

## 2. 이 실습의 목적

- 라우팅 구성을 만들고 담당마다 도구를 달리한다.
- 어디에도 맞지 않는 입력과 섞인 입력의 처리를 정한다.
- 담당을 더할 때 고칠 곳이 구성에 따라 어떻게 다른지 비교한다.

관련 이론: [7.3 주요 멀티 에이전트 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#73-주요-멀티-에이전트-패턴), [7.6 설계자가 정하는 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#76-n8n으로-멀티-에이전트-만들기-설계자가-정하는-패턴---순차-연결-라우팅-병렬)

## 3. 관련 파일

- [`test-cases/영어도우미_시험문장.json`](test-cases/영어도우미_시험문장.json): 시험 문장 12건과 기대 담당
- [`configs/영어도우미_설정.md`](configs/영어도우미_설정.md): 단일 에이전트와 라우팅 구성의 완성 설정

## 4. 결과물

- `07_영어도우미단일.json`, `07_영어공부도우미.json`: 내보낸 워크플로우
- `07_라우팅시험기록.md`: 12건의 결과, 두 구성의 도구 선택 오류 수와 분류 오류 수, 섞인 요청의 처리 판단, 담당을 더할 때 고칠 곳
- 어디에도 맞지 않는 문장에 되묻는 답이 나오고, 퀴즈 담당은 단어장을 읽기만 한다.

## 5. 해야 할 것

1. **단어장을 만든다.** 설정 1절대로 Data table `vocab`(`word`, `meaning`, `example`)을 만들고 준비 코드로 단어 여섯 개를 넣는다.
2. **에이전트 하나로 기준선을 잰다.** 설정 2절의 `영어 도우미 단일`을 만든다. 시험 문장 12건을 차례로 보내되 **문장마다 채팅 창을 새로 시작한다.** 문장마다 다음을 적는다.

    | 문장 | 에이전트가 한 일 | 도구 선택이 맞았는가 | 기대와 다른 점 |
    |---|---|---|---|
    |  |  |  |  |

3. **담당 셋으로 나눈다.** 설정 3절의 `영어 공부 도우미`를 만든다. `Text Classifier` 뒤에 문장 첨삭(`Basic LLM Chain`), 단어장 담당(`AI Agent`, `add_word`, `find_words`), 퀴즈 담당(`AI Agent`, `find_words`)을 둔다. When No Clear Match를 `Output on Extra, 'Other' Branch`로 바꾸어 어디에도 맞지 않는 문장에 되묻는 답을 보낸다. 범주의 Description은 설정 파일의 문장을 쓴다. 같은 12건을 보내 같은 표에 적는다.
4. **섞인 요청과 애매한 요청을 본다.** 시험 문장의 E-11과 E-12를 살펴본다. `Allow Multiple Classes To Be True`를 끄고 켜며 E-11이 어디로 가고 채팅 창에 어떤 답이 나오는지 표로 적는다. 끝나면 끔으로 되돌린다. Description 끝의 "다른 범주의 요청이 함께 섞여 있으면 여기에 넣지 않는다"를 잠시 지우고 다시 비교한다. 선택한 방식의 대가도 적는다.
5. **담당을 하나 더한다면 고칠 곳을 적는다.** 발음 질문 담당을 더한다고 가정한다. 실제로 만들지 않아도 된다. 단일 에이전트와 라우팅에서 각각 고칠 곳과, 기존 동작이 달라지지 않았는지 다시 확인해야 할 범위를 적는다.

## 6. 이어서 더 해 볼 만한 주제

**가족이 함께 쓰는 채팅.** 가계부 기록, 장보기 목록, 가족 일정 요청을 담당 셋으로 나눈다. 가계부 담당만 지출을 쓰게 하는 등 라우팅으로 권한을 나누고, 다른 담당으로 잘못 분류되었을 때 어떤 일까지 일어날 수 있는지 시험한다. 금액이 들어 있는 문장의 분류가 틀렸을 때의 안전장치도 정한다.

**사내 요청 채널 나누기.** IT, 총무, 인사 요청을 나누는 라우팅을 만든다. 인사 담당만 휴가 기록을 읽게 하고, 어디에도 맞지 않는 요청은 사람에게 넘긴다. 실제로 들어올 법한 요청 서른 건을 만들어 분류 오류를 범주별로 세고, Description을 고친 전후를 비교한다.

**규칙 우선 라우팅과 모델 분류 비교.** "퀴즈"처럼 분명한 낱말이 있으면 규칙으로 보내고 나머지만 모델에게 묻는 구성을 만든다. 12건에서 모델 호출 수와 분류 정확성이 어떻게 달라지는지 비교한다. 이 비교는 9장에서 본격적으로 이어진다.

# 7-3 - 상담 창구 통합과 라우팅

## 1. 실습 주제 및 상황

5장에서 하루마켓의 정책 상담 채팅을 둘 만들었다. 반품·배송 상담과 교환·취소 상담이다. 고객이 어느 채팅에 들어가야 할지 스스로 골라야 하는 불편이 있다. 이 실습에서 두 채팅을 하나의 창구로 합치고, 질문에 따라 알맞은 담당으로 보낸다. 두 상담 에이전트 서브워크플로우는 한 글자도 고치지 않고 다시 쓴다.

## 2. 이 실습의 목적

- 기존 서브워크플로우를 고치지 않고 라우팅으로 다시 쓴다.
- 담당별로 대화 메모리를 나누어 섞이지 않게 한다.
- 메시지마다 분류하는 라우팅의 한계를 확인하고 핸드오프와 비교한다.

관련 이론: [7.5 공유 상태](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#75-공유-상태-에이전트-사이에-무엇을-넘기고-어디에-남기는가), [7.6 설계자가 정하는 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#76-n8n으로-멀티-에이전트-만들기-설계자가-정하는-패턴---순차-연결-라우팅-병렬)

## 3. 관련 파일

- [`test-cases/상담창구_분류시험.json`](test-cases/상담창구_분류시험.json): 분류 시험 질문 10건과 주제가 바뀌는 대화 한 벌
- [`configs/상담창구_노드설정.md`](configs/상담창구_노드설정.md): `상담 창구` 워크플로우의 완성 설정

## 4. 결과물

- `07_상담창구.json`: 내보낸 워크플로우
- `07_상담창구_시험기록.md`: 분류 시험 결과와 다른 건의 이유, 주제가 바뀌는 대화의 결과, 핸드오프와 비교한 한계 두 줄
- 다음 상태가 되어 있어야 한다.
    - 두 상담 에이전트의 수정 시각이 5장 그대로다.
    - 어디에도 맞지 않는 질문에 담당자 연결 문구가 나온다.
    - `chat_memory`에서 같은 채팅의 `return:`과 `exchange:` 세션 행이 따로 있다.

## 5. 해야 할 것

1. **5장 채팅 워크플로우를 복제한다.** `정책 상담 채팅`을 복제해 이름을 `상담 창구`로 바꾼다. 세션 기록, 넘긴 세션 확인, 턴 결과 정하기, 세션 상태 갱신, 답변 노드는 그대로 쓰고, 설정 파일 1절에 정리한 곳만 바꾼다. 분류 뒤의 `Edit Fields` 두 개에서 담당마다 `topic`과 `session_id`를 정한다.
    - **확인 지점:** `session_id` 앞에 담당 이름(`return:`, `exchange:`)을 붙이면 대화 메모리와 `chat_sessions`에 어떤 일이 생기는가?
2. **분류를 시험한다.** 질문 10건을 **질문마다 채팅 창을 새로 시작해** 보낸다. `담당 분류`의 출력에서 기대 담당과 실제 담당을 비교하고, 5장 평가표에 있는 질문은 답의 성격을 비교한다.
    - **확인 지점:** 섞인 질문과 상관없는 질문은 어디로 가는가? 두 담당에 걸치는 질문은 어디로 갔고, 그 답이 질문에 맞는가?
3. **대화 도중에 주제가 바뀌면 어떻게 되는지 본다.** `topic_switch` 대화를 **한 채팅 창에서** 차례로 보내고, 담당과 답을 기록한다.

    | 순서 | 보낼 문장 | 간 담당 | 앞의 대화를 알고 답했는가 |
    |---|---|---|---|
    | (1) | 단순 변심 반품은 며칠 안에 신청해야 하나요? |  |  |
    | (2) | 그럼 교환은요? |  |  |
    | (3) | 배송비는 누가 내요? |  |  |

    이 결과를 [이론의 핸드오프 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#73-주요-멀티-에이전트-패턴)과 비교해 두 줄로 적는다. 이 실습에서 핸드오프를 만들지는 않는다.
4. **메모리가 나뉘었는지 확인한다.**

    ```sql
    SELECT session_id, count(*) AS messages
    FROM chat_memory
    WHERE session_id LIKE 'return:%' OR session_id LIKE 'exchange:%'
    GROUP BY session_id
    ORDER BY session_id;
    ```

5. **저장한다.** 워크플로우를 내보내고 기록을 저장한다.

## 6. 이어서 더 해 볼 만한 주제

**현재 담당을 기억해 후속 질문 처리하기.** 세션 기록에 현재 담당을 남기고, 짧은 후속 질문은 분류 전에 같은 담당으로 보내는 규칙을 만든다. 어떤 문장을 짧은 후속 질문으로 볼지 기준을 정하고, 주제가 정말 바뀐 경우를 놓치지 않는지 시험한다. 이 규칙의 대가를 라우팅만 쓸 때와 비교해 적는다.

**핸드오프 흉내 내기.** 담당을 넘길 때 앞의 대화 요약을 필드로 넘기는 구조를 설계한다. 요약을 누가 만들고, 어디에 저장하고, 다음 담당의 입력 어디에 넣을지 정한다. 작은 샘플로 구현해 라우팅만 쓸 때의 답과 비교하고, 모델 호출이 얼마나 느는지 잰다.

**세 번째 담당 더하기.** 결제·환불 문의 담당을 더한다고 하고, 정책 문서의 범위와 분류 Description, 세션 ID의 앞머리를 정한다. 기존 두 담당을 고치지 않고 더할 수 있는지 확인하고, 분류 시험을 다시 실행해 기존 질문의 분류가 달라지는지 비교한다.

# 7-4 - 위임 방식 탐색

## 1. 실습 주제 및 상황

하루마켓의 반품 처리에 다음 요구가 있다. 이 요구를 만족하는 위임 방식을 공식 문서로 찾아 고른다.

> 반품 요청의 정책 조사와 처리안 작성을 역할 둘로 나눈다. 두 역할은 따로 시험할 수 있어야 하고, 정해진 순서로 부르는 구성과 감독 에이전트가 고르는 구성 양쪽에서 같은 역할을 고치지 않고 다시 쓸 수 있어야 한다. 요청 식별자처럼 대상을 정하는 값은 모델이 채우지 않아야 한다.

## 2. 이 실습의 목적

- 역할의 형태와 연결 방식을 나누어 판단한다.
- 세 위임 방식의 차이를 공식 문서로 확인한다.
- 대상을 정하는 값을 누가 채우는지를 기준으로 방식을 고른다.

관련 이론: [7.6 설계자가 정하는 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#76-n8n으로-멀티-에이전트-만들기-설계자가-정하는-패턴---순차-연결-라우팅-병렬), [7.7 모델이 정하는 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#77-n8n으로-멀티-에이전트-만들기-모델이-정하는-패턴---감독-작업자supervisor-worker-패턴)

## 3. 관련 파일

- [`../03/templates/기능탐색기록_양식.md`](../../03/템플릿_가이드/templates/기능탐색기록_양식.md): 기능 탐색 기록 양식. 이 양식을 쓰는 마지막 장이다.

## 4. 결과물

- `07_기능탐색기록_위임.md`: 세 방법의 비교 표, 역할의 형태와 연결 방식에 대한 선택과 이유

## 5. 해야 할 것

1. **세 방법을 문서로 확인한다.**

    | 방법 | 공식 문서에서 확인할 것 |
    |---|---|
    | `Execute Sub-workflow`로 차례로 부르기 | Mode의 두 값, `Wait for Sub-Workflow Completion`, 서브워크플로우가 무엇을 돌려주는가 |
    | `Call n8n Workflow Tool`로 감독 에이전트의 도구로 주기 | Workflow Inputs를 채우는 방법(고정 값, 표현식, `$fromAI()`), 프로덕션에서의 Publish 조건 |
    | `AI Agent Tool` | Description과 Prompt (User Message), 여러 단계로 겹쳐 연결, 하위 노드의 표현식이 어떻게 계산되는가 |

2. **요구에 비추어 비교한다.**

    | 요구 | `Execute Sub-workflow` | `Call n8n Workflow Tool` | `AI Agent Tool` |
    |---|---|---|---|
    | 역할을 따로 시험한다 |  |  |  |
    | 순서대로 부르는 구성에서 쓴다 |  |  |  |
    | 감독 에이전트가 고르는 구성에서 쓴다 |  |  |  |
    | 대상을 정하는 값을 모델이 채우지 않는다 |  |  |  |

3. **고르고 이유를 적는다.** 한 가지 방법만 고를 필요는 없다. 역할은 어떤 형태로 만들고, 연결은 무엇으로 하는가를 나누어 답한다.

## 6. 이어서 더 해 볼 만한 주제

**작은 데이터로 세 방식 실행해 보기.** 문서 비교로 끝내지 말고 같은 역할을 세 방식으로 연결해 실행한다. 입력에 고객 번호를 넣고, 각 방식에서 그 값을 모델이 바꿀 수 있는지 일부러 시험한다. 실행 기록에 무엇이 어떻게 남는지도 비교해 표에 더한다.

**프레임워크 경험과 대응해 보기.** 다른 도구로 에이전트를 만들어 본 경험이 있다면, 그때의 도구 호출과 하위 그래프가 n8n의 어떤 기능에 대응하는지 표로 적는다. 그대로 대응되지 않는 기능과, n8n에서 대신 어떻게 해야 하는지 정리한다.

**내 업무의 역할 나누기 초안.** 자신의 업무에서 두세 역할로 나눌 만한 일을 고른다. 역할마다 입력, 출력, 도구, 할 수 없는 일을 적고, 순서가 정해져 있는지 요청마다 달라지는지에 따라 연결 방식을 고른다. 나누지 않는 편이 낫다는 결론이 나오면 그 근거를 적는다.

# 7-5 - 사내 세미나 준비 도우미

## 1. 실습 주제 및 상황

사내 세미나를 준비하는 담당자를 돕는 도우미를 만든다. 요청은 제각각이다. 장소만 묻기도 하고, 예산만 묻기도 하고, 장소와 예산과 안내문을 한 번에 부탁하기도 한다. 요청마다 필요한 역할이 다르므로 감독 에이전트가 필요한 전문 에이전트만 골라 맡기게 한다. 안내문 발송은 감독 에이전트가 하지 않고, 워크플로우가 사람의 승인을 받은 뒤에 한다.

## 2. 이 실습의 목적

- 감독 에이전트와 `AI Agent Tool`로 모델이 정하는 위임을 만든다.
- 같은 요청에서 경로가 달라지는 것을 추적하고 받아들일 수 있는지 판단한다.
- 반복 한도에 걸린 실행이 성공처럼 이어지지 않게 한다.
- 위임한 작업의 승인을 워크플로우가 요청하게 한다.

관련 이론: [7.3 주요 멀티 에이전트 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#73-주요-멀티-에이전트-패턴), [7.7 모델이 정하는 패턴](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#77-n8n으로-멀티-에이전트-만들기-모델이-정하는-패턴---감독-작업자supervisor-worker-패턴), [7.9 위임한 작업의 권한과 승인 경로](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#79-위임한-작업의-권한과-승인-경로)

## 3. 관련 파일

- [`data/회의실예약_샘플.json`](data/회의실예약_샘플.json): 회의실 네 곳의 한 주 예약 현황
- [`test-cases/세미나요청_시험.json`](test-cases/세미나요청_시험.json): 필요한 역할이 서로 다른 요청 네 건
- [`configs/세미나도우미_설정.md`](configs/세미나도우미_설정.md): 감독 에이전트, `AI Agent Tool` 세 개, 승인 발송의 완성 설정

- `07_세미나준비도우미.json`: 내보낸 워크플로우

- 안내문은 승인한 뒤에만 본인 메일로 도착하며, 거절하거나 한도에 걸리면 메일이 나가지 않는다.
- 금액이 `calc_budget` 도구의 결과와 같다.

## 5. 해야 할 것

1. **회의실 예약 현황을 넣는다.** 설정 1절대로 Data table `rooms`를 만들고 준비 코드로 예약 현황을 넣는다.
2. **전문 에이전트 셋과 감독 에이전트를 만든다.** 설정 2절의 `세미나 준비 도우미`를 만든다. 감독 에이전트 아래에 `AI Agent Tool`로 장소 확인(`find_venue`), 예산 계산(`estimate_budget`), 안내문 작성(`write_notice`)을 둔다. 장소 확인에는 `Data table` 도구 `find_rooms`를, 예산 계산에는 `Code Tool` `calc_budget`을 붙이고, 안내문 작성에는 도구를 붙이지 않는다. Description은 설정 파일의 문장을 그대로 쓴다. 감독 에이전트의 Options에서 `Return Intermediate Steps`를 켠다. 왜 금액을 도구가 계산하게 하는지, 왜 감독 에이전트에게 메일 도구를 주지 않는지 생각한다.
3. **요청 네 건을 넣고 위임을 추적한다.** 요청을 `요청` 노드의 `request` 값에 하나씩 넣어 실행하고 `위임 기록`의 출력을 옮긴다. 안내문이 필요한 요청에서 안내문 작성이 언제 불렸는지, 넘긴 입력에 회의실 이름과 금액이 맞게 들어 있는지 본다.

    | 요청 | 필요하다고 판단한 역할 | 부른 역할과 순서 | 안내문이 있는가 |
    |---|---|---|---|
    | S-1 ~ S-4 |  |  |  |

4. **같은 요청을 세 번 실행한다.** S-3을 세 번 실행해 표를 채운다. 경로가 달랐다면 차이를 적고, 이 업무에서 그 변동을 받아들일 수 있는지 한 줄로 판단한다.

    | 회차 | 부른 역할과 순서 | 어림 모델 호출 수 | 처리 시간 |
    |---|---|---|---|
    | 1 ~ 3 |  |  |  |

5. **반복 한도에 걸리게 해 본다.** 감독 에이전트의 `Max Iterations`를 `2`로 낮추고 S-3을 실행한다. 실행 상태, `위임 기록`에 남은 내용, 메일 발송 여부를 적는다. 끝나면 `6`으로 되돌린다.
6. **안내문 발송을 승인한다.** S-3을 실행해 승인 요청 메일을 받고, 한 번은 `Decline`을, 한 번은 `Approve`를 누른다. 6-1과 무엇이 같고 무엇이 달라졌는지 적는다.
7. (**선택**) **전문 에이전트 안에 승인을 넣어 본다.** `write_notice`의 Tool 연결점에서 Human review 묶음의 `Send Email`을 고르고, 그 아래에 안내문을 저장하는 도구를 붙여 실행한다. 이 승인이 무엇을 승인하는 것인지, 6단계와 무엇이 다른지 한 줄로 적고 사람 검토 노드를 지운다.

## 6. 이어서 더 해 볼 만한 주제

**이사 준비 도우미.** 이사업체 견적, 인터넷 이전, 주소 변경 목록 중 요청에 필요한 것만 전문 에이전트에게 맡긴다. 견적 금액은 도구가 계산하고, 실제 신청은 승인 뒤의 워크플로우가 하도록 나눈다. 같은 요청을 여러 번 실행해 경로 변동을 재고, 이사 날짜가 없는 요청에서 되묻는지 시험한다.

**신입 입사 준비 도우미.** 장비 요청, 계정 신청, 첫날 안내문을 전문 에이전트로 나눈다. 계정 신청처럼 되돌리기 어려운 일은 초안까지만 만들게 하고, 담당자 승인 뒤에 워크플로우가 처리하도록 한다. 권한 점검표를 먼저 쓰고, 각 전문 에이전트가 바꿀 수 있는 것이 없는지 확인한다.

"**모두**" **필요한 요청만 순서 고정하기.** 요청을 먼저 규칙이나 분류로 살펴, 세 역할이 모두 필요하면 순차 연결로, 일부만 필요하면 감독 구성으로 보내는 혼합 구성을 만든다. 같은 네 요청으로 경로 변동, 호출 수, 시간을 비교해 감독 구성만 쓸 때보다 나은지 판단한다.

# 7-7 - 반품 정책 조사와 처리안 작성 협업

## 1. 실습 주제 및 상황

6장까지의 하루마켓은 규칙으로 판단할 수 없는 반품 요청(`handover_reason`이 `mixed_or_other`, `flagged`)을 `under_review`로 넘기고 멈춘다. 이 실습에서는 처리안을 쓰는 일을 두 역할에게 맡긴다. 결정은 여전히 사람이 한다. 처리안이 규칙 검사를 통과하면 워크플로우가 6장의 승인 요청을 보내고(T17), 통과하지 못하면 처리안을 참고 자료로 남긴 채 `under_review`에 둔다. 종결(T18)은 담당자가 한다.

## 2. 이 실습의 목적

- 역할을 서브워크플로우로 만들어 따로 시험하고, 연결 방식만 바꾸어 다시 쓴다.
- 단일, 순차, 감독 세 구성을 같은 입력으로 비교해 판단한다.
- 공유 상태를 워크플로우만 쓰게 하고, 실행 추적을 남긴다.
- 승인 흐름을 바꾸지 않고 처리안을 만드는 자리만 더한다.

## 5. 해야 할 것

1. **업무 데이터베이스를 바꾼다.** `Postgres` 노드에서 `업무DB_7장변경.sql` 전체를 한 번 실행한다. 다음 질의로 시험 요청 여섯 줄을 확인하고, 사례 파일에서 내용을 읽는다.

    ```sql
    SELECT request_id, request_type, request_status, handover_reason, order_id
    FROM requests WHERE request_id LIKE 'REQ-70%' ORDER BY request_id;
    ```

2. **역할 계약을 확인하고 권한 점검표를 쓴다.** `반품협업_지시문.md`의 1절을 [이론 7.4절](../../../07_역할분담과상태전달을갖춘멀티에이전트.md#74-역할을-나누는-기준과-역할-계약)과 대조해 읽는다. 점검표를 복사해 `07_권한점검표_반품.md`로 채운다.
    - **확인 지점:** 조사 역할의 출력에서 워크플로우가 채우는 필드와 모델이 채우는 필드는 무엇인가? 처리안 역할의 입력에 문의 원문이 있는가? 금액은 누가 계산하는가?
3. **역할 서브워크플로우를 만든다.** 설정 1~3절을 따라 `반품 정책 조사`, `반품 처리안 작성`, `반품 단일 처리안`을 만든다. 만들 때마다 설정 1-9절의 시험 입력으로 서브워크플로우만 따로 실행해 `agent_steps`에 행이 생기는지 확인한다. 시험이 끝나면 **Publish하고**, 고친 뒤에도 다시 게시한다.
    - **확인 지점:** 공유 상태를 쓰는 주체는 누구인가? 처리안 역할이 조사 결과를 입력으로 받지 않고 `agent_steps`에서 읽는 이유는 무엇인가?
4. `반품 협업 한 건`**과** `반품 협업`**을 만든다.** 설정 4, 5절을 따라 만든다. 구성은 `설정` 노드의 `setup` 값 하나로 바꾼다.
    - **확인 지점:** 세 구성에서 달라지는 곳은 어디인가? 순차 구성은 조사 결과가 `ok`가 아니면 어떻게 하는가? `요청마다 실행` 앞에 `요청 반복`(`Loop Over Items`)을 두는 이유는 무엇인가? 감독 에이전트의 도구 입력에 `$fromAI()`가 있는가? `협업 대상 조회`의 조건 중 승인 대기 요청을 막는 줄은 무엇인가?
5. **검사 규칙을 읽는다.** 설정 4-11절의 `계약·충돌 검사와 근거 계산`을 읽고, 규칙마다 무엇을 확인하며 실패하면 어떤 종료 사유가 되는지 표로 정리한다. 처리안의 판정 값에 따라 종료 사유와 요청 상태가 어떻게 달라지는지도 적는다.
6. **기준선을 잰다.** `setup`을 `single`로 두고 실행한 뒤 다음 질의로 확인해 비교표 1절에 옮긴다. 기대와 다른 건은 `agent_steps`의 `output`을 열어 이유를 한 줄로 적는다. 승인 요청 메일이 오더라도 **이 단계에서는 승인하지 않는다.** 비교 중에는 `기한 확인`을 잠시 Unpublish하거나 결과를 확인한 뒤 초기화한다.

    ```sql
    SELECT r.request_id, r.setup, r.end_reason, r.outcome, r.model_calls,
           extract(epoch FROM r.finished_at - r.started_at)::int AS seconds
    FROM agent_runs r
    WHERE r.setup = 'single'
    ORDER BY r.request_id;
    ```

7. **순차 구성과 감독 구성을 잰다.** `업무DB_7장시험초기화.sql`을 실행해 되돌린 뒤 `sequential`을 1회, `supervisor`를 3회 실행한다. 회차마다 초기화한다. 감독 구성에서 역할을 부른 순서와 횟수를 `agent_steps`의 `supervisor` 행에서 보고, 경로가 달라진 건을 센다. 감독 에이전트가 불필요한 역할을 불렀을 때 결과가 어떻게 되는지도 확인한다.
8. **세 구성을 비교해 판단한다.** 비교표 2절을 채우고 3절에 판단을 쓴다. 측정 결과가 예상과 다르면 결과를 따른다.

    | 구분 | 단일 | 순차 | 감독(3회) |
    |---|---|---|---|
    | 기대 결과와 일치(5건 중) |  |  |  |
    | 평균 어림 모델 호출 수 |  |  |  |
    | 평균 처리 시간 |  |  |  |
    | 같은 요청에서 경로가 달라진 건 |  |  |  |
    | 종료 사유별 건수 |  |  |  |

9. **승인 경로를 확인한다.** 순차 구성으로 다시 실행해 승인 요청이 온 건을 승인한다. 메일에 처리안의 출처가 적혀 있는지 확인하고, `setup`을 바꾸어 다시 실행해 그 요청이 조회되는지 본다. 요청 기록의 `approved_refund_amount`와 `policy_ref`를 SQL로 확인한다. 이후 회수부터 환불까지는 6장 `반품 진행 통지`가 그대로 처리한다.
10. **저장한다.** 다섯 워크플로우를 내보낸다. 처음부터 다시 하려면 `업무DB_7장시험초기화.sql`을 실행한다. 모의 API에 환불이 집행되었다면 그 기록은 실습 6-3의 되돌리기 절차로 지운다.

## 6. 이어서 더 해 볼 만한 주제

**처리안을 담당자가 고치는 화면 만들기.** 규칙 검사를 통과하지 못한 처리안을 담당자가 폼으로 보고, 판정과 정책 번호를 고쳐 승인 요청으로 보내거나 종결하는 흐름을 만든다. T17, T18을 구현하는 셈이다. 담당자가 처리안을 얼마나 고쳤는지 기록해 어떤 역할을 개선해야 하는지 찾아본다.

**평가 역할 더하기.** 처리안과 조사 결과를 읽고 빠진 근거가 있는지 판정하는 평가 역할을 더한다. 7-1의 생성-평가 반복처럼 되돌림 한도를 두고, 규칙 검사로 잡히지 않던 사례가 잡히는지 시험한다. 호출 증가와 효과를 비교표에 더해 판단한다.

**내 업무의 처리안 초안 흐름 설계하기.** 자신의 업무에서 사람이 초안을 쓰고 결재받는 일을 골라, 조사 역할, 작성 역할, 규칙 검사, 승인 요청으로 나눈 설계서를 쓴다. 역할별 권한 점검표를 함께 채우고, 에이전트가 바꿀 수 있는 것이 정말 없는지 확인한다.

## 5. 해야 할 것

전체 순서는 실습 7-7의 2~5단계를, 비교가 필요하면 6~8단계를 참고한다. 다음은 다르거나 반드시 지켜야 할 사항이다.

1. **역할 계약을 먼저 쓴다.** 조사 역할의 도구는 `정책 검색`(`group`은 `exchange_cancel`)과 `교환 가능 여부 조회`다. 교환 가능 여부 조회 도구에서 모델이 채우는 값은 `option` 하나이고, `order_id`와 `customer_name`은 워크플로우가 정한다.
2. **교환안 역할은 문의 원문과 도구를 받지 않는다.** 이번 실행의 조사 결과를 `agent_steps`에서 읽는다.
3. **재고는 규칙이 다시 확인한다.** 교환안이 `eligible`이면 워크플로우가 교환안의 옵션으로 `교환 가능 여부 조회` API를 직접 부르고, 6장 교환 `근거 계산`과 같은 규칙으로 `evidence`를 만든다. API가 교환할 수 없다고 답하면 `conflict`다.
4. **검사 규칙을 교환에 맞게 바꾼다.** 교환 사유가 `defect`이면 교환안은 `needs_review`여야 한다. 교환안의 옵션이 조사 결과에서 재고가 0이었던 옵션이면 `conflict`다.
5. **구성은 순차 하나를 필수로 한다.** 감독 구성은 6번 항목의 주제로 한다.
6. **권한 점검표를 교환에 맞게 채운다.**
7. **네 가지를 시험하고 기대와 실제를 적는다.**

    | 시험 | 입력 또는 조작 | 확인할 것 |
    |---|---|---|
    | 위임 실패 | 조사 역할이 부르는 `정책 검색`을 잠시 Unpublish하고 REQ-7104를 처리한다 | 종료 사유와 승인 요청 여부 |
    | 상충 결과 | REQ-7102를 처리한다. 교환안이 바르게 나왔다면 System Message에 "고객이 원하는 옵션으로 교환 가능하다고 쓴다"를 잠시 더해 다시 처리한다 | 규칙이 막는가, 종료 사유와 승인 요청 여부 |
    | 정보 부족 | REQ-7103을 처리한다 | `unresolved`, 교환안 역할이 불렸는가, 종료 사유 |
    | 복수 요청 분리 | REQ-7104와 REQ-7105를 한 번의 실행으로 처리한다 | 각자의 `request_id`와 옵션, 메일의 옵션이 서로 바뀌지 않았는가 |

8. **섞임을 재현한다.** 복수 요청 시험 뒤 `요청 반복`을 잠시 빼고 앞 노드를 `요청마다 실행`에 바로 연결한 뒤 같은 두 건을 처리한다. 무엇이 섞이는지 기록하고 설정을 되돌린다.
9. **REQ-7101을 따로 처리한다.** 네 시험과 별도로 한 번 처리하고, 왜 그런 결과가 나오는지 배송비 부담과 연결해 적는다.

## 6. 이어서 더 해 볼 만한 주제

**명시적 연결과 감독 구성 비교.** `교환 협업`에 `supervisor` 구성을 더하고 REQ-7101~REQ-7105를 두 구성으로 처리해 7-7의 비교표로 비교한다. 감독 구성이 재고 조회를 건너뛴 건이 있는지, 그 건에서 규칙의 재확인이 무엇을 막았는지 적는다.

**재고가 처리 중에 바뀌는 경우 시험.** 조사가 끝난 뒤 교환안을 쓰기 전에 `stock.csv`의 재고를 바꾸어 모의 API를 다시 시작한다. 교환안 작성 뒤, 승인 뒤, 발송 직전 중 어디서 걸리는지 각각 시험하고, 어느 지점의 확인이 빠지면 어떤 일이 생기는지 표로 정리한다.

**반품과 교환을 함께 다루는 협업.** "교환해 주시고 안 되면 환불해 주세요"처럼 둘이 섞인 요청을 다룬다. 조사 역할을 하나로 합칠지, 반품과 교환 역할을 차례로 부를지 비교해 설계한다. 어느 경우에 사람에게 넘길지 규칙을 정하고, `mixed` 요청의 실제 처리 흐름을 그려 본다.

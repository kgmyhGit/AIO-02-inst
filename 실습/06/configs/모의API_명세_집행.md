# 하루마켓 주문 API 명세: 집행 요청

> 교재 6장 실습용이다. 4장 [`모의API_명세.md`](../../../04/템플릿_가이드/configs/모의API_명세.md)의 조회 요청에 **집행 요청 두 가지**를 더한 부분만 적는다.
> 조회 요청은 4장 명세를 그대로 쓴다. 이 문서만 보고 n8n에서 집행 요청을 보낼 수 있어야 한다.

## 1. 조회 요청과 무엇이 다른가

| 항목 | 조회 요청(4장) | 집행 요청(6장) |
|---|---|---|
| **메서드** | `GET` | `POST` |
| **하는 일** | 주문 정보를 읽는다. 몇 번을 불러도 주문은 그대로다 | 환불과 교환 발송을 집행한다. 주문 시스템의 상태가 바뀐다 |
| **키** | 조회 키(`MOCK_API_KEY`) | 집행 키(`MOCK_EXEC_KEY`) |
| **본문** | 없다 | JSON 객체를 보낸다 |
| **같은 요청을 두 번 보내면** | 같은 응답을 받는다 | 요청 식별자가 같으면 처음 집행의 결과를 그대로 받는다(3절) |

**두 키는 서로의 일을 하지 못한다.** 조회 키로 집행 요청을 보내면 403, 집행 키로 조회 요청을 보내면 401을 받는다. 그래서 워크플로우에는 자격 증명을 두 개 등록하고, 집행 요청을 보내는 노드에만 집행 키 자격 증명을 연결한다.

| 자격 증명 이름(권장) | 헤더 이름 | 값 | 연결하는 노드 |
|---|---|---|---|
| 하루마켓 주문 API | `X-API-Key` | `.env`의 `MOCK_API_KEY` | 주문 조회, 교환 가능 여부 조회 |
| 하루마켓 집행 API | `X-API-Key` | `.env`의 `MOCK_EXEC_KEY` | 환불 집행, 교환 발송 집행 |

## 2. 공통 요청 형식

```text
POST /orders/{order_id}/refund
POST /orders/{order_id}/exchange
X-API-Key: <MOCK_EXEC_KEY 값>
Content-Type: application/json
```

| 위치 | 이름 | 필수 | 형식 | 설명 |
|---|---|---|---|---|
| 경로 | `order_id` | 예 | `O-` 뒤 숫자 네 자리 | 집행 대상 주문번호 |
| 헤더 | `X-API-Key` | 예 | 문자열 | 집행 키 |
| 본문 | `request_id` | 예 | `APV-` 뒤 숫자 네 자리 이상 | 요청 식별자. 이 실습에서는 승인 번호를 그대로 쓴다 |
| 본문 | `amount` | 환불만 | 0보다 큰 정수 | 환불 금액(원). 주문 금액보다 클 수 없다 |
| 본문 | `option` | 교환만 | 문자열 | 보낼 옵션. 예: `블루/L` |

## 3. 요청 식별자와 중복 집행

서버는 처리한 `request_id`와 그때의 집행 결과를 기억해 둔다. **같은 `request_id`로 다시 오면 새로 집행하지 않고 처음 결과를 그대로 돌려준다.** 응답의 `repeated`가 `true`로 바뀌는 것만 다르다.

| 보낸 값 | 서버가 하는 일 | 응답의 `repeated` |
|---|---|---|
| 처음 보는 `request_id` | 집행하고 결과를 저장한다 | `false` |
| 이미 처리한 `request_id`, 같은 주문·같은 작업 | 집행하지 않고 저장한 결과를 돌려준다 | `true` |
| 이미 처리한 `request_id`, 다른 주문이거나 다른 작업 | 409 `REQUEST_ID_CONFLICT`를 돌려준다 | — |

기억한 내용은 파일에 남으므로 컨테이너를 다시 시작해도 사라지지 않는다. 6장은 승인 한 건에 식별자 하나를 발급해 보내는 데까지 다루고, 집행이 실패해 다시 보낼 때 같은 식별자를 쓰는 규칙은 8장에서 다룬다.

## 4. 환불 집행

```text
POST /orders/{order_id}/refund
```

**요청 본문 예시**

```json
{
  "request_id": "APV-1001",
  "amount": 33000
}
```

**성공 응답의 필드**(200)

| 필드 | 데이터 타입 | 설명 |
|---|---|---|
| `request_id` | 문자열 | 보낸 요청 식별자를 그대로 돌려준다 |
| `order_id` | 문자열 | 주문번호 |
| `action` | 문자열 | `refund` |
| `execution_id` | 문자열 | 서버가 매긴 집행 번호. `RFD-` 뒤 네 자리다 |
| `amount` | 숫자(정수) | 집행한 환불 금액 |
| `executed_at` | 문자열(날짜시각) | 처음 집행한 시각. 반복 요청일 때도 처음 집행 시각이다 |
| `repeated` | 참거짓 | 이 응답이 처음 집행의 결과인지(`false`), 이미 집행한 것을 다시 돌려준 것인지(`true`) |

**응답 예시**(주문 O-1004, 결제 금액 39,000원, 배송비 6,000원을 뺀 33,000원 환불)

```json
{
  "request_id": "APV-1001",
  "order_id": "O-1004",
  "action": "refund",
  "executed_at": "2026-09-20T16:21:57+09:00",
  "repeated": false,
  "execution_id": "RFD-0001",
  "amount": 33000
}
```

같은 요청을 한 번 더 보냈을 때의 응답이다. `execution_id`와 `executed_at`이 같고 `repeated`만 달라진다.

```json
{
  "request_id": "APV-1001",
  "order_id": "O-1004",
  "action": "refund",
  "executed_at": "2026-09-20T16:21:57+09:00",
  "repeated": true,
  "execution_id": "RFD-0001",
  "amount": 33000
}
```

## 5. 교환 발송 집행

```text
POST /orders/{order_id}/exchange
```

**요청 본문 예시**

```json
{
  "request_id": "APV-1002",
  "option": "블루/L"
}
```

**성공 응답**(200)

```json
{
  "request_id": "APV-1002",
  "order_id": "O-2001",
  "action": "exchange",
  "executed_at": "2026-09-20T16:21:57+09:00",
  "repeated": false,
  "execution_id": "EXG-0001",
  "option": "블루/L"
}
```

필드의 뜻은 환불과 같다. `amount` 대신 `option`이 들어가고 `execution_id`의 앞자리가 `EXG-`다.

**이 요청은 재고를 확인하지 않는다.** 보낼 수 있는 옵션인지 판단하는 일은 워크플로우가 교환 가능 여부 조회(4장 명세 5절)로 먼저 해야 한다. 서버는 승인받은 집행을 그대로 수행할 뿐이다. 조회 시점과 집행 시점 사이에 재고가 달라질 수 있다는 문제는 실습 6-5에서 다룬다.

## 6. 오류 응답

형식은 4장 명세 3절과 같다.

| 상태 코드 | `error.code` | 뜻 | 요청한 쪽이 할 일 |
|---|---|---|---|
| 400 | `INVALID_ORDER_ID` | 주문번호가 `O-` 뒤 숫자 네 자리가 아니다 | 요청을 고친다 |
| 400 | `INVALID_BODY` | 본문이 JSON 객체가 아니다 | 본문과 `Content-Type`을 확인한다 |
| 400 | `INVALID_REQUEST_ID` | `request_id`가 없거나 `APV-` 뒤 숫자 네 자리 이상이 아니다 | 승인 번호를 확인한다 |
| 400 | `INVALID_AMOUNT` | `amount`가 0보다 큰 정수가 아니다 | 금액 계산을 확인한다 |
| 400 | `AMOUNT_TOO_LARGE` | 환불 금액이 주문 금액보다 크다 | 금액 계산을 확인한다. 다시 보내도 결과는 같다 |
| 400 | `OPTION_REQUIRED` | 교환 집행에 `option`이 없거나 비어 있다 | 승인받은 옵션을 넣는다 |
| 401 | `INVALID_API_KEY` | 키가 없거나 둘 중 어느 키도 아니다 | 자격 증명을 확인한다 |
| 403 | `FORBIDDEN` | 조회 키로 집행을 요청했다 | 집행 키 자격 증명을 연결한다. 다시 보내도 결과는 같다 |
| 404 | `ORDER_NOT_FOUND` | 그런 주문이 없다 | 주문번호를 확인한다 |
| 404 | `NOT_FOUND` | 없는 경로다 | 주소를 고친다 |
| 409 | `REQUEST_ID_CONFLICT` | 같은 `request_id`가 다른 주문이나 다른 작업에 이미 쓰였다 | 승인 번호를 다시 확인한다 |

**403과 401을 나눈 이유가 있다.** 401은 "당신이 누구인지 모르겠다", 403은 "누구인지는 알겠는데 이 일을 할 권한이 없다"는 뜻이다. 조회 키로 집행을 부르면 403이 나오는 것이 설계가 막고 있다는 신호다. 실습 6-4에서 이 응답을 직접 확인한다.

## 7. 상태 확인

```text
GET /health
```

키 없이 부를 수 있다. 서버가 살아 있는지와 지금까지 기억한 집행 건수를 돌려준다.

```json
{"status": "ok", "as_of": "2026-09-10", "executions": 2}
```

`executions`는 서버가 기억하는 `request_id`의 개수다. 집행 요청을 보낸 뒤 이 값이 늘어나지 않았다면 집행이 되지 않은 것이다.

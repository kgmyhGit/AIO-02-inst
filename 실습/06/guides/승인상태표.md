# 승인 상태표

> 실습 6-3과 6-5에서 요청 기록을 확인할 때 옆에 두고 보는 표다. 어느 상태에서 무슨 일이 일어나야 하는지를 한 장에 모았다.
> 전이 번호(T10~T22)는 2장 실습의 전이표를 가리킨다.

## 1. 지금 이 요청은 어디에 있는가

| `request_status` | `approval_status` | 뜻 | 다음에 일어날 일 | 기다리는 것 |
|---|---|---|---|---|
| `received` | (비어 있음) | 접수만 되었다 | 판단과 정책 검사 | 판단 워크플로우 실행 |
| `under_review` | 여러 값 | 담당자가 봐야 한다 | 담당자 처리(T17, T18) | 사람 |
| `pending_approval` | `pending` | 승인 요청을 보냈다 | 승인(T13), 거절(T14), 알림(T15), 만료(T16) | 담당자 응답 또는 기한 |
| `pickup_requested` | `approved` | 승인받아 회수를 요청했다 | 회수 완료 통지(T19) | 택배사 |
| `inspecting` | `approved` | 상품이 돌아와 검수 중이다 | 검수 통과 후 재검증과 환불 집행(T20) | 창고 |
| `closed` | `approved` 또는 비어 있음 | 끝났다 | 없다 | 없다 |

**`approval_status`가 `approved`인데 `request_status`가 `closed`가 아닌 상태가 정상이다.** 승인은 받았지만 아직 집행하지 않은 구간이 있기 때문이다. 하루마켓에서는 회수와 검수가 그 구간이다.

## 2. 값이 이렇게 남아 있어야 한다

| 시점 | 반드시 채워져 있어야 하는 값 | 아직 비어 있어야 하는 값 |
|---|---|---|
| 승인 요청을 보낸 직후 | `approval_status`=`pending`, `approval_due_at`, `evidence`, `reply_draft` | `approval_id`, `approval_decided_at`, `execution_id` |
| 승인을 기록한 직후 | `approval_id`, `approval_status`=`approved`, `approval_decided_at`, `approved_refund_amount`(교환은 `approved_option`, `approved_shipping_fee`) | `execution_id`, `executed_at` |
| 거절을 기록한 직후 | `approval_status`=`rejected`, `approval_decided_at`, `approval_note`, `handover_reason`=`approval_rejected` | `approval_id`, `execution_id` |
| 팀장에게 알린 직후 | `lead_notified_at` | 나머지는 그대로 |
| 만료 처리 직후 | `approval_status`=`expired`, `handover_reason`=`approval_expired` | `approval_id`, `execution_id` |
| 환불을 집행한 직후 | `execution_id`, `executed_at`, `request_status`=`closed`, `close_reason`=`completed` | 없다 |

`approval_id`는 **승인을 기록하는 순간에만** 발급한다. 거절과 만료에는 발급하지 않는다. 승인 번호는 집행 요청의 식별자로 쓰이므로, 집행하지 않을 건에 번호를 매기면 번호와 집행이 일대일로 묶이지 않는다.

## 3. 이런 상태는 잘못된 것이다

확인 질의로 찾아내야 할 어긋남이다. 실습 6-3의 확인 단계에서 쓴다.

| 어긋난 상태 | 무엇이 잘못되었는가 | 어디를 보아야 하는가 |
|---|---|---|
| `approval_status`가 `approved`인데 `approval_id`가 비어 있다 | 승인 번호를 발급하지 않았다. 집행 요청을 보낼 수 없다 | 승인 응답 수신 워크플로우의 기록 노드 |
| `approval_status`가 `approved`인데 `approved_refund_amount`가 비어 있다 | 승인한 대상을 복사해 두지 않았다. 재검증을 할 수 없다 | 같은 노드 |
| `execution_id`가 있는데 `approval_status`가 `approved`가 아니다 | 승인 없이 집행되었다 | 집행 워크플로우의 상태 검사 |
| 같은 `approval_id`가 두 요청에 있다 | 승인 번호가 중복 발급되었다 | 발급 방식(`approval_no_seq`를 쓰고 있는가) |
| `request_status`가 `pending_approval`인데 `approval_due_at`이 비어 있다 | 기한을 정하지 않았다. 기한 확인 워크플로우가 이 건을 영영 찾지 못한다 | 승인 요청 발송 노드 |
| `lead_notified_at`이 있는데 여러 번 알림 메일이 와 있다 | 알림을 보낸 뒤 기록하지 않았거나, 조회 조건에 `lead_notified_at IS NULL`이 빠졌다 | 기한 확인 워크플로우의 조회 조건 |
| `request_status`가 `closed`인데 `execution_id`가 비어 있다 | 환불하지 않고 종결했다. `close_reason`이 `not_eligible`이나 `closed_by_staff`라면 정상이다 | `close_reason` 값 |

## 4. 확인 질의

n8n의 Postgres 노드나 데이터베이스 도구에 그대로 붙여 넣어 쓴다.

지금 승인을 기다리는 건을 본다.

```sql
SELECT request_id, customer_name, approval_status, approval_due_at, lead_notified_at
FROM requests
WHERE request_status = 'pending_approval'
ORDER BY approval_due_at;
```

3절의 어긋남을 한 번에 찾는다. 결과가 한 줄도 없어야 정상이다.

```sql
SELECT request_id, '승인인데 승인 번호 없음' AS 문제
FROM requests WHERE approval_status = 'approved' AND approval_id IS NULL
UNION ALL
SELECT request_id, '승인인데 승인 금액 없음'
FROM requests WHERE approval_status = 'approved' AND approved_refund_amount IS NULL AND approved_option IS NULL
UNION ALL
SELECT request_id, '승인 없이 집행됨'
FROM requests WHERE execution_id IS NOT NULL AND approval_status IS DISTINCT FROM 'approved'
UNION ALL
SELECT request_id, '기한 없이 대기 중'
FROM requests WHERE request_status = 'pending_approval' AND approval_due_at IS NULL;
```

집행된 건과 보낸 메일을 함께 본다.

```sql
SELECT r.request_id, r.approval_id, r.execution_id, r.executed_at,
       (SELECT count(*) FROM notifications n WHERE n.request_id = r.request_id) AS 보낸메일수
FROM requests r
WHERE r.execution_id IS NOT NULL
ORDER BY r.executed_at DESC;
```

# 실행 환경 점검표

> 3장 실습 3-1에서 환경이 뜨지 않거나 이상하게 동작할 때 사용한다. 증상을 먼저 찾고, 확인할 곳을 본 뒤, 해결 방법을 적용한다.

## 먼저 볼 세 가지

무엇이 문제인지 모를 때는 아래 세 명령의 결과부터 본다. 모두 `compose.yml`이 있는 폴더에서 실행한다.

```bash
docker compose ps
```

```bash
docker compose logs n8n --tail 50
```

```bash
docker compose logs db --tail 50
```

`docker compose ps`에서 두 서비스의 상태가 모두 `running`이고 `db`가 `healthy`면 컨테이너 자체는 정상이다.

## 증상별 점검

### 컨테이너가 뜨지 않는다

| 증상 | 확인할 곳 | 해결 |
|---|---|---|
| `cannot connect to the Docker daemon` 같은 메시지가 나온다 | Docker Desktop이 실행 중인지 | Docker Desktop을 실행하고 고래 모양 아이콘이 준비 상태가 될 때까지 기다린 뒤 다시 실행한다 |
| `port is already allocated` 또는 `bind: address already in use` | 5678 포트를 다른 프로그램이 쓰고 있다 | `compose.yml`의 `ports`에서 왼쪽 숫자만 바꾼다(예: `"15678:5678"`). 접속 주소도 그 번호로 바꾼다 |
| `variable is not set` 경고가 여러 줄 나온다 | `.env` 파일이 `compose.yml`과 같은 폴더에 있는지, 이름이 정확히 `.env`인지 | 파일 이름을 확인한다. 편집기가 `.env.txt`로 저장했을 수 있다 |
| `db` 서비스가 계속 다시 시작된다 | `docker compose logs db` | 비밀번호에 특수문자가 섞여 있으면 영문자와 숫자로만 바꾼 뒤, 볼륨까지 지우고 다시 만든다 |
| 컨테이너가 뜨다 멈춘다 | Docker Desktop의 자원 설정 | 메모리를 4GB 이상으로 올린다 |

### 화면이 열리지 않는다

| 증상 | 확인할 곳 | 해결 |
|---|---|---|
| 브라우저에서 연결이 거부된다 | `docker compose ps`의 상태 | `n8n`이 `running`이 될 때까지 기다린다. 처음 실행은 시간이 걸린다 |
| 계속 로딩만 된다 | `docker compose logs n8n` | 데이터베이스 연결 오류가 있으면 아래 항목을 본다 |
| 포트를 바꿨는데 안 열린다 | 주소의 포트 번호 | `http://localhost:15678`처럼 바꾼 번호로 접속한다 |

### 공개 주소로 접속되지 않는다

| 증상 | 확인할 곳 | 해결 |
|---|---|---|
| `ngrok` 명령을 찾을 수 없다 | 설치 여부, 터미널을 언제 열었는지 | 설치를 확인하고 터미널을 새로 연다 |
| ngrok이 인증 오류를 표시한다 | authtoken 등록 여부 | authtoken을 다시 복사해 `ngrok config add-authtoken`을 실행한다 |
| 공개 주소에서 ngrok 오류 페이지가 나온다 | `ngrok http 5678`을 실행한 터미널, `docker compose ps` | 터널을 열고 n8n이 실행 중인지 확인한다. `compose.yml`에서 포트를 바꿨다면 `ngrok http` 뒤의 번호와 `N8N_EDITOR_BASE_URL`의 번호를 왼쪽 숫자로 바꾼다 |
| 공개 주소에서 경고 페이지가 나온다 | 무료 플랜의 정상 동작이다 | `Visit`을 누른다 |
| `Webhook` 노드의 주소가 `localhost`로 시작한다 | `.env`의 `N8N_WEBHOOK_URL` | 값을 고치고 `docker compose up -d`를 다시 실행한다. 환경 변수는 컨테이너를 다시 만들어야 적용된다 |

### 데이터베이스에 연결되지 않는다

| 증상 | 확인할 곳 | 해결 |
|---|---|---|
| n8n 로그에 `ECONNREFUSED` 또는 데이터베이스 연결 실패가 보인다 | `compose.yml`의 `DB_POSTGRESDB_HOST` 값 | 값이 `db`여야 한다. `localhost`로 두면 컨테이너가 자기 자신을 가리킨다 |
| 자격 증명 화면에서 연결 시험이 실패한다 | 자격 증명의 Host 칸 | 여기도 `localhost`가 아니라 `db`다. 컨테이너끼리는 서비스 이름으로 찾는다 |
| 비밀번호가 틀렸다고 나온다 | `.env`의 `POSTGRES_PASSWORD` | `.env` 값과 자격 증명에 넣은 값이 같은지 본다. 값 앞뒤의 공백과 따옴표를 지운다 |
| `harumarket` 데이터베이스가 없다고 나온다 | 초기화 스크립트 실행 여부 | 아래 '초기화 스크립트' 항목을 본다 |
| `n8n_exam` 데이터베이스가 없다고 나온다 | 예제DB 초기화 스크립트 실행 여부 | 아래 '초기화 스크립트' 항목의 데이터베이스 추가 명령을 실행한다 |

### 초기화 스크립트가 실행되지 않았다

`업무DB_초기화.sql`은 **데이터베이스 볼륨이 비어 있을 때 한 번만** 실행된다. 이미 한 번 실행한 뒤에 스크립트를 고치거나 추가해도 다시 실행되지 않는다. `예제DB_초기화.sql`도 같다.

예제용 `n8n_exam` 데이터베이스만 없다면 볼륨을 지울 필요가 없다. `compose.yml`이 있는 폴더에서 아래 명령을 한 번 실행한다. `<사용자>`는 `.env`의 `POSTGRES_USER` 값으로 바꾼다. 이 명령은 기존 워크플로우와 자격 증명을 지우지 않는다.

```bash
docker compose exec db psql -U <사용자> -d n8n -c "CREATE DATABASE n8n_exam;"
```

처음부터 다시 만들려면 아래 명령으로 컨테이너와 볼륨을 함께 지운다. **이 명령은 지금까지 만든 워크플로우와 자격 증명도 함께 지운다.**

```bash
docker compose down -v
```

```bash
docker compose up -d
```

### 시각이 맞지 않는다

| 증상 | 확인할 곳 | 해결 |
|---|---|---|
| 표현식의 현재 시각이 한국 시간이 아니다 | `.env`의 `TIMEZONE` 값 | `Asia/Seoul`인지 확인하고 `docker compose up -d`로 다시 만든다 |
| 값을 고쳤는데 그대로다 | 컨테이너 재생성 여부 | 환경 변수는 컨테이너를 다시 만들어야 적용된다. `docker compose up -d`를 다시 실행한다 |

### 만든 것이 사라졌다

| 증상 | 원인 | 확인 |
|---|---|---|
| 다시 켰더니 워크플로우가 없다 | `docker compose down -v`로 볼륨까지 지웠다 | 볼륨을 지우면 복구할 수 없다. 다음부터는 `-v` 없이 `docker compose down`을 쓴다 |
| 자격 증명이 열리지 않는다 | `N8N_ENCRYPTION_KEY`가 바뀌었다 | `.env`의 키를 처음 값으로 되돌린다. 값을 잃었다면 자격 증명을 다시 만들어야 한다 |

## 되돌리기 정리

| 명령 | 사라지는 것 | 남는 것 |
|---|---|---|
| `docker compose stop` | 없음 | 전부 |
| `docker compose down` | 컨테이너 | 워크플로우, 자격 증명, 업무 데이터(볼륨에 있다) |
| `docker compose down -v` | 컨테이너와 볼륨 전부 | 없음. `compose.yml`과 `.env` 같은 파일만 남는다 |

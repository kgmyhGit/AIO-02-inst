# 3장 실습과제. 실행 환경과 데이터 흐름 읽기

# 개요

## 1. 이 실습을 통해 배울 것

이 장부터 n8n을 실제로 실행한다. 자기 컴퓨터에 n8n과 업무 데이터베이스를 실행할 환경을 만들고, 그 위에서 워크플로우를 직접 만들면서 데이터가 노드 사이를 어떻게 흐르는지 읽는 방법을 익힌다.

- 컨테이너를 내렸다 올려도 작업이 남는 실행 환경을 만들고, 그 환경에서 무엇을 지켜야 하는지 확인한다.
- 목록이 아이템으로 나뉘고 조건을 지나며 수가 바뀌는 과정을 실행 결과에서 세어 본다.
- 실제 뉴스 피드와 웹 페이지에서 기사를 읽어, 메일로 보내거나 데이터베이스에 쌓는다.
- 표기가 제각각인 값을 표현식으로 다듬어 계약에 맞는 형식으로 바꾼다.
- 요구를 검색 문장으로 바꾸어 공식 문서에서 기능을 찾고, 작은 데이터로 실행해 확인한다.
- 2장에서 문서로 정한 문의 기록 계약을 실제로 동작하는 워크플로우로 옮긴다.

## 2. 실습 목차

| 실습 이름 | 종류 | 실습으로 익힐 것 |
|---|---|---|
| 3-1 n8n과 업무 데이터베이스 실행 환경 준비 | 공통 준비 | 설치 방식 비교, 영속 저장, 암호화 키, 시간대, 자격 증명, 두 데이터베이스의 구분 |
| 3-2 뉴스 키워드 필터링 | 주제 실습(개인) | 트리거, 필드 참조, 아이템 수가 바뀌는 지점 |
| 3-3 주식 뉴스 RSS 메일 받기 | 주제 실습(개인) | 피드 읽기, 아이템 수 줄이기와 묶기, 외부 서비스 자격 증명 |
| 3-4 지출 내역 정리 | 주제 실습(업무) | 데이터 타입과 형식 변환, 규칙 분기, 실행 결과 읽기 |
| 3-5 Daum 경제 뉴스 수집과 저장 | 주제 실습(업무) | 페이지에서 값 뽑기, 한 건씩 반복, 데이터베이스에 저장 |
| 3-6 웹 문의 정규화와 유형 분기 | 누적 프로젝트(함께하는 실습) | 기능 탐색, 필수 값 검사, 계약 형식으로 정규화 |
| 3-7 메일 채널 교환·취소 문의 정규화 | 누적 프로젝트(스스로 하는 실습) | 같은 계약으로 정규화, 필드 변경·누락·복수 입력 시험 |

실습 3-1을 먼저 끝내야 나머지를 할 수 있다. 3-2~3-5는 서로 독립이므로 어느 것을 먼저 해도 된다. 다만 3-3은 3-2에서 하지 않은 수집과 발송을 다루므로 3-2 뒤에 하면 이어서 이해하기 쉽다. 3-6과 3-7은 2장의 하루마켓 설계를 이어받는다.

## 3. 공통사항

**진행 방식**

실습의 단계별 진행은 수업에서 강사와 함께 한다. 이 문서의 "해야 할 것"에는 실습마다 해야 할 작업과 주의할 점만 적었다. 스스로 하는 실습(3-7)은 이 문서와 제공 파일만 보고 주어진 시간 동안 먼저 직접 해 본다. 시간이 끝나면 강사가 예시 답안을 보여 주며 왜 그렇게 되는지 설명한다. 자신의 결과물은 고치기 전 상태로 남겨 두고, 풀이와 비교해 다른 부분을 표시한다. 예시 답안과 달라도 이유가 맞으면 성립하는 답이 있으므로, 다른 점마다 자신의 이유를 적어 둔다.

**필요한 것**

- Docker Desktop 또는 Docker Engine과 Docker Compose가 필요하다. 설치는 각 운영체제의 공식 안내를 따른다. 회사 노트북에서 컨테이너 실행이 막혀 있으면 강사가 안내하는 대체 환경을 사용한다.
- 메모리 4GB 이상, 비어 있는 디스크 5GB 이상, 최신 브라우저, 텍스트 편집기가 필요하다.
- 외부 서비스 계정이 세 가지 필요하다. 모두 무료로 쓴다.
    - ngrok: 외부 서비스가 n8n을 호출할 수 있도록 공개 HTTPS 주소를 받는 데 쓴다(3-1, 3-6).
    - Google 계정과 Google Cloud 프로젝트: Gmail로 메일을 보내는 자격 증명을 만드는 데 쓴다(3-3). 결제 수단은 필요하지 않다.
    - Discord 계정과 서버: 채널에 알림을 보내는 웹후크를 만드는 데 쓴다(3-5).
- LLM API 키는 필요하지 않다.

**결과물 저장**

- 작업 폴더에 `03/` 폴더를 만들고 결과물을 저장한다.
- 워크플로우는 n8n 편집 화면에서 JSON 파일로 내보내 저장한다. 이 파일들은 10장에서 Git으로 관리한다.
- `.env` 파일에는 비밀번호와 암호화 키가 들어 있다. 다른 사람과 공유하지 않고 저장소에도 올리지 않는다.

**모든 실습에 적용하는 기준**

| 항목 | 기준 |
|---|---|
| 시간대 | `Asia/Seoul`. 모든 시각은 `+09:00`이 포함된 ISO 8601로 적는다 |
| 접속 주소 | `http://localhost:5678`. 포트를 바꿔 실행했다면 그 번호로 읽는다 |
| 공개 주소 | `.env`의 `N8N_WEBHOOK_URL`에 적은 ngrok 주소. `Webhook` 노드의 주소가 이 값으로 시작한다. 편집 화면에는 계속 `localhost`로 접속한다 |
| LLM | 이 장에서는 쓰지 않는다. 모든 처리를 규칙으로 한다 |
| 요청 유형 | 3장의 분기는 경로만 나눈다. 2장 계약의 `detected_type`과 `request_type` 값은 이 장에서 확정하지 않는다 |
| 노드 이름 | 이 문서와 노드 설정 파일에 적힌 이름을 그대로 붙인다. 표현식에서 이름으로 참조할 수 있기 때문이다 |
| 데이터 | 제공하는 샘플은 모두 실습용 가상 데이터다 |

# 3-1 - n8n과 업무 데이터베이스 실행 환경 준비

## 1. 실습 주제 및 상황

앞으로 만들 모든 워크플로우는 자기 컴퓨터에서 실행하는 n8n 위에서 동작한다. 강사가 제공한 구성 파일로 n8n과 PostgreSQL을 함께 실행하고, 이 환경이 작업을 잃지 않고 안전하게 유지되는지 직접 확인한다.

## 2. 이 실습의 목적

- 영속 저장, 암호화 키, 시간대, 자격 증명이 이 환경의 어디에서 지켜지는지 확인한다.
- n8n이 자기 정보를 저장하는 내부 저장 데이터베이스와 업무 데이터를 저장하는 업무 데이터베이스가 서로 다르다는 것을 눈으로 확인한다.
- 설치 방식을 업무 조건으로 비교하고 선택 근거를 설명한다.
- 외부 서비스가 내 컴퓨터의 n8n을 호출할 수 있도록 공개 HTTPS 주소를 준비한다.

관련 이론: [3.1 n8n을 어디에서 실행할 것인가](../../../03_실행환경과데이터흐름읽기.md#31-n8n을-어디에서-실행할-것인가), [3.2 실행 환경이 지켜야 하는 것](../../../03_실행환경과데이터흐름읽기.md#32-실행-환경이-지켜야-하는-것), [부록 D. ngrok으로 공개 HTTPS 주소 만들기](../../../부록D_ngrok으로공개주소만들기.md)

## 3. 관련 파일

- [`env/compose.yml`](env/compose.yml): n8n과 PostgreSQL 실행 구성
- [`env/환경변수_예시.env`](env/환경변수_예시.env): 환경 변수 자리표시자(Placeholder) 샘플. (`.env`로 변환)
- [`env/업무DB_초기화.sql`](env/업무DB_초기화.sql): 업무 데이터베이스와 문의·요청 기록 테이블 생성
- [`env/예제DB_초기화.sql`](env/예제DB_초기화.sql): 워크플로우 예제의 DB 연동 연습에 쓰는 `n8n_exam` 데이터베이스 생성
- [`guides/환경점검표.md`](guides/환경점검표.md): 증상별 확인 위치와 해결 방법

## 4. 결과물

- 다음 상태가 되어 있어야 한다.
    - `docker compose ps`에서 `db`와 `n8n` 두 서비스가 실행 중이다.
    - 브라우저에서 편집 화면이 열리고 워크플로우를 저장할 수 있다.
    - `$now` 값이 `+09:00`으로 끝난다.
    - `하루마켓 업무 DB` 자격 증명으로 `inquiries` 테이블을 조회할 수 있다.
    - 컨테이너를 내렸다 올린 뒤에도 워크플로우와 자격 증명이 남아 있다.
    - 공개 주소를 브라우저에서 열면 경고 페이지 뒤에 n8n 로그인 페이지가 나온다.

## 5. 해야 할 것

막히면 [`guides/환경점검표.md`](guides/환경점검표.md)를 먼저 본다.

**해야 할 작업**

- [ngrok](https://ngrok.com) 무료 계정을 만들고 authtoken을 등록해, 외부에서 n8n을 호출할 공개 HTTPS 주소를 받는다.
- `compose.yml`을 읽고 볼륨, 시간대, 데이터베이스 주소를 정하는 줄을 찾는다.
- 작업 폴더의 `03/`에 제공 파일 세 개를 복사하고, `환경변수_예시.env`를 `.env`로 복사해 `POSTGRES_PASSWORD`, `N8N_WEBHOOK_URL`, `N8N_ENCRYPTION_KEY` 세 값을 채운다.
- 컨테이너를 올려 `db`와 `n8n` 두 서비스가 실행 중인지 확인하고, 편집 화면에서 소유자 계정을 만든다.
- `$now` 값을 출력해 시간대가 `+09:00`인지 확인한다.
- `Postgres` 노드에 `하루마켓 업무 DB` 자격 증명을 만들어 `inquiries` 테이블을 조회한다.
- 컨테이너를 내렸다 올린 뒤 로그인 정보, 워크플로우, 자격 증명이 남아 있는지 확인한다.

**주의할 점**

- authtoken과 `.env`에 적은 값은 비밀번호처럼 관리하고 다른 사람과 공유하지 않는다.
- 편집기가 `.env`를 `.env.txt`로 저장하지 않았는지 확인한다.
- `N8N_WEBHOOK_URL`에는 공개 주소 끝에 `/`를 붙여 적는다. ngrok을 쓸 수 없으면 강사에게 알리고 `http://localhost:5678/`로 둔다.
- `N8N_ENCRYPTION_KEY`는 한 번 정한 뒤에는 바꾸지 않는다.
- 소유자 계정은 내 컴퓨터의 n8n에만 저장되며 외부 서비스 가입이 아니다. 다만 로그인 페이지가 공개 주소로도 열리므로, 다른 서비스에 쓰지 않는 긴 비밀번호를 정한다. 비밀번호를 잊으면 환경을 다시 만들어야 한다.
- 업무 데이터베이스 자격 증명의 Host는 `localhost`가 아니라 `db`로 적는다. User와 Password는 `.env`의 값을 쓴다.
- `docker compose down -v`는 볼륨까지 지워 되돌릴 수 없다. 환경을 처음부터 다시 만들 때만 쓴다.
- 실습을 마치면 `Ctrl+C`로 ngrok 터널을 닫는다.

# 3-2 - 뉴스 키워드 필터링

## 1. 실습 주제 및 상황

매일 아침 수집된 뉴스기사 목록을 받아, 관심 있는 키워드(`AI`)가 들어간 기사만 골라 확인하려고 한다. 기사 목록은 기사 여러 건이 한 덩어리로 들어오므로 기사 한 건씩 나누어 검사해야 한다. 제공한 기사 목록에는 다음과 같은 문제가 있어서, 단순하게 고르면 결과가 틀리게 나온다.

- 키워드가 제목에 있는 기사도 있고 요약에만 있는 기사도 있다. 그래서 제목과 요약을 모두 검사해야 한다.
- 키워드를 대문자로 쓴 기사와 소문자로 쓴 기사가 섞여 있다. 그래서 대소문자를 구분하지 않고 검사해야 한다.
- 같은 기사가 두 번 들어 있다. 어떤 필드를 기준으로 같은 기사로 볼지 정해서 한 건만 남겨야 한다.
- 기사마다 아침에 읽을 때 필요 없는 필드도 들어 있다. 그래서 제목, 발행 시각, 출처만 남겨야 한다.

이 실습의 목표는 매일 7시에 실행되어, 키워드가 들어간 기사를 중복 없이 제목·발행 시각·출처만 담은 목록으로 만드는 워크플로우를 완성하는 것이다. 키워드가 들어 있는지만 보고 고르면 관련 없는 기사가 섞일 수 있다. 이 문제는 이 실습에서 고치지 않고, 결과를 직접 읽어 찾아낸 뒤 그 이유를 메모로 남긴다. 발행 시각의 표기가 기사마다 다른 점도 확인만 하고 맞추지는 않는다.

다음 작업은 이 실습에서 하지 않는다.

- 실제 기사 수집: 실습 3-3에서 다룬다. 이 실습은 제공한 샘플 8건을 넣어 시작한다. 수집 단계를 뺐을 뿐 그 뒤의 처리는 실제와 같다.
- 만든 목록을 메신저나 메일로 보내는 일
- 어제 확인한 기사를 오늘 목록에서 빼는 일: 이 실습의 중복 제거는 한 번의 실행 안에서만 한다.

## 2. 이 실습의 목적

- 목록 하나가 아이템 여러 개로 나뉘는 지점과 조건을 지나며 아이템 수가 줄어드는 지점을 실행 결과에서 확인한다.
- 건수가 아니라 내용을 보고 결과가 맞는지 판단하는 습관을 익힌다.

관련 이론: [3.3 노드 사이를 흐르는 데이터: 아이템](../../../03_실행환경과데이터흐름읽기.md#33-노드-사이를-흐르는-데이터-아이템), [3.4 필드 참조와 표현식](../../../03_실행환경과데이터흐름읽기.md#34-필드-참조와-표현식)

## 3. 관련 파일

- [`data/뉴스항목_샘플.json`](data/뉴스항목_샘플.json): 뉴스기사 샘플 8건이 `articles` 배열에 들어 있는 목록

## 4. 결과물

- `03_뉴스필터.json`: 내보낸(export) n8n 워크플로우
- 마지막 노드의 출력에 키워드와 관련된 기사만 중복 없이 남아 있고, 필드는 `title`, `published_at`, `source` 세 개다.
- 노드마다 출력 아이템 수를 적은 메모와, 결과에 잘못 들어온 기사가 있다면 그 이유를 적은 메모

## 5. 해야 할 것

**해야 할 작업**

- `Schedule Trigger`로 매일 7시에 시작하는 워크플로우를 만들고, 샘플 목록을 넣는다. 만드는 동안에는 편집 화면에서 직접 실행한다.
- 목록을 기사 한 건씩의 아이템으로 나눈다.
- 제목 또는 요약에 `AI`가 들어 있는 기사만 남긴다.
- 같은 기사를 한 건으로 줄인다.
- `title`, `published_at`, `source` 세 필드만 남긴다.
- 노드를 하나 붙일 때마다 실행하고 출력 아이템 수를 적어 둔다.
- 워크플로우를 `03_뉴스필터.json`으로 내보낸다.

**주의할 점**

- 목록을 나누기 전에는 기사 8건이 아이템 하나 안에 들어 있다. 나누기 전에 키워드로 거르면 어떤 결과가 나오는지 확인해 본다.
- 나눈 뒤에는 기사 필드의 위치가 바뀐다. 표현식을 적기 전에 출력에서 필드가 어디에 있는지 확인한다.
- 대소문자를 구분하는지에 따라 통과하는 기사가 달라진다. 설정을 바꿔 결과를 비교해 본다.
- 아이템 수가 맞아도 통과한 기사를 하나씩 읽어 정말 키워드와 관련된 기사인지 확인한다. 관련 없는 기사가 있으면 왜 통과했는지 찾아 메모로 남긴다.
- 무엇을 기준으로 같은 기사로 볼지는 샘플을 보고 정한다. 다른 필드를 기준으로 바꾸었을 때 결과가 어떻게 달라지는지도 비교한다.
- 결과의 `published_at` 표기가 모두 같은지 확인한다.

## 6. 이어서 더 해 볼 만한 주제



**중고 거래 글에서 관심 품목과 가격 범위 고르기.** 품목명, 가격, 지역, 작성 시각이 있는 거래 글 10건을 직접 만든다. 목록을 아이템으로 나누고, 품목명 키워드와 가격 범위 두 조건으로 걸러 내고, 같은 글을 없앤다. 가격이 `"35만원"`처럼 문자열이면 3-4의 변환을 먼저 해야 한다. 나눌 필드의 이름과 조건만 달라지고 흐름은 같다.

**사내 공지에서 우리 부서 관련 항목만 모으기.** 공지 제목, 대상 부서, 본문이 있는 목록을 만든다. 대상 부서가 비어 있는 공지와 '전 직원' 공지를 어떻게 처리할지 먼저 정하고 조건으로 옮긴다. 조건에 걸리지 않아 사라지는 공지 가운데 놓치면 안 되는 것이 있는지 확인한다.

# 3-3 - 주식 뉴스 RSS 메일 받기

## 1. 실습 주제 및 상황

매일 아침 주식 관련 뉴스를 몇 건만 골라 메일로 받아 보려고 한다. 3-2에서는 기사 목록을 제공 파일로 넣었고, 결과를 어디로 보내지도 않았다. 이번에는 Google 뉴스가 공개하는 RSS 피드에서 실제 기사를 읽고, 고른 기사를 메일 한 통으로 보낸다.

- 기사는 Google 뉴스에서 "주식"으로 검색한 RSS 피드(`https://news.google.com/rss/search?q=주식&hl=ko&gl=KR&ceid=KR:ko`)에서 읽는다. 피드 하나에 기사가 100건 안팎 들어 있다.
- 메일에는 피드의 앞에서부터 5건만 넣는다. 기사마다 제목, 발행 시각, 링크를 적는다.
- 발행 시각은 이 장의 시간대 기준(`+09:00`)에 맞춘다.
- 메일은 매일 6시에 본인 Gmail로 한 통만 보낸다.

이 실습의 목표는 매일 6시에 실행되어, 주식 뉴스 5건을 담은 메일 한 통을 본인에게 보내는 워크플로우를 완성하는 것이다.

다음 작업은 이 실습에서 하지 않는다.

- 기사 내용을 읽고 관련 있는 기사만 고르는 일: 피드가 준 순서대로 앞의 5건을 쓴다.
- 어제 보낸 기사를 오늘 메일에서 빼는 일

## 2. 이 실습의 목적

- 피드를 읽는 노드가 기사마다 아이템을 만들고, 아이템 수를 줄이고, 여러 아이템을 하나로 묶는 지점을 실행 결과에서 확인한다.
- 묶은 배열을 표현식으로 메일 본문 하나로 만든다.
- 비밀번호 대신 로그인 허락을 받는 방식(OAuth2)의 자격 증명을 만들어 본다.

관련 이론: [3.3 노드 사이를 흐르는 데이터: 아이템](../../../03_실행환경과데이터흐름읽기.md#33-노드-사이를-흐르는-데이터-아이템), [3.4 필드 참조와 표현식](../../../03_실행환경과데이터흐름읽기.md#34-필드-참조와-표현식)

## 3. 관련 파일

- [`guides/외부서비스_연결안내.md`](guides/외부서비스_연결안내.md): 1절 RSS 피드의 구성, 2절 Gmail 자격 증명을 만드는 절차와 자주 만나는 오류

## 4. 결과물

- `03_주식뉴스메일.json`: 내보낸 워크플로우. Client Secret이 들어 있지 않아야 한다.
- 본인 받은편지함에 도착한 메일 한 통. 제목에 실행한 날의 날짜가 있고, 본문에 기사 5건이 기사마다 제목, `+09:00`이 붙은 발행 시각, 링크 순서로 들어 있다.
- 노드마다 출력 아이템 수를 적은 메모

## 5. 해야 할 것

**해야 할 작업**

- 이름이 `주식 뉴스 메일`인 워크플로우를 만들고, `Schedule Trigger`로 매일 6시에 시작하게 한다. 만드는 동안에는 편집 화면에서 직접 실행한다.
- `RSS Read` 노드로 피드를 읽고, 출력에 어떤 필드가 있는지 확인한다.
- 앞에서부터 5건만 남긴다.
- 제목, 링크, 발행 시각 세 필드만 남긴다. 발행 시각은 한국 시간으로 바꾼다.
- 5건을 하나로 묶은 뒤 메일 본문을 표현식으로 만든다.
- [`외부서비스_연결안내.md`](guides/외부서비스_연결안내.md) 2절대로 Gmail 자격 증명을 만들고, `Gmail` 노드로 본인에게 메일을 보낸다. 본문 끝에 n8n 안내 문구가 붙지 않게 한다.
- 노드를 하나 붙일 때마다 실행하고 출력 아이템 수를 적어 둔다.
- 워크플로우를 `03_주식뉴스메일.json`으로 내보낸다.

**주의할 점**

- 3-2에서는 기사 목록을 아이템으로 나누어야 했다. 이번 피드의 출력은 처음부터 몇 건인지 먼저 세어 본다.
- 피드의 발행 시각 필드가 어느 시간대인지 값 끝을 보고 확인한다.
- 묶지 않고 메일 노드를 붙이면 어떻게 되는지 연결선의 아이템 수로 예상해 본다.
- 묶은 뒤에는 기사 필드의 위치가 바뀐다. 표현식을 적기 전에 묶은 결과를 JSON 보기로 확인한다.
- 제공한 샘플은 메일 제목의 날짜를 `{{ $today.format('yyyy-MM-DD') }}`로 만들었다. 이 표현식이 실제로 어떤 값을 내는지 실행해서 읽어 보고, 이상하면 이유를 찾아 고친다.
- Google 로그인에서 오류가 나면 [`외부서비스_연결안내.md`](guides/외부서비스_연결안내.md) 2.3의 표를 본다.
- 일정대로 실행되게 하려면 Publish해야 한다. 편집 화면에서 직접 실행하는 것과 무엇이 다른지 확인한다.

## 6. 이어서 더 해 볼 만한 주제

**어제 보낸 기사 빼기.** 보낸 기사의 링크를 예제 데이터베이스(`n8n_exam`)의 테이블에 남기고, 다음 실행에서 이미 보낸 링크를 빼고 5건을 고른다. 테이블에 무엇을 남겨야 같은 기사인지 알 수 있는지(링크, `guid`, 제목)를 비교하고, Google 뉴스의 링크가 같은 기사에 대해 늘 같은지 두 번 실행해 확인한다.

**피드 여러 개를 한 메일로 받기.** 검색어를 `주식`, `환율`, `금리` 세 개로 늘리고 피드마다 `RSS Read` 노드를 둔다. 세 피드에서 각각 3건씩 골라 한 메일에 검색어별 제목을 붙여 보낸다. 여러 경로를 하나로 모으는 노드를 찾아 쓰고, 같은 기사가 두 검색어에 모두 걸리면 어떻게 할지 정한다.

**자주 읽는 블로그의 새 글 모아 받기.** RSS를 제공하는 블로그 두세 곳의 피드 주소를 찾는다. 피드마다 필드가 어떻게 다른지(발행 시각이 있는지, 요약에 HTML이 섞였는지) 실행 결과로 비교하고, 같은 필드 이름으로 맞춘 뒤 일주일에 한 번 메일로 받는다.

# 3-4 - 지출 내역 정리

## 1. 실습 주제 및 상황

교육운영팀은 법인카드 한 장을 함께 쓴다. 사용 내역의 금액은 문자열이나 `"12,000원"`, `"8000"`처럼 다양한 형식으로 입력된다. 날짜 표기 형식도 세 가지가 섞여 있어, 월말 정산에서 합계가 한 번에 맞는 일이 드물다. 이런 것들을 사내 기준 문서가 정한 형식으로 내역을 정리하고, 사람이 확인해야 할 건을 따로 나누는 워크플로우를 만든다.

## 2. 이 실습의 목적

- 2장에서 계약으로 정한 값의 표기를 실제 사용용도에 맞게 변환하는 방법을 익힌다.
- `Switch` 노드의 규칙 순서와 Fallback Output이 결과에 주는 영향을 확인한다.
- 실행 결과를 앞 노드부터 차례로 읽어 잘못된 곳을 찾는다.

관련 이론: [3.4 필드 참조와 표현식](../../../03_실행환경과데이터흐름읽기.md#34-필드-참조와-표현식), [3.5 실행 결과 읽기](../../../03_실행환경과데이터흐름읽기.md#35-실행-결과-읽기)

## 3. 관련 파일

- [`data/지출내역_샘플.json`](data/지출내역_샘플.json): 법인카드 사용 내역 12건이 `entries` 배열에 들어 있는 목록
- [`guides/지출정리_기준.md`](guides/지출정리_기준.md): 정리 결과의 형식, 지출 항목 분류 규칙, 확인 기준

## 4. 결과물

- `03_지출정리.json`: 내보낸 워크플로우
- `정리 결과` 노드의 출력이 기준 문서의 형식을 만족하고, `확인 필요 표시` 노드의 출력에 사람이 볼 건과 그 이유가 값으로 남아 있다.
- 두 노드의 아이템 수를 더하면 원본 내역 수와 같다.
- `정리 결과`의 금액 합계를 직접 더해 적은 메모

## 5. 해야 할 것

**해야 할 작업**

- 기준 문서를 읽고 필드마다 데이터 타입과 형식을 확인한 뒤, 샘플에서 그 형식과 다른 값을 찾는다.
- 샘플 내역을 넣고 한 건씩의 아이템으로 나눈다.
- 금액, 사용처, 날짜의 표기를 다듬은 값을 새 필드(`amount_text`, `merchant_clean`, `used_at_iso`, `text_all`)로 만든다. `text_all`은 지출 항목 분류에 쓰도록 사용처와 메모를 합친 문장이다.
- 금액이나 사용처를 알 수 없는 건을 확인 대상으로 나눈다.
- 나머지 건으로 기준 문서 형식의 정리 결과를 만든다. 다 만든 뒤 `account` 표현식이 읽기에 어떤지, `needs_check`를 만들 때 어떤 불편이 생기는지 메모한다.
- 확인 대상 건에는 `row_id`, `needs_check`와 함께 왜 확인 대상이 되었는지를 `reason` 값으로 남긴다.
- 정리 결과를 기준 문서와 한 건씩 대조하고, 아이템 수와 금액 합계를 직접 확인한다.
- 워크플로우를 `03_지출정리.json`으로 내보낸다.

**주의할 점**

- 금액이 문자열이면 더하기가 숫자 계산이 되지 않는다. 다듬기 전에 `{{ $json.amount + 1000 }}`의 결과를 확인하고 그 이유를 설명해 본다.
- 원본 필드는 그대로 두고 다듬은 값을 새 필드로 만든다.
- 사용처가 없는 건이 들어와도 노드가 멈추지 않아야 한다.
- 날짜 표기가 세 가지 섞여 있다. 몇 건만 보지 말고 12건의 `used_at_iso`를 모두 확인한다.
- 확인 대상을 나누는 `Switch` 노드는 Options에서 Fallback Output을 Extra Output으로 둔다. 그렇지 않으면 어느 규칙에도 맞지 않는 건이 사라진다.
- 원본 필드와 다듬은 필드 중 어느 쪽을 검사할지, 금액과 사용처가 모두 빈 건은 어디로 가는지 따져 본다.
- 정리 결과의 `amount`는 숫자 타입이어야 한다. `account`는 기준 문서가 정한 검사 순서를 따르며, `$if`를 이어 쓰고 `match`로 낱말을 찾으면 한 표현식으로 적을 수 있다.
- 이상한 값이 보이면 마지막 노드가 아니라 앞 노드부터 차례로 본다.

## 6. 이어서 더 해 볼 만한 주제

**낱말과 지출 항목의 짝을 표로 옮기기.** 정리 결과를 만들며 메모한 불편을 해결해 본다. 낱말과 지출 항목의 짝을 업무 데이터베이스의 테이블이나 별도 파일로 두고, 찾아보는 구조로 바꾼다. 같은 낱말 목록을 두 곳에 적지 않아도 되는지, 지출 항목이 서른 개로 늘어나도 감당할 수 있는지 비교한다. `Switch` 경로 방식과 `$if` 방식, 표 방식의 장단점을 표로 정리한다.

**가계부 앱 내역 정리하기.** 가계부 앱이나 은행에서 내려받는 CSV와 비슷한 샘플을 20건 만든다. 수입과 지출의 부호, 금액 표기, 날짜 표기를 먼저 통일하고, 확인이 필요한 건을 나눈 뒤, 나머지를 식비·교통비·구독료 같은 항목으로 분류한다. 정기 결제처럼 사용처로 바로 정할 수 있는 건과 메모까지 봐야 하는 건을 구분해 본다.

**출장비 정산의 증빙 확인 나누기.** 출장자, 날짜, 항목, 금액, 증빙 여부가 있는 내역을 만든다. 일비 한도를 넘는 건, 증빙이 필요한데 없는 건, 출장 기간 밖의 날짜를 각각 다른 이유로 표시한다. 이유 값을 정해 두면 담당자가 실행 결과만 보고 무엇을 확인할지 알 수 있는지 살펴본다.

# 3-5 - Daum 경제 뉴스 수집과 저장

## 1. 실습 주제 및 상황

시장분석팀은 Daum 뉴스 경제 면(`https://news.daum.net/economy`)의 "경제 주요뉴스"를 매시간 모아 데이터베이스에 쌓아 두려고 한다. 모을 때마다 팀 Discord 채널에 몇 건을 저장했는지 알린다. 이 페이지에는 RSS 피드가 없어서 웹 페이지(HTML)를 받아 필요한 부분을 직접 골라내야 한다.

- 목록 페이지에는 주요뉴스가 여러 건 있다. 기사마다 기사 페이지 주소와 제목이 있다.
- 기사 본문은 기사 페이지에 따로 있다. 기사마다 페이지를 한 번씩 받아야 한다.
- 기사 페이지를 연달아 요청하지 않도록 요청 사이에 1~2초를 기다린다.
- 기사는 예제 데이터베이스 `n8n_exam`의 `daumnews` 테이블에 제목과 본문으로 저장한다. 본문은 4,000자까지만 저장한다.
- 모든 기사를 저장한 뒤 Discord 채널에 저장한 건수와 시각을 한 번 알린다.

제공하는 샘플 워크플로우는 MySQL에 저장하도록 되어 있다. 이 과정의 실행 환경은 PostgreSQL이므로 테이블과 저장 노드를 PostgreSQL에 맞게 바꾼다.

이 실습의 목표는 직접 실행하거나 매시간 실행되어, 경제 주요뉴스를 `daumnews`에 저장하고 Discord에 알림을 한 번 보내는 워크플로우를 완성하는 것이다.

다음 작업은 이 실습에서 하지 않는다.

- 이미 저장한 기사를 다시 저장하지 않게 막는 일
- 기사 본문을 요약하거나 분류하는 일

기사는 언론사의 저작물이다. 수집한 본문은 실습에서 동작을 확인하는 데만 쓰고, 다른 곳에 게시하거나 공유하지 않는다.

## 2. 이 실습의 목적

- 페이지 하나에서 여러 값을 뽑아 기사 한 건씩의 아이템으로 만드는 방법을 익힌다.
- 아이템을 한 건씩 반복 처리하는 구간과, 반복이 끝난 뒤 한 번만 하는 일을 나누어 연결한다.
- 이름으로 앞선 노드의 값을 참조해 데이터베이스에 저장한다.

관련 이론: [3.3 노드 사이를 흐르는 데이터: 아이템](../../../03_실행환경과데이터흐름읽기.md#33-노드-사이를-흐르는-데이터-아이템), [3.5 실행 결과 읽기](../../../03_실행환경과데이터흐름읽기.md#35-실행-결과-읽기), [3.6 요구에서 기능을 찾아 연결하기](../../../03_실행환경과데이터흐름읽기.md#36-요구에서-기능을-찾아-연결하기)

## 3. 관련 파일

- Discord 채널에 실행 한 번마다 알림이 한 통 도착해 있다. 알림의 건수가 저장된 행 수와 같다.

## 5. 해야 할 것

**해야 할 작업**

- 노드 설정 파일 1절대로 `예제 DB` 자격 증명을 만들고, 0절의 SQL로 `daumnews` 테이블을 만든다.
- 이름이 `Daum 경제 뉴스 수집`인 워크플로우를 만든다. `Manual Trigger`와 매시간 실행하는 `Schedule Trigger`를 둘 다 둔다.
- 목록 페이지를 받고, 페이지에서 기사 주소 배열과 제목 배열을 뽑는다.
- 두 배열을 같은 순서끼리 짝지어 기사 한 건씩의 아이템으로 만든다.
- 기사마다 한 건씩 반복하며 기사 페이지를 받고, 본문을 뽑고, `daumnews`에 저장하고, 1~2초를 기다린다.
- 반복이 끝나면 저장한 기사를 하나로 묶고, [`외부서비스_연결안내.md`](guides/외부서비스_연결안내.md) 3절대로 만든 웹후크로 Discord에 알린다.
- 직접 실행한 뒤 노드 설정 파일 4절의 SQL로 저장된 행을 확인한다.
- 워크플로우를 `03_다음경제뉴스수집.json`으로 내보낸다.

**주의할 점**

- 샘플 워크플로우는 MySQL 문법으로 테이블을 만든다. 번호를 자동으로 매기는 열과 저장 시각을 자동으로 넣는 열을 PostgreSQL에서는 어떻게 적는지 노드 설정 파일 0절과 비교해 본다.
- 샘플은 목록을 찾는 선택자로 브라우저가 복사해 준 긴 id를 썼다. 브라우저 개발자 도구에서 목록 영역의 HTML을 열어 보고, 그 id가 어떤 값인지와 이 실습의 선택자가 무엇을 기준으로 찾는지 비교해 본다.
- 값을 뽑는 노드에서 배열로 받는 설정을 켜고 끌 때 결과가 어떻게 다른지 확인한다.
- 기사로 나누는 단계에서 3-2처럼 배열을 나누는 노드를 쓰면 무엇이 부족한지 생각해 본다. 코드는 노드 설정 파일 3절에 있다.
- 저장 노드 바로 앞 노드의 출력에 제목이 있는지 확인한다. 없으면 제목이 어느 노드의 출력에 있는지 찾아 참조한다.
- Discord 알림은 실행 한 번에 한 통이어야 한다. 반복 노드의 두 출력 중 어디에 붙여야 하는지 확인한다.
- 같은 워크플로우를 두 번 실행하면 테이블이 어떻게 되는지 확인하고, 그 이유를 메모로 남긴다.
- 시험한 행을 지우려면 노드 설정 파일 0절의 `TRUNCATE` 문을 쓴다.

## 6. 이어서 더 해 볼 만한 주제

**같은 기사를 다시 저장하지 않기.** `daumnews`에 기사 주소 열을 더하고 같은 주소가 두 번 들어가지 않게 제약을 건다. 저장 노드의 동작을 "넣기"에서 "있으면 고치고 없으면 넣기"로 바꾸어 매시간 실행해도 행이 늘지 않는지 확인한다. Discord 알림의 건수가 새로 저장한 기사 수만 세도록 고친다.

**경제 면 말고 다른 면도 모으기.** IT 면이나 사회 면의 주요뉴스 영역을 개발자 도구로 찾아 선택자를 정한다. 면 이름을 열로 더하고, 면마다 반복 구간을 따로 두지 않고 한 반복 구간에서 처리할 수 있는지 시험한다.

**선택자가 깨졌을 때 알기.** 목록에서 뽑은 기사가 0건이면 저장을 건너뛰고 Discord에 "목록을 찾지 못했습니다"를 보내게 한다. 선택자를 일부러 틀리게 바꾸어 실행이 성공으로 끝나면서 아무것도 저장하지 않는 경우와, 오류로 멈추는 경우를 비교한다.

# 3-6 - 웹 문의 정규화와 유형 분기

## 5. 해야 할 것

**해야 할 작업**

- 다음 세 요구를 검색 문장으로 바꾸어 공식 문서에서 쓸 노드를 찾는다. 후보가 둘 이상이면 고르지 않은 쪽이 왜 맞지 않는지도 따져 본다.
    - 웹 양식에서 보낸 문의를 받는다.
    - 필수 값이 비어 있으면 다음으로 넘기지 않는다.
    - 요청 유형별로 경로를 나눈다.
- `Webhook` 노드로 웹 문의를 받고, 받은 데이터의 모양을 확인한다.
- 양식이 보낸 값을 다듬고, 내용과 이름이 비었는지 검사해 각각의 실패 경로로 보낸다.
- 검사를 통과한 문의를 2장 계약의 필드명과 형식으로 옮긴다.
- 주문번호가 없거나 형식이 틀린 문의를 주문번호 요청 경로로 보낸다.
- 요청 유형별로 경로를 나누고, 6건을 모두 보내 각 문의가 어느 경로에 도달하는지 확인한다.
- `configs/웹문의정규화_노드설정.md`의 빈칸과 질문을 채운다. 값이 무엇인지보다 왜 그 값이어야 하는지를 설명할 수 있어야 한다.
- 2장 계약만으로 정할 수 없었던 항목을 메모하고, 워크플로우를 `03_웹문의정규화.json`으로 내보낸다.

**주의할 점**

- 기능을 고를 때는 조건에 맞지 않는 아이템이 어디로 가는지 확인한다. 걸러진 아이템이 그냥 사라지는 기능을 고르면 "이름이 없는 문의에는 이름을 요청한다" 같은 계약의 행동을 지킬 수 없다.
- Test URL은 Listen for test event를 누를 때마다 요청을 한 번만 받는다. 같은 요청을 여러 번 쓸 때는 데이터 고정을 걸고, 다른 사례를 시험할 때는 고정을 푼다.
- 받은 값이 출력의 어디에 들어 있는지 먼저 확인하고 표현식을 적는다.
- 필드가 아예 없는 요청(W-3)도 있다. 없는 필드에 문자열 기능을 쓰면 오류 없이 빈 값이 나오므로, 값이 없을 때 무엇을 낼지 직접 정해 둔다.
- 필수 값을 검사하는 `Switch` 노드에는 어느 규칙에도 맞지 않는 아이템이 갈 출력(Fallback Output)을 둔다. 이 출력이 없으면 정상 문의가 사라진다.
- 계약의 값을 만들 수 없을 때 아무 값이나 넣지 않는다. 값이 없는 필드는 빈 문자열이 아니라 `null`로 둔다.
- 계약 형식으로 옮긴 출력에는 계약의 필드만 남기고, 다듬는 중에 만든 필드(`name_raw` 등)는 남기지 않는다.
- 낱말 포함 여부로 경로를 나누면 한 문장에 두 유형이 섞인 문의가 틀린 경로로 갈 수 있다. 사람이 문장을 읽고 판단한 유형과 실제로 도달한 경로를 비교하고, 규칙 순서를 바꾸면 해결되는지 확인한다.

## 6. 이어서 더 해 볼 만한 주제

**접수 결과를 양식에 돌려주기.** 지금은 요청을 받자마자 응답하므로 양식을 쓴 고객은 접수 결과를 알 수 없다. `Webhook` 노드의 Respond 설정을 바꾸고 `Respond to Webhook` 노드를 경로 끝에 붙여, 정상 접수와 이름 요청, 주문번호 요청마다 다른 응답을 돌려준다. 상태 코드를 무엇으로 할지 정하고, 실패 이유를 고객에게 어디까지 보여 줄지도 판단한다.

**실제 입력 화면 붙이기.** n8n의 `Form Trigger` 노드로 문의 양식을 직접 만들고 같은 뒤쪽 흐름에 연결한다. 양식의 필수 칸 설정으로 막히는 입력과 워크플로우의 검사로 걸러야 하는 입력을 구분한다. 양식이 있어도 `필수 값 확인`을 지우면 안 되는 이유를 공백만 입력한 사례로 시험한다.

**Production URL로 운영해 보기.** 워크플로우를 Publish하고 Production URL로 6건을 다시 보낸다. 결과를 편집 화면이 아니라 실행 목록에서 찾아 경로를 확인한다. Test URL로 시험할 때와 무엇이 달라지는지 정리한다.

# 3-7 - 메일 채널 교환·취소 문의 정규화

## 1. 실습 주제 및 상황

하루마켓 고객지원 메일함으로 교환과 주문 취소 문의가 들어온다. 이 문의를 실습 3-6과 같은 문의 기록 계약 형식으로 맞춘다. 웹 양식과 달리 메일에는 주문번호를 적는 칸이 없다. 고객이 제목이나 본문 어딘가에 적었거나 아예 적지 않았다. 실제 메일함을 연결하려면 계정이 필요하므로, 이 장에서는 메일을 표로 옮긴 샘플을 붙여 넣어 시작한다.

## 2. 이 실습의 목적

- 형식이 다른 채널의 입력을 같은 계약으로 정규화한다.
- 필드 변경, 누락, 복수 입력을 시험하면서 워크플로우가 오류 없이 조용히 틀리는 경우를 찾아낸다.
- 스스로 요구를 기능으로 바꾸고 선택 근거를 기록한다.

관련 이론: [3.3 아이템](../../../03_실행환경과데이터흐름읽기.md#33-노드-사이를-흐르는-데이터-아이템), [3.4 필드 참조와 표현식](../../../03_실행환경과데이터흐름읽기.md#34-필드-참조와-표현식), [3.6 요구에서 기능을 찾아 연결하기](../../../03_실행환경과데이터흐름읽기.md#36-요구에서-기능을-찾아-연결하기)

## 3. 관련 파일

- [`data/메일문의_샘플.json`](data/메일문의_샘플.json): 메일 10통. 메일마다 `from_name`, `from_address`, `subject`, `text`, `received_at`이 들어 있다.
- `02_워크플로우설계서_교환.md`: 2장 예시 답안. 문의 기록 계약을 목표 형식으로 쓴다.

## 4. 결과물

- `03_메일문의정규화.json`: 내보낸 워크플로우
- 다음 상태가 되어 있어야 한다.
    - 메일 10통이 빠짐없이 어느 한 경로의 끝에 도달하며, 경로별 아이템 수를 더하면 10이다.
    - 계약의 필드가 모두 있고 계약에 없는 필드는 없다.
    - `received_at`이 10건 모두 `+09:00`으로 끝난다.
    - `order_id`가 있는 건은 모두 `O-` 뒤 숫자 네 자리이고 대문자다.
    - 주문번호를 찾지 못한 건은 정보 요청 경로로, 보낸 사람 이름이 빈 건은 이름 요청 경로로 간다.

## 5. 해야 할 것

작업은 실습 3-6과 같은 구성이다. 메일을 받아 값을 다듬고, 필수 값을 검사하고, 계약의 필드명과 형식으로 옮기고, 주문번호를 찾아 검사한 뒤 요청 유형별로 경로를 나눈다. 시작 부분은 `Manual Trigger`와 `Edit Fields (Set)`의 JSON Output 모드로 샘플을 넣고 `Split Out`으로 `mails`를 나눈다.

다음은 3-6과 다르거나 반드시 지켜야 할 사항이다.

- **주문번호는 규칙으로만 찾는다.** 제목과 본문을 모두 찾아본다. LLM 추출은 4장 이후에 더한다.
- **찾지 못한 값을 추측해 채우지 않는다.** 계약이 정한 대로 `null`로 둔다.
- `channel` **값은** `email`**이다.**
- `received_at` **표기가 하나가 아니다.** 메일에 적힌 도착 시각을 쓰되 계약이 정한 표기로 맞춘다.
- `inquiry_id`**와** `request_id`**는 실습 3-6과 같은 이유로** `null`**로 둔다.**

다음 세 가지를 반드시 시험한다.

| 시험할 것 | 확인할 질문 |
|---|---|
| 필드 변경 | 보낸 사람 표시 이름의 표기가 달라도 계약의 같은 필드에 들어가는가? 다듬을 것인가, 그대로 둘 것인가? |
| 누락 | 주문번호가 없거나 형식이 다를 때 `null`로 두고 정보 요청 경로로 가는가? |
| 복수 입력 | 한 번의 실행에 메일 10통이 들어와도 아이템마다 같은 처리가 되는가? 본문에 주문번호가 두 개이면 무엇을 고르고, 그 판단이 맞는가? |

## 6. 이어서 더 해 볼 만한 주제

**웹과 메일을 하나의 공통 계약으로 정규화하기.** 두 가지 구성을 모두 만들어 비교한다. 첫째는 채널별로 값을 꺼내는 앞부분을 따로 두고 계약 형식으로 맞추는 뒷부분을 공유하는 구성이고, 둘째는 하나의 워크플로우에서 `channel` 값으로 분기하는 구성이다. 채널이 하나 더 늘어날 때 무엇을 고쳐야 하는지, 한 채널의 규칙을 고칠 때 다른 채널에 영향이 가는지 표로 정리한다.

**주문번호가 둘 이상인 메일의 처리 정하기.** 지금은 찾은 값 하나만 쓴다. 정규식으로 주문번호를 모두 찾아 개수를 세고, 하나면 그대로 진행하고 둘 이상이면 담당자 확인 경로로 보내도록 바꾼다. 어떤 메일에서 처리가 달라지는지 확인하고, 2장 계약에 어떤 항목을 더해야 하는지 제안한다.

**실제 메일 형식으로 바꿔 보기.** `Email Trigger (IMAP)` 노드의 공식 문서에서 Format 옵션(RAW, Resolved, Simple)을 확인하고, 시험용 메일로 실제로 어떤 필드가 나오는지 본 뒤, 샘플의 필드 이름과 대응표를 만든다. 달라지는 곳이 앞부분뿐인지 살펴본다. 시험용 메일 계정이 있다면 직접 연결해 본다. 이때 앱 비밀번호 같은 비밀 값은 자격 증명에만 넣고 결과물에는 적지 않는다.

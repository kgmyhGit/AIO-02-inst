# 5장 실습과제. Memory와 검색 근거를 갖춘 응답

# 개요

## 1. 이 실습을 통해 배울 것

이 장에서는 실행이 끝난 뒤에도 남는 데이터를 대화 메모리, 업무 상태, 지식 베이스로 나누어 쓴다. 스포츠 이벤트 문서와 Paul Graham 에세이를 적재해 검색으로 답하는 챗봇을 만들고, 하루마켓의 문의를 업무 데이터베이스에 저장한 뒤, 출처가 있는 정책 상담 채팅을 만들어 근거 평가표로 품질을 확인한다.

- 값마다 대화 메모리, 업무 상태, 지식 베이스, 외부 조회 중 어디에 두어야 하는지 구분한다.
- 문서를 분할하고 임베딩해 저장하고, 벡터 검색의 점수를 읽는 방법을 익힌다.
- 세션이 기억의 단위라는 것을 확인하고, 재시작 뒤에도 남고 섞이지 않는 메모리를 연결한다.
- 문의 기록과 요청 기록을 저장해 재문의를 요청에 연결한다.
- 모델이 적은 출처를 검색 결과와 대조하고, 근거가 없으면 추가 질문이나 담당자 확인으로 전환한다.

## 3. 공통사항

**진행 방식**

모든 실습은 같은 순서로 진행한다. 먼저 이 문서와 제공 파일만 보고 주어진 시간 동안 직접 해 본다. 시간이 끝나면 강사가 예시 답안을 보여 주며 왜 그렇게 되는지 설명한다. 자신의 결과물은 고치기 전 상태로 남겨 두고, 풀이와 비교해 다른 부분을 표시한다. 예시 답안과 달라도 이유가 맞으면 성립하는 답이 있으므로, 다른 점마다 자신의 이유를 적어 둔다.

**필요한 것**

- 4장에서 바꾼 실행 환경과 `웹 문의 처리`, `메일 문의 처리` 워크플로우
- ngrok 터널. `Webhook` 노드와 폼의 주소, 메일의 응답 링크는 3장에서 받은 공개 주소로 만들어지므로, 이 주소를 쓰기 전에 `ngrok http 5678`을 실행한다. 실습을 마치면 `Ctrl+C`로 닫는다. 3장에서 `localhost`로 설정했다면 필요하지 않다.
- 4장의 `OpenAI 실습`과 3장의 `하루마켓 업무 DB` 자격 증명. 실습 5-1의 `Notion 실습` 외에 새로 만드는 자격 증명은 없다.
- 임베딩 모델을 부를 수 있는 OpenAI 키. 실습 5-2에서 먼저 확인하고, 부를 수 없다는 오류가 나오면 강사에게 알린다.
- 실습 5-1에서 쓸 노션 계정. 계정이 없으면 5-1을 시작하기 전에 가입한다.
- 실습 5-3에서 Hugging Face의 CSV 파일을 내려받을 인터넷 연결. 가입이나 토큰은 필요 없다.
- 벡터 데이터베이스 서비스 가입은 필요하지 않다. 3장의 PostgreSQL에 확장을 더해 쓴다.

**비용**

임베딩도 모델 호출이다. 문서를 적재할 때 청크 수만큼, 벡터 검색할 때마다 검색어 한 번만큼 호출한다. 메모리를 붙이면 앞의 대화가 입력에 더해져 호출마다 입력 토큰이 늘어난다.

- 실습 5-2에서 n8n을 다시 시작한 뒤의 재적재와 실습 5-5의 재적재 확인 외에는 문서를 바꿨을 때만 다시 적재한다.
- 실습 5-3은 에세이 앞 30편만 적재한다. 215편을 모두 넣으면 청크 수가 여덟 배 넘게 늘어난다.
- 만드는 중에는 앞 노드의 출력에 데이터 고정을 걸어 두고, 모델이나 임베딩이 들어간 노드만 다시 실행한다.
- 근거 평가는 정해진 횟수(5-6은 1회, 5-7은 3회)만 실행한다.

**결과물 저장**

- 작업 폴더에 `05/` 폴더를 만들어 저장한다. 워크플로우는 JSON 파일로 내보낸다.
- 내보낸 파일에 OpenAI 키, 모의 API 키, 데이터베이스 비밀번호가 들어 있지 않은지 확인한다.

# 5-1 - 심리 상담 봇의 대화를 노션에 기록하기

## 1. 실습 주제 및 상황

채팅으로 고민을 이야기하면 공감하며 답하는 심리 상담 봇을 만든다. 봇은 "그것 때문인지 아침에 일어나기도 힘들어요."처럼 앞의 말에 기대는 문장을 이해해야 하고, 나눈 대화는 나중에 사람이 읽을 수 있게 노션(Notion) 데이터베이스에 남아야 한다. 대화 하나는 노션의 행 하나가 되며, 같은 대화가 이어지면 그 행의 본문에 질문과 답이 추가된다.

이 봇은 메모리와 노션 연동을 익히기 위한 실습용이며 실제 상담 서비스가 아니다. 노션은 외부 서비스이므로 제공한 가상의 문장만 입력하고, 자신이나 다른 사람의 실제 고민은 입력하지 않는다.

## 2. 이 실습의 목적

- `AI Agent`에 `Simple Memory`를 연결해 앞의 대화를 이해하는 채팅을 만든다.
- 외부 서비스의 자격 증명을 만들고 필요한 페이지에만 접근 권한을 준다.
- 노션 데이터베이스에서 행을 찾고, 없으면 만들고, 있으면 내용을 추가하는 흐름을 구현한다.
- 모델에게 다시 보내는 메모리와 사람이 읽으려고 남기는 기록이 서로 다른 것임을 확인한다.

관련 이론: [5.2 대화 메모리](../../../05_Memory와검색근거를갖춘응답.md#52-대화-메모리-앞의-대화를-다시-보여-주는-방법), [5.1 실행이 끝난 뒤에도 남는 데이터](../../../05_Memory와검색근거를갖춘응답.md#51-실행이-끝난-뒤에도-남는-데이터)

## 3. 관련 파일

- [`configs/심리상담봇_지시문.md`](configs/심리상담봇_지시문.md): 시스템 메시지, 노션 데이터베이스 구조, 시험 대화 C-1~C-5

필요한 외부 서비스는 노션이다. 개인 무료 요금제로 진행할 수 있는지는 가입 화면에서 확인한다. 질문마다 채팅 모델을 한 번 호출하므로 OpenAI 호출 비용이 생긴다.

## 4. 결과물

- `05_심리상담봇.json`: 내보낸 워크플로우. 노션 토큰이 들어 있지 않아야 한다
- 노션의 `상담기록` 데이터베이스: 세션마다 행이 하나씩 있고, 행의 본문에 그 세션의 질문과 답이 순서대로 쌓여 있어야 한다
- 대화 시험 기록표(아래 표)와, 메모리와 노션 기록의 차이를 세 문장 이내로 적은 메모

## 5. 해야 할 것

1. **노션을 준비한다.** 노션에 가입하고 새 페이지 `상담기록`을 만든 뒤, 지시문 문서 2절의 구조로 빈 표 데이터베이스를 만든다. <https://www.notion.com/my-integrations>에서 내부 통합(integration)을 만들고 Capabilities에서 콘텐츠 읽기, 갱신, 입력을 허용한다. Secrets 탭의 값을 복사한 뒤, `상담기록` 페이지 오른쪽 위 메뉴의 Connections에서 만든 통합을 연결한다. 노션의 화면 이름은 바뀔 수 있으므로 같은 뜻의 메뉴를 찾는다.
2. **n8n에 자격 증명을 만든다.** 이름이 `Notion 실습`인 Notion API 자격 증명을 만들고 Internal Integration Secret에 1단계의 값을 넣는다. 저장할 때 연결 시험이 통과하는지 본다.
3. **메모리가 있는 채팅을 만든다.** 새 워크플로우 `심리 상담 봇`을 만든다. `Chat Trigger` 노드(`채팅 받기`), `AI Agent` 노드(`상담 에이전트`), `OpenAI Chat Model`, `Simple Memory`를 연결한다. System Message에는 지시문 문서 1절을 넣고, `Simple Memory`의 Session ID는 Connected Chat Trigger Node, Context Window Length는 `10`으로 둔다. C-1과 C-2를 보내 C-2 실행의 모델 입력에 무엇이 들어 있는지 확인한다.
4. **응답을 보낼 노드를 정한다.** `채팅 받기`의 Options에 Response Mode를 더하고 Using Response Nodes를 고른다. 워크플로우의 맨 끝에 `Chat` 노드(`챗봇 응답`)를 놓고 Operation은 Send Message, Message에는 `상담 에이전트`의 답을 넣는다. 앞으로 에이전트와 응답 사이에 노션 노드가 들어갈 것이다. 응답 노드 없이 마지막 노드가 노션이면 채팅에 무엇이 표시될지 생각해 본다.
5. **이 세션의 행을 찾는다.** `상담 에이전트` 뒤에 `Notion` 노드(`세션 페이지 찾기`)를 놓는다. Resource는 Database Page, Operation은 Get Many, Data Source는 `상담기록`이다. Filter를 Build Manually로 두고 `SessionID`가 이번 메시지의 `sessionId`와 같은 행만 찾는다. 다른 노드의 값은 `$('채팅 받기').item.json.sessionId`처럼 노드 이름으로 참조한다. 찾은 행이 없을 때 뒤의 노드가 어떻게 되는지 실행해 보고, 이 노드의 Settings에서 필요한 설정을 찾아 바꾼다.
6. **행이 있는지로 경로를 나눈다.** `If` 노드(`페이지가 있는가`)로 앞 노드의 출력에 `url` 필드가 있는지 검사한다. Get Many의 출력을 먼저 열어 행을 찾았을 때와 못 찾았을 때 무엇이 다른지 본다.
7. **없으면 만들고 있으면 추가한다.** false 경로에 `Notion` 노드(`상담 페이지 만들기`)를 놓는다. Resource는 Database Page, Operation은 Create다. Title은 현재 시각이 들어간 `상담 yyyy-MM-dd HH:mm` 형식의 제목으로, `SessionID` 속성은 `sessionId`로 채운다. Blocks에는 제목 블록 `상담자`, 사용자가 보낸 글, 제목 블록 `답변`, 에이전트의 답을 차례로 넣는다. true 경로에는 `Notion` 노드(`상담 내용 추가`)를 놓는다. Resource는 Block, Operation은 Append After이고, Parent Block에는 찾은 행의 `url`을 넣으며 블록은 같은 순서로 구성한다. 두 경로를 모두 `챗봇 응답`에 연결한다.
8. **대화를 시험한다.** 지시문 문서 3절의 대화를 차례로 보내고 아래 표를 채운다. C-4는 새 대화를 시작한 뒤 보내며, `sessionId`가 바뀌었는지로 새 대화인지 판단한다. C-5 앞에는 `docker compose restart n8n`을 실행하고 브라우저를 새로 고친다. 단계마다 실행 기록의 `sessionId`와 노션의 행을 함께 확인한다.

    |---|---|---|---|---|---|

    | C-4 |  |  |  |  |  |
    | C-5 |  |  |  |  |  |

9. **메모리와 기록을 비교한다.** C-5의 답과 노션의 행을 나란히 보고, 노션에 대화가 남아 있는데도 봇의 답이 그렇게 나온 이유를 메모에 적는다.
10. **저장한다.** 워크플로우를 내보내 편집기로 열고 토큰이 없는지 확인한다. 실습을 마친 뒤에는 필요 없는 통합의 연결을 끊거나 통합을 삭제한다.

## 6. 이어서 더 해 볼 만한 주제

**노션 기록을 다음 상담에 활용하기.** 같은 사용자가 다음 날 돌아왔을 때 지난 상담의 요약을 참고하는 봇을 만든다. 상담이 끝날 때 대화를 요약해 노션의 속성에 저장하고, 새 대화가 시작되면 이 요약을 찾아 에이전트의 입력에 넣는다. 이때 세션 ID가 사용자를 증명하지 않는다는 점 때문에 무엇을 더 확인해야 하는지 적고, 요약과 전체 대화를 넣었을 때의 입력 토큰을 비교한다.

**독서 기록 봇으로 바꾸기.** 책을 읽고 느낀 점을 대화로 나누면 책마다 노션의 행이 하나씩 쌓이는 봇을 만든다. 이번에는 세션 ID 대신 책 제목으로 행을 찾게 바꾸고, 표기가 조금 다른 제목이 들어오면 어떤 일이 생기는지 확인한다. 행을 찾는 열쇠가 갖추어야 할 조건을 정리한다.

**회의 메모 봇으로 업무에 적용하기.** 회의 중 채팅으로 결정 사항을 보내면 회의별 노션 페이지에 쌓이는 봇을 만든다. 메모리에 둘 값과 노션에 남길 값을 표로 나누고, 노션 저장에 실패했을 때 사용자에게 무엇을 알려야 하는지 정해 오류 경로를 더한다.

# 5-2 - 스포츠 이벤트 문의 챗봇 만들기

## 1. 실습 주제 및 상황

가상의 스포츠 마케팅 회사에서 직원들이 기획 자료를 쓰다가 올림픽과 FIFA 월드컵에 관한 사실을 채팅으로 묻는다. 회사는 두 대회를 설명한 문서 두 개를 정리해 두었다. 이 문서를 벡터 검색할 수 있게 저장하고, "올림픽은 몇 년마다 열리나요?"처럼 물으면 문서에서 찾아 근거와 함께 답하는 챗봇을 만든다. 두 대회와 관계없는 질문에는 모델이 알고 있는 지식으로 답한다.

같은 챗봇을 두 가지 구조로 만든다. 첫째는 질문이 들어오면 먼저 벡터 검색하고 그 결과를 에이전트에게 넘기는 구조이고, 둘째는 검색을 에이전트의 도구로 주어 모델이 필요할 때 부르게 하는 구조다. 이 실습에서 쓰는 `Simple Vector Store`의 내용은 같은 n8n을 쓰는 다른 사용자도 저장소 이름으로 볼 수 있으므로 제공한 문서만 적재한다.

## 2. 이 실습의 목적

- 문서가 청크와 벡터가 되어 저장되고, 검색어도 같은 모델로 벡터가 되어 비교되는 흐름을 익힌다.
- 벡터 검색 결과의 점수를 읽고, 기준에 못 미치는 결과를 걸러 내는 방법을 익힌다.
- 정해진 순서로 벡터 검색하는 구조와 에이전트가 필요할 때 검색 도구를 부르는 구조를 비교한다.
- 저장 위치에 따라 데이터의 수명이 달라지는 것을 확인한다.

관련 이론: [5.4 문서를 검색할 수 있게 만들기](../../../05_Memory와검색근거를갖춘응답.md#54-문서를-검색할-수-있게-만들기-분할-임베딩-저장), [5.5 검색해서 답하기](../../../05_Memory와검색근거를갖춘응답.md#55-검색해서-답하기-검색-도구와-출처)

## 3. 관련 파일

- [`data/스포츠이벤트_문서/olympic.txt`](data/스포츠이벤트_문서/olympic.txt): 올림픽을 설명한 문서
- [`data/스포츠이벤트_문서/fifa_worldcup.txt`](data/스포츠이벤트_문서/fifa_worldcup.txt): FIFA 월드컵을 설명한 문서
- [`configs/스포츠이벤트챗봇_지시문.md`](configs/스포츠이벤트챗봇_지시문.md): 두 구조의 시스템 메시지와 사용자 메시지, 도구 설명, 시험 질문 G-1~G-7

## 4. 결과물

- `05_스포츠이벤트적재.json`, `05_스포츠이벤트챗봇_검색후전달.json`, `05_스포츠이벤트챗봇_도구.json`: 내보낸 워크플로우
- 벡터 검색 점수 기록과 질문별 시험 기록표(아래 표 두 개), 두 구조의 차이와 재시작 뒤 결과를 다섯 문장 이내로 적은 메모
- 다음 상태가 되어 있어야 한다.
    - 저장소 `sportevent-dataset-key`에 두 문서의 청크가 한 벌씩만 들어 있다.
    - 두 대회에 관한 질문에는 답 끝에 근거가 된 문서의 글이 붙어 있고, 문서에 답이 없으면 지시문에 정한 문구로 답한다.

## 5. 해야 할 것

1. **문서를 적재한다.** 새 워크플로우 `스포츠 이벤트 적재`를 만든다.
    - `n8n Form Trigger` 노드(`문서 올리기`): Form Title은 `스포츠 이벤트 문서 올리기`, 파일 칸의 Field Label은 `data`, Element Type은 File이며 Required Field를 켠다.
    - `Extract from File` 노드(`텍스트 읽기`): Operation은 Extract From Text File이다.
    - `Simple Vector Store` 노드(`문서 저장`): Operation Mode는 Insert Documents, Memory Key는 `sportevent-dataset-key`다.
    - 하위 노드: Embedding 연결점에 `Embeddings OpenAI`(모델 `text-embedding-3-large`)를, Document 연결점에 `Default Data Loader`를 붙인다. `Default Data Loader`의 Text Splitting을 Custom으로 바꾸고 `Recursive Character Text Splitter`(Chunk Size `1000`, Chunk Overlap `100`)를 붙인다.

    워크플로우를 실행하면 시험용 양식이 열린다. `olympic.txt`를 올려 제출하고 `문서 저장`의 출력에서 청크 수를 센다. 한 번 더 실행해 `fifa_worldcup.txt`를 올린다. 두 번째 적재 뒤 저장소에 무엇이 들어 있는지, `문서 저장`의 Clear Store를 켰다면 어떻게 되었을지 적는다. 같은 파일을 두 번 올리지 않는다.
2. **질문으로 벡터 검색하고 점수를 본다.** 새 워크플로우 `스포츠 이벤트 챗봇(검색 후 전달)`을 만든다. `Chat Trigger` 노드(`채팅 받기`) 뒤에 `Simple Vector Store` 노드(`문서 검색`)를 붙인다. Operation Mode는 Get Many, Memory Key는 `sportevent-dataset-key`, Prompt는 `{{ $json.chatInput }}`이고 Limit은 기본값 `4`로 둔다. `Embeddings OpenAI`는 적재와 같은 모델로 붙인다. 지시문 문서 3절의 G-1, G-2, G-6, G-7을 보내고, 실행마다 `문서 검색`의 출력을 열어 표를 채운다. 이 저장소의 점수는 클수록 가까운지 작을수록 가까운지 확인하고, 문서에 답이 있는 질문과 없는 질문의 1위 점수를 비교해 기준 값을 정한다.

    | 질문 | 1위 청크의 첫머리 | 1위 점수 | 4위 점수 | 문서에 답이 있는가 |
    |---|---|---|---|---|
    | G-1 |  |  |  |  |
    | G-2 |  |  |  |  |
    | G-6 |  |  |  |  |
    | G-7 |  |  |  |  |

3. **검색 결과를 걸러 에이전트에게 넘긴다.** `문서 검색` 뒤에 다음 노드를 차례로 붙인다.
    - `Filter` 노드(`점수 기준`): `score`가 2단계에서 정한 기준을 넘는 결과만 남긴다. 점수의 방향에 맞게 비교 연산을 고른다.
    - `Aggregate` 노드(`검색 결과 모으기`): Individual Fields로 `document.pageContent`를 모아 아이템 하나로 만든다.
    - `AI Agent` 노드(`답변 에이전트`): 지시문 문서 1절의 시스템 메시지와 사용자 메시지를 넣는다. Chat Model 연결점에 `OpenAI Chat Model`을, Memory 연결점에 `Simple Memory`(Context Window Length `20`)를 붙인다.

    G-6을 보내 `점수 기준`의 출력이 비는지 보고, 비었을 때 뒤의 노드가 어떻게 되는지 확인한다. 채팅에 답이 오지 않으면 `점수 기준`의 Settings에서 필요한 설정을 찾아 바꾼다.

    - Description에는 지시문 문서 2-2를 넣는다.
    - Embedding 연결점에 `Embeddings OpenAI`를 붙인다.

    새 대화에서 G-1~G-7을 차례로 보내고 표의 "도구" 칸을 채운다. 도구를 불렀는지와 도구가 돌려준 결과는 실행 화면의 Logs에서 `sportevent_info`를 눌러 확인한다.

    - G-6처럼 두 대회와 관계없는 질문에서 두 구조는 각각 임베딩 모델을 불렀는가?
    - G-4에서 두 구조가 벡터 검색에 넣은 검색어는 어떻게 다르며, 그 차이가 답에 어떤 영향을 주었는가?

7. **n8n을 다시 시작하고 묻는다.** 다음을 실행한 뒤 브라우저를 새로 고치고, 도구 구조에서 G-1을 다시 보내 결과를 적는다. 공식 문서가 이 저장소를 어떤 용도로 권하는지 찾아본다. 확인했으면 두 문서를 한 번씩 다시 적재한다.


## 6. 이어서 더 해 볼 만한 주제

**제품 설명서로 사내 문의 챗봇 만들기.** 회사 제품의 공개 설명서나 자주 묻는 질문 문서 두세 개를 같은 방식으로 적재하고, 직원이 고객을 응대하면서 찾아보는 챗봇을 만든다. 문서마다 파일 이름을 메타데이터로 붙여 답 끝에 어느 문서에서 찾았는지 적게 한다. 서로 다른 문서에 비슷한 내용이 있을 때 답이 어느 쪽을 따르는지 확인한다. 외부에 공개된 문서만 사용한다.

**청크 크기를 바꾸어 답 비교하기.** Chunk Size를 `300`과 `2000`으로 바꾸어 각각 다시 적재하고, G-1~G-7의 1위 점수와 답을 비교한다. 역대 우승국 목록처럼 짧은 줄이 이어지는 부분이 어떻게 나뉘는지 청크 출력에서 확인하고, "1990년대에 월드컵에서 우승한 나라를 모두 알려 줘"처럼 목록 여러 줄을 함께 봐야 하는 질문의 답이 어떻게 달라지는지 본다.

**답이 없는 질문을 늘려 기준 다시 정하기.** 두 대회를 다루지만 문서에 답이 없는 질문을 다섯 개 더 만들고, 답이 있는 질문과 1위 점수를 비교해 기준 값을 다시 정한다. 질문을 늘렸을 때 기준이 계속 통하는지 확인하고, 기준을 흔드는 질문의 공통점을 적는다.

# 5-3 - Paul Graham 에세이를 pgvector에 적재하고 질문하기

## 1. 실습 주제 및 상황

스타트업과 글쓰기에 관한 Paul Graham의 에세이를 읽으며 공부하려고 한다. 에세이 215편은 Hugging Face에 CSV 파일 하나로 공개되어 있다. 이 가운데 앞 30편을 PostgreSQL의 pgvector에 적재하고, 한국어로 물으면 영어 에세이를 검색해 출처(제목, 날짜)와 함께 답하는 챗봇을 만든다. 실습 5-2와 달리 n8n을 다시 시작해도 남는 저장소를 쓰고, 에세이마다 제목과 날짜를 메타데이터로 붙인다. 챗봇은 5-2처럼 두 구조로 만들되, 검색 후 전달 구조는 에이전트 대신 체인(`Basic LLM Chain`)으로 만든다.

에세이 본문의 저작권은 저자에게 있다. 수업 안에서 실습용으로만 쓰고, 본문을 다시 배포하거나 길게 옮기지 않는다.

## 2. 이 실습의 목적

- 지속되는 벡터 저장소에 CSV 자료를 적재하고, 열의 값을 메타데이터로 붙이는 방법을 익힌다.
- 메타데이터를 출처 표시에 쓰고, 검색어의 언어가 벡터 검색 결과를 바꾼다는 것을 확인한다.
- 체인과 에이전트가 앞의 대화를 다루는 방식이 어떻게 다른지 확인한다.
- 세션이 기억의 단위라는 것을 확인하고, n8n을 다시 시작한 뒤 벡터 저장소와 대화 메모리가 각각 어떻게 되는지 비교한다.

## 5. 해야 할 것

1. **실행 환경을 확인한다.** 이 실습에는 pgvector 확장이 있는 PostgreSQL이 필요하다. `docker compose ps`로 `db`의 이미지가 `pgvector/pgvector`인지 확인하고, 아니면 실습 5-4의 2단계를 따라 실행 환경을 먼저 바꾼다. 자격 증명은 3장의 `하루마켓 업무 DB`를 쓴다.
2. **데이터셋 명세를 읽는다.** 명세의 2절과 4절에서 내려받을 파일과 열 구조를, 6절과 8절에서 본문의 형식과 품질 문제를 확인한다. 이 실습이 데이터셋의 최신 파일이 아니라 커밋 하나에 고정된 파일을 내려받는 이유를 생각해 본다.
3. **적재 워크플로우를 만든다.** 새 워크플로우 `PG 에세이 적재`를 만든다. `Manual Trigger` 뒤에 다음 노드를 차례로 붙인다.
    - `Postgres` 노드(`기존 표 지우기`): Operation은 Execute Query, Query는 `DROP TABLE IF EXISTS pg_essays;`다. **테이블 이름을 한 번 더 확인한다.** 업무 데이터베이스의 다른 테이블을 지우면 이 장의 다른 실습 결과가 사라진다.
    - `HTTP Request` 노드(`CSV 내려받기`): URL은 아래 주소이고, Options의 Response에서 Response Format을 File로 둔다.

        ```text
        https://huggingface.co/datasets/sgoel9/paul_graham_essays/resolve/0c7155a53c25e24c9b9858314460e0ee1f5c3e4e/pual_graham_essays.csv
        ```

    - `Extract from File` 노드(`CSV 읽기`): Operation은 Extract From CSV이고, Options에 Header Row를 더해 켠다.
    - `Limit` 노드(`30편만 남기기`): Max Items는 `30`이다.
    - `Postgres PGVector Store` 노드(`에세이 적재`): Operation Mode는 Insert Documents, Table Name은 `pg_essays`다.
    - 하위 노드: `Embeddings OpenAI`(모델 `text-embedding-3-large`), `Default Data Loader`, `Recursive Character Text Splitter`(Chunk Size `1000`, Chunk Overlap `150`)를 붙인다. `Default Data Loader`는 Mode를 Load Specific Data로 바꾸어 Data에 `{{ $json.text }}`를 넣고, Options의 Metadata에 `essay_id`, `title`, `date`를 더해 CSV의 `id`, `title`, `date`로 채운다. Text Splitting은 Custom으로 둔다.

    실행해 보고 `기존 표 지우기` 뒤의 노드가 실행되지 않으면 이 노드의 Settings에서 필요한 설정을 찾아 바꾼다.
4. **적재 결과를 확인한다.** `CSV 읽기`의 출력에서 아이템 수와 열을, `에세이 적재`의 출력에서 청크의 글과 메타데이터를 본다. 새 워크플로우에 `Manual Trigger`와 `Postgres` 노드(Execute Query)를 두고 다음 SQL 문을 하나씩 실행해 표를 채운 뒤, 명세 5절의 청크 수와 비교한다.

    ```sql
    SELECT count(*) AS chunks,
           count(DISTINCT metadata->>'essay_id') AS essays,
           max(vector_dims(embedding)) AS dims
    FROM pg_essays;
    ```

    ```sql
    SELECT metadata->>'title' AS title, metadata->>'date' AS date, count(*) AS chunks
    FROM pg_essays
    GROUP BY 1, 2
    ORDER BY chunks DESC
    LIMIT 5;
    ```

    | 확인할 것 | 결과 |
    |---|---|
    | 청크 수와 에세이 수 |  |
    | 벡터 차원 |  |
    | 청크가 가장 많은 에세이와 그 청크 수 |  |
    | 날짜가 빈 에세이가 있는가 |  |

    `기존 표 지우기`를 끈 채 다시 실행하면 `pg_essays`와 벡터 검색 결과가 어떻게 될지 생각해 본다. 임베딩 비용이 다시 들므로 실행하지는 않는다.
5. **검색 후 전달 구조를 만든다.** 새 워크플로우 `PG 에세이 챗봇(검색 후 전달)`을 만든다.
    - `Chat Trigger` 노드(`채팅 받기`): 마지막 노드의 `output` 필드가 채팅에 표시된다.
    - `Postgres PGVector Store` 노드(`에세이 검색`): Operation Mode는 Get Many, Table Name은 `pg_essays`, Prompt는 `{{ $json.chatInput }}`, Limit은 `4`다. Options에 Distance Strategy를 더해 Cosine으로 둔다. 적재와 같은 모델의 `Embeddings OpenAI`를 붙인다.
    - `Aggregate` 노드(`검색 결과 모으기`): Aggregate를 All Item Data로 두어 검색 결과 네 개를 아이템 하나로 모은다.
    - `Basic LLM Chain` 노드(`에세이로 답하기`): 지시문 문서 1절의 시스템 메시지와 사용자 메시지를 넣고 `OpenAI Chat Model`을 붙인다.
    - `Edit Fields (Set)` 노드(`채팅 답`): `output` 필드에 `{{ $json.text }}`를 넣는다.

    E-1, E-2를 보내고 이어서 E-3을 보낸다. 실행마다 `에세이 검색`의 출력에서 1위 에세이와 점수를 아래 표에 적는다. 이 저장소의 점수 방향도 확인한다.
6. **도구 구조를 만든다.** 새 워크플로우 `PG 에세이 챗봇(도구)`를 만든다. `채팅 받기` 뒤에 `AI Agent` 노드(`에세이 에이전트`)를 두고 System Message에 지시문 문서 2-1을 넣는다. `OpenAI Chat Model`과 `Simple Memory`(Context Window Length는 기본값)를 붙인다. Tool 연결점에는 `Postgres PGVector Store`를 붙여 노드 이름을 `paul_graham_search`로, Operation Mode를 Retrieve Documents (As Tool for AI Agent)로, Table Name을 `pg_essays`로 두고 Limit은 `4`로 맞춘다. Description에는 지시문 문서 2-2를 넣고, 적재와 같은 모델의 `Embeddings OpenAI`를 붙인다.

    `CSV 읽기`의 출력에서 에세이 제목을 보고 E-7과 E-8을 만든다. 새 대화에서 E-1~E-8을 차례로 보내고, Logs에서 `paul_graham_search`를 눌러 모델이 만든 검색어와 돌려받은 결과를 확인한다. 검색 후 전달 구조에도 E-4~E-8을 보내 표를 채운다.

    | E-8 |  |  |  |  |

7. **앞의 대화와 세션을 확인한다.** 표의 E-3을 보고 두 구조 중 어느 쪽이 "그 글"을 이해했는지, 그 이유가 무엇인지 메모에 적는다. 이어서 도구 구조에서 새 대화를 시작해 E-3만 보낸다. `채팅 받기` 출력의 `sessionId`가 바뀌었는지로 새 대화가 시작되었는지 판단하고, 답이 어떻게 달라졌는지 적는다.
8. **n8n을 다시 시작하고 묻는다.** 도구 구조에서 E-1을 보낸 대화 창을 그대로 두고 `docker compose restart n8n`을 실행한다. 브라우저를 새로 고쳐 E-3을 보내고 세션 ID와 답을 기록한다. 이어서 E-1을 다시 보내 에세이를 검색할 수 있는지 확인한다. 실습 5-2의 7단계 결과와 비교해 두 저장소의 차이를 메모에 적는다.
9. **저장한다.** 세 워크플로우를 내보내고, 내보낸 파일에 데이터베이스 비밀번호와 OpenAI 키가 없는지 확인한다.

## 6. 이어서 더 해 볼 만한 주제

**다른 글 모음으로 바꾸어 적재하기.** 이용 조건이 공개된 다른 글 모음이나 자신이 쓴 블로그 글을 같은 구조로 적재한다. 열 구성이 다르면 무엇을 메타데이터로 붙일지 정하고, 그 값을 출처 표시에 쓴다. 적재하기 전에 이용 조건을 먼저 확인한다.

**연도로 걸러 찾기.** `date`는 `September 2004`처럼 문자열이다. 적재할 때 연도만 뽑아 `year` 메타데이터를 더하고, 검색할 때 Metadata Filter로 `year`가 `2009`인 청크만 찾게 한다. "2009년에 쓴 창업 조언"처럼 기간이 들어간 질문을 필터 없이 검색할 때와 비교한다.

**전체 215편의 비용 추정하기.** 명세 5절의 글자 수로 전체를 적재할 때의 청크 수와 임베딩 토큰, 비용을 추정한다. 실제로 전체를 적재한다면 `30편만 남기기`를 끄고 걸린 시간과 청크 수를 재어 추정과 비교한다. 1위 점수가 30편일 때와 어떻게 달라지는지도 본다.

# 5-4 - 문의 기록과 요청 기록을 업무 데이터베이스에 저장하기

## 1. 실습 주제 및 상황

4장의 `웹 문의 처리`는 결과를 확인만 하고 저장하지 않았다. 이 실습에서는 웹 문의를 받자마자 번호를 받아 저장하고, 분류 결과를 더하고, 반품 요청을 요청 기록으로 만들거나 같은 주문의 재문의를 연결한다. 2장 예시 답안 `02_워크플로우설계서_반품.md`의 계약과 전이표에서 다음 네 줄을 구현한다.

| 전이 | 조건 | 할 일 |
|---|---|---|
| T01 | 같은 주문의 열린 요청이 없다 | 반품·교환·`mixed` 문의면 요청 기록을 만든다 |
| T02 | 같은 주문의 열린 요청이 있고, 연결 후 재문의가 1회다 | 문의를 요청에 연결하고 상태는 그대로 둔다 |
| T03 | 연결 후 재문의가 2회 이상이다 | 문의를 연결하고 요청을 `under_review`로 바꾸며 넘긴 이유를 `repeat_inquiry`로 적는다 |
| T08 | 새 요청의 유형이 `mixed`이거나 분쟁·재문의 언급 표시가 참이다 | 요청을 만들면서 곧바로 `under_review`로 둔다 |

배송·취소·기타 문의는 요청 기록을 만들지 않고 문의 기록만 남긴다. 정보 요청과 판단 이후의 전이는 6장에서 붙인다.

2. **실행 환경을 바꾼다.** 벡터 열을 쓰려면 pgvector 확장이 있는 이미지가 필요하다. 먼저 지금 `db`의 기반 운영체제를 확인한다.

    ```bash
    docker compose exec db cat /etc/os-release
    ```

    `compose.yml`을 5장판으로 바꾼다. `VERSION_CODENAME`이 `bookworm`이면 `db`의 `image`를 `pgvector/pgvector:0.8.6-pg17-bookworm`으로 고치고, `trixie`면 그대로 둔다. `data/policies` 폴더를 작업 폴더에 `policies`라는 이름으로 복사한다. `docker compose up -d`로 다시 실행하고 `docker compose logs --tail 30 db`로 로그를 확인한다. 볼륨은 지우지 않는다. 실습 5-3을 하면서 이미 바꾸었다면 확인 지점만 다시 본다.
    - **확인 지점:** 세 서비스가 실행 중이고, 정렬 규칙 버전 경고(`collation version mismatch`)가 없으며, 이전 장의 워크플로우가 남아 있는가? 왜 기반 운영체제를 맞추는가?
3. **업무 데이터베이스를 바꾼다.** 새 워크플로우 `업무 DB 확인`을 만들고 `Manual Trigger` 뒤에 `Postgres` 노드(`하루마켓 업무 DB`, Execute Query)를 둔다. `업무DB_5장변경.sql`의 내용을 붙여 넣어 실행한 뒤 `SQL_확인문장.md`의 1-1, 1-2로 결과를 확인한다.
4. **문의 기록을 받자마자 저장한다.** `웹 문의 처리`를 복제하지 않고 그대로 고친다. 복제하면 같은 `Webhook` 경로를 쓰게 되어 Publish할 때 충돌하기 때문이다. `문의저장_노드설정.md`의 2절을 따라 `문의 기록 만들기`와 `주문번호 형식 확인` 사이에 `문의 기록 저장`과 `번호 붙이기`를 끼우고, 2-3을 따라 `분류 결과 붙이기`의 식을 고친다. R-1을 보내 발급된 번호를 확인한 뒤, 같은 요청을 한 번 더 보내 무슨 일이 생기는지 본다. 확인했으면 초기화 스크립트 [가]를 실행한다.
    - **확인 지점:** 고객 문장을 SQL 문 안에 이어 붙이지 않고 Query Parameters로 넘기는 이유는 무엇인가? 왜 분류보다 앞에서 저장하는가?
5. **분류 결과를 저장한다.** 설정 3절을 따라 `분류 값 확인`의 true 출력과 `요청 유형 경로` 사이에 `분류 결과 저장`을 끼운다.
6. **요청 기록을 만들거나 연결한다.** 설정 4절을 따라 만든다. 하는 일은 한 문장이다. 같은 주문에 끝나지 않은 요청이 있으면 연결하고, 없으면 요청 대상 유형일 때만 새로 만든다.
    - **확인 지점:** 연결 여부를 유형과 주문번호 중 무엇으로 정하며, 왜 그런가? 조회 결과가 없을 때도 다음 노드가 실행되는가? 재문의 횟수를 무엇으로 세는가? 이미 `under_review`인 요청에서 뒤의 노드가 실행되는가? 네 갈래가 어떻게 하나로 모이는가?
7. **여섯 건을 차례로 보내고 대조한다.** 초기화 스크립트 [가]를 실행한 뒤 샘플 여섯 건을 **적힌 순서대로 한 건씩** 보낸다. `SQL_확인문장.md`의 1-3, 1-4로 결과를 확인해 표를 채운다.

    | 사례 | `inquiry_id` | `detected_type` | `request_id` | 요청의 `request_status` | `handover_reason` | 전이 |
    |---|---|---|---|---|---|---|
    |  |  |  |  |  |  |  |

8. **처음 상태로 되돌리는 방법을 확인한다.** 초기화 스크립트 [가]를 실행하고 1-3으로 결과를 본다. 시험 데이터를 남긴 채 같은 입력을 보내면 어떻게 달라질지 생각해 본다.
9. **저장한다.** `웹 문의 처리`와 `업무 DB 확인`을 내보낸다. 이 장을 진행하는 동안에는 5장 구성을 유지한다.

## 6. 이어서 더 해 볼 만한 주제

**개인 할 일 기록의 상태 저장하기.** 메일이나 메시지에서 할 일을 받아 번호를 붙여 저장하고, 같은 일의 재요청을 앞의 기록에 연결하는 작은 흐름을 만든다. 상태 값을 `open`, `waiting`, `done`으로 정하고, 재요청이 두 번 넘으면 표시를 올린다. 문장이 달라도 같은 일로 볼 기준을 무엇으로 할지가 이 주제의 핵심이다.

**같은 요청이 두 번 들어올 때 막아 보기.** 4단계에서 확인한 중복 저장을 먼저 생각해 본다. 요청 본문과 시각으로 키를 만들어 중복이면 새 행을 만들지 않게 해 본다. 이 방법의 한계를 적은 뒤 8장에서 다루는 방법과 비교한다.

**문의 처리 현황 보기 만들기.** `inquiries`와 `requests`를 묶어 유형별 건수, 담당자에게 넘어간 건수, 재문의가 많은 주문을 뽑는 SQL을 쓰고, 하루 한 번 실행되는 워크플로우로 요약을 만든다. 모델 없이 규칙으로 만들 수 있는 보고의 범위를 확인한다.

# 5-5 - 반품·배송 정책 문서 적재와 검색 확인

## 1. 실습 주제 및 상황

고객이 채팅으로 정책을 물으면 답하려면 먼저 정책을 찾을 수 있어야 한다. 하루마켓의 반품·배송 정책 문서 6개를 PostgreSQL에 메타데이터와 함께 적재하고, 질문을 벡터 검색해 점수를 읽은 뒤 실습 5-6에서 쓸 점수 기준의 후보를 정한다.

## 2. 이 실습의 목적

- 지속되는 벡터 저장소에 문서를 적재하고 메타데이터를 붙이는 방법을 익힌다.
- 재색인이 왜 지우고 넣는 일인지 결과로 확인한다.
- 점수의 방향을 확인하고, 답이 있는 질문과 없는 질문을 가르는 기준을 찾는다.

관련 이론: [5.4 문서를 검색할 수 있게 만들기](../../../05_Memory와검색근거를갖춘응답.md#54-문서를-검색할-수-있게-만들기-분할-임베딩-저장)

- `05_기능탐색기록_정책적재.md`: 탐색 기록과 점수 기준 후보, 그 근거

## 5. 해야 할 것

1. **기능을 찾아 기록한다.** 양식을 복사해 `05_기능탐색기록_정책적재.md`를 만든다. 요구는 "정책 문서 파일을 뜻으로 검색할 수 있게 저장한다"이다. 공식 문서에서 벡터 저장소 노드와 문서 로더를 찾아 비교한다.
    - **확인 지점:** 실습 5-2에서 쓴 저장소를 그대로 쓰면 어떤 문제가 있는가?
2. **정책 문서를 읽는다.** `policies/shipping_return/RET-01.md`를 열어 첫머리의 머리 정보와 `##`로 시작하는 절 제목을 확인한다. `정책문서_목록.md`에서 일부러 남긴 빈칸을 본다.
    - **확인 지점:** 절 제목을 "배송비"처럼 짧게 쓰지 않은 이유는 무엇인가?
3. `정책 적재` **워크플로우를 만든다.** `정책적재_노드설정.md`의 1절을 따라 만든다. Table Name은 반드시 `policy_chunks`로 바꾼다.
    - **확인 지점:** 지우는 단계가 왜 적재 앞에 있으며, 지우는 조건에 무엇이 꼭 있어야 하는가? 파일 경로는 어느 기준의 경로인가? 형식이 틀린 파일은 어떻게 되는가? 왜 문서를 한 건씩 적재하는가? 메타데이터 일곱 개는 각각 어디에 쓰이는가?
4. **적재하고 청크를 읽는다.** 실행한 뒤 `정책 문서 읽기`, `머리 정보 확인`, `청크 적재`의 출력을 차례로 본다. `SQL_확인문장.md`의 2-1~2-4로 문서별 청크 수, 청크의 글, 메타데이터, 벡터 차원을 확인해 표를 채운다.

    | 문서 | 청크 수 | 둘째 청크의 첫머리 |
    |---|---:|---|
    | `COM-01`, `SHP-01`, `SHP-02`, `RET-01`, `RET-02`, `RET-03` |  |  |

5. **다시 적재하면 어떻게 되는지 확인한다.** `기존 청크 지우기`를 선택해 `D` 키로 잠시 비활성화하고 다시 실행한 뒤 2-1, 2-3을 본다. 다시 활성화해 한 번 더 실행하고 결과를 비교한다. 이 단계는 임베딩을 두 번 더 호출하므로 한 번만 한다.
    - **확인 지점:** 문서를 고친 뒤 지우지 않고 넣었다면 벡터 검색에서 어떤 일이 생겼겠는가?
6. **벡터 검색하고 점수를 읽는다.** 설정의 2절을 따라 `검색 확인`을 만들어 질문 6개를 Get Many로 검색한다. Metadata Filter로 `group`이 `shipping_return`인 청크만 찾는다. 다음 표를 채운 뒤 점수의 방향을 먼저 확인하고, 답이 있는 질문과 없는 질문의 1위 점수를 비교해 점수 기준 후보를 정한다. 두 값이 겹치면 답이 있는 질문의 1위가 찾아야 할 문서였는지부터 확인한다. 정한 후보와 근거를 기능 탐색 기록에 적는다.

    | 질문 | 찾아야 할 문서 | 1위(점수) | 2위(점수) | 3위(점수) | 4위(점수) |
    |---|---|---|---|---|---|
    |  |  |  |  |  |  |

7. **저장한다.** 두 워크플로우를 내보낸다.

## 6. 이어서 더 해 볼 만한 주제

**내 문서로 적재 규칙 만들기.** 업무 매뉴얼이나 공부 노트처럼 자신의 문서 다섯 개를 고른다. 문서마다 넣을 머리 정보를 정하고, 절 제목만 보고도 내용을 알 수 있게 고친 판과 원본을 각각 적재해 같은 질문으로 비교한다. 문서를 고치는 일이 검색 설정을 고치는 일과 비교해 얼마나 효과가 있는지 살펴본다. 외부에 공개해도 되는 문서만 사용한다.

**PDF와 표가 있는 문서 적재해 보기.** PDF 파일을 Binary 로더로 적재하고, 표가 많은 문서에서 청크가 어떻게 나뉘는지 읽어 본다. 표가 잘리는 경우 검색 결과가 어떻게 되는지 확인하고, 표를 문장으로 풀어 쓴 판과 비교한다.

**분할 조건을 바꾸어 점수 분포 비교하기.** Chunk Size 200, 100, 1000으로 각각 별도 테이블에 적재하고, 같은 질문 6개의 1위 점수와 답이 있는 질문·없는 질문의 간격을 비교한다. 어느 조건에서 기준을 정하기 쉬운지 표로 정리한다. 이 실험은 실습 5-7의 재색인 실험으로 이어진다.

# 5-6 - 출처가 있는 정책 상담과 후속 질문

## 1. 실습 주제 및 상황

고객이 채팅으로 반품·배송 정책을 묻고 이어서 물을 수 있는 정책 상담 채팅을 만든다. 답에는 검증을 통과한 출처가 붙고, 근거가 없으면 담당자에게 넘어간다. 채팅의 세션 ID는 고객이 누구인지 증명하지 않으므로, 채팅에서 주문을 조회하지는 않는다. 끝으로 질문 세트를 실행해 근거 평가표를 만든다.

## 2. 이 실습의 목적

- 벡터 검색을 계약이 있는 도구로 감싸 점수 기준을 규칙으로 적용한다.
- 재시작 뒤에도 남는 메모리를 세션 ID로 나누어 연결한다.
- 모델이 적은 출처를 그 턴의 검색 결과와 대조한다.
- 근거가 없을 때의 전환과 확인 질문 한도를 규칙으로 구현하고, 근거 평가표로 품질을 판정한다.

관련 이론: [5.2 대화 메모리](../../../05_Memory와검색근거를갖춘응답.md#52-대화-메모리-앞의-대화를-다시-보여-주는-방법), [5.3 세션](../../../05_Memory와검색근거를갖춘응답.md#53-세션-기억을-나누는-열쇠), [5.5 검색해서 답하기](../../../05_Memory와검색근거를갖춘응답.md#55-검색해서-답하기-검색-도구와-출처), [5.6 근거가 없을 때와 근거 평가](../../../05_Memory와검색근거를갖춘응답.md#56-근거가-없을-때와-근거-평가)

5. `정책 상담 채팅`**을 만든다.** 설정 2절을 따라 만든다. `정책 검색`은 편집 화면에서 시험할 때도 Publish해 둔다. 에이전트가 도구로 부르는 `정책 검색`은 게시 버전을 찾기 때문이다. 게시하지 않으면 도구 호출이 실패하고 에이전트가 근거 없이 담당자에게 넘긴다.

## 6. 이어서 더 해 볼 만한 주제

**에세이 챗봇을 출처 있는 채팅으로 키우기.** 실습 5-3의 Paul Graham 에세이 챗봇을 이 실습의 구조로 다시 만든다. 벡터 검색을 서브워크플로우 도구로 감싸 점수 기준을 규칙으로 적용하고, 지속 메모리와 인용 검증을 붙인다. 모델이 적은 `essay_id`가 그 턴의 검색 결과에 있는지 대조하고, 적재하지 않은 에세이를 물었을 때 어떻게 답할지 정한다. 근거 평가 질문을 열 개 만들어 5-3의 도구 구조와 비교한다.

**창 크기와 비용의 관계 재기.** `Postgres Chat Memory`의 창 크기를 바꾸고, 다섯 턴 이어지는 대화의 턴별 입력 토큰을 표로 적는다. 도구 결과가 메모리에 함께 쌓일 때 비용이 어떻게 늘어나는지 계산한다. 이어지는 질문을 이해하는 데 실제로 필요한 창 크기를 찾아 본다.

**답변 근거 판정의 일부를 자동화하기.** 사람이 판정한 평가표를 정답으로 두고, 답과 인용 문서를 모델에게 주어 "문서에 없는 내용이 있는가"를 판정하게 한다. 사람의 판정과 일치하는 비율을 재고, 어떤 경우에 틀리는지 적는다. 이 판정 결과를 믿을 수 있는 범위를 정리해 본다.

## 5. 해야 할 것

다음 여섯 가지를 한다. (가)는 실습 5-4의 4~8단계, (나)는 실습 5-5의 3~6단계, (다)는 실습 5-6의 2~8단계, (바)는 실습 5-6의 9단계를 참고한다.

- (가) **메일 문의 저장:** 4장 `메일 문의 처리`에 저장 구조를 적용한다. 모든 메일을 문의 기록으로 저장하고, 교환 유형(`exchange_option`, `exchange_other_product`)과 `mixed`는 요청 기록을 만들거나 같은 주문의 열린 요청에 연결한다. 원하는 옵션은 4장에서 뽑은 고객 표현 그대로 `desired_option`에 남긴다. 취소 문의는 문의 기록만 남긴다.
- (나) **교환·취소 정책 적재:** 문서 6개를 같은 `policy_chunks` 테이블에 `group` `exchange_cancel`로 적재한다. 교환·취소 질문으로 검색 확인 표를 직접 만든다.
- (다) **교환·취소 정책 상담:** `교환 취소 상담 에이전트`와 `교환 취소 상담 채팅`을 만든다. 검색 도구는 `정책 검색`을 **복제하지 않고 다시 쓴다.** 시스템 메시지와 도구 설명은 교환·취소에 맞게 직접 쓴다.
- (라) **두 사용자의 세션 분리:** 채팅을 공개로 전환하고 세 워크플로우를 Publish한다. 일반 창과 시크릿 창에서 두 사용자처럼 번갈아 묻는다. 한 사용자는 자기 주문번호와 상품을 말한다. 다른 사용자의 답에 그 정보가 나오는지 확인하고 `chat_memory`의 세션별 행과 대조한다. 이어서 두 대화를 한 번의 실행에 넣었을 때 기억이 섞이는 조건을 재현하고, 한 턴씩 실행하도록 되돌린 결과와 비교한다.
- (마) **답이 없는 질문:** 문서에 없는 질문, 기준이 정해지지 않은 질문, 모호한 질문, 개별 사실을 묻는 질문을 각각 하나 이상 시험한다.
- (바) **근거 평가표:** 질문 세트를 세 번 실행하고 판정한다. 실패마다 실패 유형과 먼저 고칠 곳을 적는다.

지켜야 할 조건은 다음과 같다.

- 고객 문의 원문은 SQL 문에 직접 끼워 넣지 않고 Query Parameters로 넘긴다.
- 메일은 한 통씩 처리한다. 앞 메일이 저장한 요청을 다음 메일이 읽어야 하기 때문이다.
- 세션 ID를 모델이 만들거나 바꾸지 않는다. 모델에게 세션 ID를 주지 않는다.
- 에이전트를 담은 서브워크플로우는 언제나 한 턴씩 부른다.
- 에이전트에 연결하는 도구 노드의 이름은 영문자, 숫자, 밑줄로 붙인다.
- 넘길 때의 안내문은 고정 문구로 하고, 출처 줄은 검증을 통과한 인용으로 규칙이 붙인다.
- 교환이나 취소를 접수했다거나 진행하겠다고 안내하지 않는다. 집행은 6장에서 승인과 함께 다룬다.
- "L 사이즈 재고 있어요?"처럼 문서로 답할 수 없는 개별 사실은 채팅에서 답하지 않는다.

## 6. 이어서 더 해 볼 만한 주제

**재색인과 검색 설정 비교 실험.** 같은 질문 세트로 검색 설정을 바꾸어 결과를 비교한다. 분할 조건 A(Chunk Size 200, Chunk Overlap 20, Split Code `markdown`), B(Text Splitting Simple, 청크 크기 1000, 겹침 200), C(Chunk Size 100, Chunk Overlap 0, Split Code `markdown`)를 정한다. 조건마다 별도 테이블(`policy_chunks_b`, `policy_chunks_c`)에 적재하고, `정책 검색`의 Table Name만 바꾸어 실행한다. Limit 2와 4도 비교한다. 검색 적중 비율, 인용 정확 비율, 잘못된 전환 수, 모델에게 간 글의 평균 길이를 표로 정리한다.

**정책 개정을 재색인으로 반영하기.** `정책개정안_선택심화.md`는 단순 변심 반품 기한을 14일로 바꾼 가상 개정안이다. `RET-01.md`를 따로 보관하고 개정안을 같은 이름으로 복사한다. `기존 청크 지우기`를 비활성화한 채 적재해 "단순 변심 반품은 며칠 안에 해야 해요?"를 묻고, 두 버전이 함께 검색되는지와 답이 어느 쪽을 따르는지 기록한다. 활성화해 다시 적재한 뒤 같은 질문을 한다. 끝나면 **원래** `RET-01.md`**로 되돌리고 다시 적재한다.**

**사용자 인증과 세션 ID 연결 설계하기.** 지금 세션 ID는 사용자가 누구인지 증명하지 않는다. 로그인한 사용자에게만 주문을 조회하게 하려면 세션 ID를 어디서 받고 무엇으로 검증해야 하는지 설계서를 쓴다. 웹 양식이 서명된 토큰을 보낸다고 가정하고, `Webhook`으로 받은 토큰을 검증한 뒤 세션과 주문을 연결하는 흐름을 그려 본다. 어떤 값을 모델에게 주면 안 되는지도 표시한다.
